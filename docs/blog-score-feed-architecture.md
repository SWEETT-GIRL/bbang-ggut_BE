# 메인 피드 — 블로그 크롤링 기반 빵 카테고리별 가게 추천 (계획)

> 상태: **계획 문서 (코드 없음)** · 작성일 2026-06-02 · 브랜치 작업 예정
> 컨셉: 다이닝코드 초기 방식 — 네이버 블로그/리뷰를 크롤링해 가게를 **빵 카테고리별로 점수화**하고 메인 피드에서 추천한다.
> **PoC 범위: 망원동(region3rd = '망원동') 가게만** 먼저 크롤·점수화해 공식을 검증한 뒤 확장.

---

## 0. 절대 원칙 — 운영DB 무손상

- **운영DB(`soboro`)에는 쓰기를 절대 하지 않는다.** 기존 크롤러(`scripts/naver_menu_scraper.py` 등)는 운영DB에 직접 write 하지만, **이 기능은 그 경로를 일절 쓰지 않는다.**
- 가게 목록은 **1회성 read-only 스냅샷**(SELECT export)으로만 가져온다. (운영 store/menu/image 테이블 read는 스냅샷 시점 1회, 이후 무접근)
- 크롤링 결과·점수·피드 데이터는 **전부 별도 테스트 저장소**에만 적재한다.
- 지금은 테스트 단계이므로 격리를 가볍게: **별도 로컬/테스트 PostgreSQL(또는 SQLite)** 1개. 운영 승격 시 별도 스키마/인스턴스로 옮기는 건 후속 과제.

```
[운영 soboro DB] --(read-only 스냅샷 export 1회)--> stores_snapshot.csv
                                                          │
                                              [블로그 크롤러 (신규 파이썬)]
                                                          │  네이버 블로그/리뷰
                                                          ▼
                                            [별도 테스트 DB: bbang_score]
                                            blog_post / category_score ...
                                                          │
                                              결과 확인: HTML 리포트
```

> **신규 API는 만들지 않는다.** 이번 단계는 크롤 → 점수 산출 → **HTML 리포트**로 결과 검증까지. 앱 피드 노출(API 연동)은 점수 신뢰도 확인 후 별도로 결정.

## 1. 데이터 소스 — 하이브리드 (API 발견 + 스크래핑 본문, 둘 다 필수)

**"목록은 오픈API, 알맹이는 스크래핑"** 하이브리드. 스크래핑은 본문/리뷰 확보에 **반드시 포함**한다.

| 단계 | 소스 | 용도 | 수단 |
|------|------|------|------|
| 발견 | 네이버 블로그 검색 오픈API (`/v1/search/blog.json`) | 가게별 언급 글 수(`total`) · 글 날짜(`postdate`) · 글 URL 목록 | 안정적·차단위험 낮음, 일 25,000건 한도 |
| 본문 | 블로그 글 **스크래핑** (필수) | 전문 텍스트 → 카테고리 키워드 매칭 · 감성 분석 · **협찬/광고/체험단 판별** | API `description`(스니펫)만으로는 부족 → 본문 스크래핑 필수 |
| 품질 | 네이버 플레이스 **스크래핑** (필수) | 리뷰 수(품질 prior) | 공식 API 없음. 기존 `naver_menu_scraper.py` 스크래핑 로직 재사용 |
| 대상 | 운영 store 스냅샷 | 크롤 대상 가게 목록 (id·이름·지역·좌표) | 운영DB read-only SELECT 1회 export (망원동) |

> 검색 쿼리 형태: `"{region2nd} {store_name}"` (예: `"망원동 소금집"`). 동명 가게 오염 방지로 지역명 prefix. 매칭 게이트는 기존 `naver_match.py`의 정규화/충돌차단 로직 참고.
> 스크래핑 안정성: IP 차단·HTML 변경 대비 → 요청 간 슬립·재시도·User-Agent 로테이션, 망원동 소규모라 부하 낮음.

## 3. 점수 공식

가게 `s`, 카테고리 `c` 단위로 점수 산출. 선택된 5개 신호를 모두 반영.

### 3.0 협찬/광고/체험단 글 제외 (점수 산입 전 필터)
점수 계산 **이전에** 광고성 글을 모두 걸러낸다. (`store_blog_post.is_ad = true` → 점수 산입 제외, 리포트엔 표시)
- **룰 필터**: 본문/맺음말에 `협찬`·`제공받`·`체험단`·`서포터즈`·`원고료`·`광고 포함`·`소정의 고료`·`#협찬`·`방문 협찬` 등 사전 매칭
- **LLM 보강 판별**: 룰로 못 거른 위장 광고 → LLM이 광고/실방문 여부 판정 (망원동 소규모라 비용 미미)
- 두 방식 OR로 광고 판정 → 제외

### 3.1 신호
1. **언급 글 수** `n(s)` — 가게를 언급한 (광고 제외) 블로그 글 개수
2. **최신성 가중** `decay(p)` — 글 `p`의 작성일 기준 `0.5 ^ (age_days / HALFLIFE)`, `HALFLIFE = 180일`
3. **카테고리 키워드 매칭(점유율 분배)** — 글 본문 키워드 적중을 카테고리 비율로 분배.
   `strength(p) = 1 + ln(1 + 전체적중수)`, `share(p,c) = hits_c / 전체적중수` → 기여 = `strength·share`.
   (BAGEL 33·SAVORY 3 글이면 SAVORY엔 3/36만 귀속 → 약한 카테고리 과대평가 방지. 예: 샌드베이글집이 샌드위치 1위로 뜨던 버그 해결)
   ※ 키워드 사전 주의: bare `샌드`(→샌드베이글 오염)·bare `슈`(→브리오슈/크로크무슈 오염) 등 부분일치 충돌 토큰 금지
4. **감성/평점** `senti(p)` — 본문 감성: 부정 0.5 / 중립 1.0 / 긍정 1.5. **LLM 기반**(광고 판별과 한 번에 묶어 처리), 사전 기반은 폴백
5. **네이버 리뷰 수** `R(s)` — 가게 품질 prior

### 3.1.5 묶음글 분배 가중 (focus) — 빵지순례 글 과대귀속 차단
망원동 빵지순례 묶음글은 여러 가게를 한 글에서 다룬다. 그대로 두면 한 글의 카테고리 적중이
언급된 모든 가게에 통째로 중복 가산되어 점수가 부풀려진다. → **글 1건을 그 글이 언급한
가게들에 가게명 언급 비율로 분배**한다.
```
focus(p, s) = (글 p 내 가게 s 언급수) / (글 p 내 전체 스냅샷 가게명 언급수)
            # 전용 리뷰글 → 1.0, 5곳 묶음글 → 각 ~0.2, 본 가게 미언급 → 0(제외)
```

### 3.2 합성
```
RawCatScore(s,c) = Σ_{p ∈ posts(s)}  decay(p) · senti(p) · strength(p)·share(p,c) · focus(p,s)

Quality(s)       = 1 + γ · log10(1 + R(s))            # γ ≈ 0.3
ScoreQ(s,c)      = RawCatScore(s,c) · Quality(s)
```

### 3.3 콜드스타트 보정 (베이지안 수축)
글이 적은 가게가 우연히 1등 하는 것 방지. 카테고리 `c` 전체 평균 `C_c`, 사전강도 `m`(예: 그룹별 중앙값 글수):
```
n_c(s) = 카테고리 c 유효 글 수
FinalCatScore(s,c) = (n_c / (n_c + m)) · ScoreQ(s,c) + (m / (n_c + m)) · C_c
```

### 3.4 정규화 & 피드 랭킹
- 카테고리 내 **0~100 정규화**(백분위 또는 min-max)로 노출 점수 산출.
- 위치 제공 시 거리 블렌딩: `rank = FinalCatScore · 1/(1 + d/d0)` (`d0` ≈ 2km).
- 개인화(선택): `member.LikedMenuCategory`와 그룹 매핑해 선호 카테고리 가중.

> 가중치(`γ, m, HALFLIFE, d0`)는 설정값으로 빼서 PoC 결과 보고 튜닝.

## 4. 데이터 모델 (별도 테스트 DB `bbang_score`)

```
blog_crawl_run        크롤 1회 실행 기록
  id, started_at, finished_at, source_store_count, status, note

store_snapshot        운영 store read-only 스냅샷 (FK 아님, 참조 id만)
  store_id(PK), name, region1st, region2nd, region3rd, lat, lng, snapshot_at

store_blog_post       크롤된 원천 글
  id, store_id, run_id, post_url, post_date, title, snippet, body,
  matched(bool), is_ad(bool), ad_reason, sentiment(enum: POS/NEU/NEG),
  fetched_at

store_review_stat     플레이스 리뷰 수 스냅샷
  store_id, review_count, fetched_at, run_id

store_category_score  (핵심) 가게×카테고리 점수
  store_id, bread_category(enum), run_id,
  raw_score, quality, final_score, normalized_score(0~100),
  mention_count, recent_mention_count, computed_at
  UNIQUE(store_id, bread_category, run_id)
```

> 운영 store 테이블을 FK로 묶지 않는다(물리 격리). `store_snapshot.store_id`는 단순 참조값.

## 5. 결과 확인 방식 — HTML 리포트 (신규 API 없음)

**신규 API는 만들지 않는다.** 점수 산출 결과는 **HTML 리포트**로 출력해 눈으로 검증한다.

- 출력물: `docs/reports/mangwon_blog_score_{run_id}.html` (정적 파일, 브라우저로 바로 열기)
- 구성:
  - **카테고리별 랭킹 테이블** — 카테고리 탭/섹션마다 가게 상위 N (순위, 가게명, 정규화점수 0~100, 언급 글 수, 최근 글 수, 리뷰 수)
  - 행 클릭 시 **근거 글 펼침** — 매칭된 블로그 글 제목·날짜·감성·링크 (점수 신뢰도 디버깅용)
  - 상단 요약 — run 정보, 망원동 가게 수, 카테고리별 데이터 분포
- 생성 방식: 파이썬 스크립트가 `store_category_score` 조회 → 템플릿 렌더(예: Jinja2) → 단일 HTML 파일. 외부 의존 최소화(인라인 CSS).
- 거리 블렌딩·개인화는 점수 신뢰도 검증 후 판단 (지금은 순수 점수 랭킹만).

앱 피드 노출(API 연동)은 본 PoC 범위 밖.

## 6. 크롤 & 스코어링 파이프라인 (배치)

```
1. snapshot   운영DB read-only SELECT → store_snapshot 적재 (1회)
2. crawl      각 가게: 네이버 블로그 검색 API 호출 → store_blog_post 적재
              + 플레이스 리뷰 수 스크래핑 → store_review_stat
3. annotate   글별 카테고리 키워드 매칭 + 감성 태깅
4. score      §3 공식으로 store_category_score 계산·정규화
5. publish    run을 'active'로 마킹 → API가 최신 run 조회
```

- 신규 파이썬 스크립트 위치: `scripts/blog_score/` (기존 운영 크롤러와 디렉터리 분리).
- 멱등성: `run_id` 단위로 적재, 실패 시 재실행 안전. 일 25,000건 한도 → 가게 수에 맞춰 배치/슬립.
- 기존 자산 재사용: `naver_match.py`(정규화·매칭 게이트), 플레이스 스크래핑 로직.
