# 코스 추천 지역 커버리지와 동네 선택 Spec

작성일: 2026-10-12 · 상태: 구현 전 설계 · 관련 이슈: [742](https://github.com/SWEETT-GIRL/bbang-ggut_BE/issues/742) · 실행 순서: [Plan](course-area-coverage-742-plan.md)

> **설계 재검토:** 아래 내용은 ‘고정 원을 추가하고 코스를 비교하는 대안’이다. [구역 모델 비교와 경계 도입](course-area-model-comparison-742.md)을 선행 판단으로 읽는다. 현재 권고는 지역 소속을 정비하고 도시 전체에서 근거리 코스를 만드는 대안 D를 함께 검증하는 것이다. 아래 최대 6개 동네·공개 DTO 유지 가정을 D에 그대로 적용하지 않으며, 비교 전 시드 추가를 확정하지 않는다.

지역 소속 검증은 주소의 가변 계층을 전제로 한다. 시·구가 함께 있는 4단계 주소와 세종의 중간 단계 생략·별도 투영을 보존하며, `region_3rd`가 동이 아니라는 이유만으로 오류로 분류하지 않는다. 공식 코드 계층과 앱의 세 필드는 별도 계약으로 다룬다.

**도시 안에서 비교하는 동네를 늘리고, 각 동네에서 실제로 만들 수 있는 코스를 비교해 추천 기회를 넓힌다.** 현재 스키마와 API를 확장해 구현할 수 있다. 가게 선정·동선은 서버가 결정하고, 운영 중인 Gemini 이유 문장 API는 최종 선택된 추천에 그대로 적용한다. 추천 점수의 개선은 검증할 가설이며 사용자 만족도 향상을 보장하지 않는다.

이 설계는 #742의 지역 후보와 동네 선택에 한정한다. 2026-09-21의 `course-recommendation-v2-spec.md`에 제안된 사용자 신호 재설계·새 특성 저장소·LLM 정책 변경을 선행 조건으로 삼지 않는다. #819와 #801은 보류된 별도 작업이다. 이 문서의 새로운 정책값은 초기 구현안이며 실험 결과에 따라 버전을 올려 변경한다.

## 문제와 측정 기준

2026-10-12 14:53 KST 운영 읽기 전용 집계는 활성 동네 59개, 도장 칸 48개다. 반경은 1,200m, 새로 추천하는 가게 사이 구간 상한은 1,500m다. [전체 결과](../reports/recommendation-coverage-20261012.json)와 [재현 SQL](../reports/recommendation-coverage-20261012.sql)을 기준선으로 보존한다.

|---|---:|---:|---:|
| 수원 | 1,046 | 178 | 17.0% |
| 성남 | 718 | 105 | 14.6% |
| 고양 | 853 | 156 | 18.3% |
| 용인 | 614 | 74 | 12.1% |
| 창원 | 698 | 85 | 12.2% |

분모는 해당 지역의 ACTIVE 가게 중 프로필이 있고 `bakery_score >= 0.5`인 가게다. 분자는 같은 도장 칸의 모든 동네 범위 합집합에 들어오는 고유 가게다. 서울 밖 비교 가능한 41칸의 중앙값은 29.4%다. 인천 중구는 현재 주소 이름과 맞지 않아 분모에서 제외했다. 서울 동 단위와 시군구 단위 비율을 섞어 전국 평균을 만들지 않는다.

후보 4곳을 채우는 것만으로 성공을 판단하지 않는다. 현재 59개 동네 모두 기본 후보가 4곳 이상이지만, 원 밖의 더 적합한 가게는 비교 기회가 없다. 반대로 커버율을 높였다는 이유만으로 새 동네를 채택하지 않는다. 추가되는 가게·취향별 추천 변화·동선·지연을 함께 평가한다.

ACTIVE 가게 55,473곳 중 6,249곳은 `store_profile`이 없다. 프로필 계산 시각은 2026-09-25다. 프로필 없는 가게 전부를 빵집으로 간주하지 않으며, 공간 확장과 데이터 적재 개선의 효과를 별도로 측정한다. 최근 30일 저장된 AREA 추천 36건은 수요 판단에 부족하다. 빈 소진 응답은 추천 행이 생성되지 않아 저장 행만으로 소진율을 계산할 수 없다.

## 구현 가능성

검토 기준은 `main@7b7c882d`의 추천 패키지와 현재 프론트 계약이다. 해당 백엔드 패키지는 검토한 로컬 HEAD와 동일하다.

| 필요한 기능 | 현재 기반 | 필요한 변경 |
|---|---|---|
| 도시 아래 여러 동네 | `CourseArea.passportSpot`과 동네별 중심·반경 | 추가 동네 시드와 활성화 그룹 |
| 회원별 동네 선택 | `resolveNeighborhood`, 원별 조회·저장·취향 통계 | 가게 수 대신 생성 가능한 코스 비교 |
| 후보 점수 | `CandidateStoreRow.score`, `tasteFit`, LABEL/AXIS 폴백 | 요청 전체에서 고정한 비교 기준 |
| 동선 구성 | `chainWithinHop` | 저장 없는 코스 초안 생성으로 추출 |
| 재사용·다시 받기 | 추천 ID, 세션, `previousRecommendationId`, `exactArea` | 도장 칸 단위 재사용·중복 제외와 정책 버전 |
| Gemini 이유 | 별도 reasons API, 룰 기본 문장 | 최종 선택 한 건에만 기존 경로 연결 |

동네 시드만 추가하는 단계는 현재 구조로 가능하다. 완성 코스를 비교하는 단계는 서비스 분리와 작은 내부 스키마 확장이 필요하다. 외부 지도 API, 벡터 DB, 새 LLM, 실시간 군집화는 필요하지 않다. 여러 동네를 읽는 비용과 개인화 이득은 아직 실측하지 않았으므로 운영 투입 전 통과 조건으로 둔다.

## 사용자 동작과 범위

사용자는 기존처럼 수원시 등의 지역 칩을 선택한다. 서버가 그 도시의 허용된 동네들을 검토하고 한 동네의 코스를 반환한다. 응답의 `area.areaId`는 실제 선택된 동네이며, 제목도 기존 지역명 기반 규칙을 따른다. 앱에 동네 선택 단계를 추가하지 않는다.

- 첫 적용 후보는 수원·성남·고양이다. 광교·서현·주엽 등의 이름과 좌표는 과거 제안일 뿐이며 이번 운영 데이터로 확정한다.
- 한 코스는 한 동네 범위에서 구성한다. 구간 상한은 실제 도보 경로가 아닌 기존 좌표 거리 기준이다.
- 요청 가게 수는 기존 1~6곳, 기본 4곳을 유지한다.
- 같은 일차의 기존 가게가 특정 동네를 가리키면 그 맥락을 우선한다. 이미 담긴 가게에서 새 코스 첫 가게까지의 실제 보행 경로 최적화는 포함하지 않는다.
- 앵커 추천의 1→2→3km 동작, 취향 프로필 산식, Gemini 프롬프트는 변경하지 않는다.
- 현재 AREA 후보 SQL에는 여행 날짜에 따른 영업시간 필터가 없다. 이번 단계에서 추가하거나 이미 있는 제약으로 가정하지 않는다.

## 동네 후보를 추가하는 방법

중심점 계산은 운영 요청 경로 밖의 오프라인 작업으로 수행한다. 읽기 전용 집계나 승인된 랩 스냅샷으로 후보를 만들고, 검수한 좌표를 Flyway 시드로 넣는다.

1. 도시 식별은 검증된 `region_1st`와 `region_2nd`로 고정한다. 옛 행정구역 이름을 임의 별칭으로 치환하지 않는다. 인천 중구와 서울 성수동의 어휘 불일치는 첫 시범 범위에서 제외한다.
2. 도시 안 적격 가게를 모으고, 기존 동네 범위의 합집합에 없는 가게를 구한다.
3. 원 밖 적격 가게의 좌표를 새 중심 후보로 삼아 반경 1,200m의 추가 고유 가게 수를 센다. 가장 많은 후보를 선택하고 합집합을 갱신한 뒤 반복한다. 동률은 가게 ID로 고정한다.
4. 도시별 기존 중심을 포함해 최대 6개 동네를 초기 비교 상한으로 둔다. 추가 중심을 하나씩 늘렸을 때의 증가량 전체를 남겨 한계 이득을 확인한다. 6개는 검증할 비용 상한이지 최적 개수나 서비스 약속이 아니다.
5. 단순 밀집도는 특이 취향의 작은 가게 집단을 놓칠 수 있다. LABEL 표현이 있는 가게의 특성 구간별로 같은 과정을 보조 실행해 추가 중심 후보를 얻고, 밀집도 후보와 합쳐 오프라인 비교한다. 모든 중심에서 셀 전체의 추가 커버 수와 라벨별 추가 커버 수를 함께 기록한다.
6. 기존 원과 중복만 생기는 후보는 제외한다. 신규 고유 가게가 있어도 실제 코스를 거의 만들지 못하면 채택하지 않는다. 가게 위치 기반 중심은 연속 공간 전체의 최적 원을 보장하지 않는다.
7. 좌표·동네 이름·직선 동선·강/고속도로 등 접근성 단절을 검수한다. 1,500m 직선 상한이 도보 가능성을 보장하지 않으므로 물리적으로 분리된 집단을 하나의 새 동네로 묶지 않는다.

검수 산출물에는 도시, 동네명, 중심 좌표, 기존/추가 고유 가게 수, 중복률, 프로필·라벨 보유율, 계산 시각, 데이터 기준, 후보 생성 규칙 버전을 남긴다. 이름에 특정 행정동을 써야 한다고 고정하지 않으며 앱에서 이해할 수 있는 동네 이름을 사용한다.

대표 행의 ID·이름·`passport_spot`·우선순위를 유지한다. 추가 행의 `display_order`는 대표 행보다 뒤로 둔다. 운영 가게 프로필은 dataops 소유로 유지하며 BE가 임의로 채우지 않는다.

## 코스 초안과 공통 점수

`buildAreaRecommendation`을 동네마다 호출하지 않는다. 이 메서드는 추천 저장·이유 문장 생성·계측을 수행하기 때문이다. 다음 경계를 분리한다.

```text
요청 검증과 기존 결과 재사용
  → 허용 동네와 제외 가게 확정
  → 요청 공통 점수 설정 고정
  → 동네별 후보 조회
  → 저장 없는 코스 초안 생성
  → 동네와 코스 한 개 선택
  → 기존 룰 문장 생성과 추천 한 건 저장
  → 앱의 기존 이유 API 요청으로 Gemini 문장 생성
```

초안은 `areaId`, 정렬된 가게, 요청/완성 가게 수, 새 코스 구간 거리, 취향 폴백 여부, 비교 점수, 취향 점수 진단값을 가진다. 탈락 초안은 `recommendation`, 피드백, 사용자 노출 지표에 기록하지 않는다. 성능·선택 진단은 별도 내부 지표로 남긴다.

비교 기준은 다음처럼 고정한다.

- 요청 시작에 유효한 LABEL/AXIS/NONE 모드, 중심화 상수, 사용자 프로필 버전, 가중치와 신호 조회 기준 시각을 한 번 결정한다. 동네별로 중심화 상수를 다시 읽어 다른 기준을 적용하지 않는다.
- 동네 안 후보 정렬과 `chainWithinHop`은 기존 규칙을 재사용한다. 처음부터 경로 최적화 알고리즘까지 바꾸지 않는다.
- 기존 취향 폴백은 취향 후보가 적으면 `TasteQuery.empty()`로 다시 조회한다. 이때의 점수는 개인화 점수와 직접 비교할 수 없다.
- 각 초안에 실제로 들어간 가게를 **원래 회원과 고정한 설정으로 평가한 점수**를 `comparisonScore`로 보존한다. 인기 폴백으로 뽑은 가게도 같은 기준으로 평가한다. `meanComparisonScore = 합계 / 실제 가게 수`로 계산하되 빈 초안은 점수를 갖지 않는다.
- 초안의 평균 `tasteFit`, 종류 일치, 라벨 결측률도 진단값으로 남긴다. 기존 복합 점수의 상승을 취향 적합도나 만족도 상승과 동일시하지 않는다.
- 개인화 신호가 없는 회원은 현재의 중립 평가 기준을 공통 사용한다. 없는 취향을 만들어 넣지 않는다.

후보 쿼리는 기존 점수식을 공통 SQL 조각으로 재사용한다. 개인화/폴백 정렬 두 목록이 필요하면 전체 후보의 점수를 한 번 계산한 뒤 각각 상위 15개를 반환하는 방식을 우선 검토한다. 최대 6개 동네 × 두 목록 × 15개 = 180행이 초기 응답 상한이다. 이것이 DB 스캔·정렬 비용까지 180행으로 제한한다는 뜻은 아니다. 필요한 경우 두 번의 일괄 조회로 나누되 동네별 N+1 호출을 기본 구현으로 삼지 않는다.

## 동네를 선택하는 규칙

요청이 명시한 장소와 이미 잡힌 일정을 먼저 존중한다. 이후 코스 비교의 순서는 고정해 결과를 재현할 수 있게 한다.

| 단계 | 처리 |
|---|---|
| 명시적 동네 | `exactArea=true` 또는 대표 행이 아닌 동네 ID는 그 동네만 사용 |
| 다시 받기 | 이전 추천에 저장된 동네·일차만 사용. 다른 동네로 자동 이동하지 않음 |
| 같은 일차의 가게 | 해당 일차 가게를 가장 많이 포함하는 동네 집합으로 제한. 동률만 비교 |
| 일차가 완전히 비어 있음 | 기존처럼 코스 전체 가게로 동네 집합을 제한할 수 있음 |
| 그 밖의 요청 | 활성·허용된 모든 후보 동네를 비교 |

일차에 가게는 있으나 어느 원에도 들어오지 않으면 다른 날짜의 가게로 그 일차의 위치를 덮지 않는다. 이는 현재 동작을 유지한다. 위치 맥락으로 제한된 집합의 후보가 부족하다고 멀리 있는 동네로 몰래 넘어가지 않고, 부분 결과나 기존 다음 동네/앵커 안내를 사용한다.

제한된 집합 안에서는 다음 키를 순서대로 비교한다. 뒤 키는 앞 키가 동률일 때만 사용한다.

1. 요청한 가게 수를 더 많이 채운 초안.
2. 원 안의 최근 조회 가게 수가 많은 동네.
3. 원 안의 저장 가게 수가 많은 동네.
4. `meanComparisonScore`가 높은 초안. 비교에는 반올림하지 않은 동일 정밀도 점수를 쓴다.
5. 새 코스의 총 구간 거리가 짧은 초안.
6. 기존 `display_order`, 동네 이름, 동네 ID 순.

조회·저장은 기존의 명시적 관심 우선순위를 보존한다. 해당 신호가 동률이거나 없는 경우에 코스 적합도 비교가 동네를 바꾼다. 도시 전체 조회·저장 수인 `region*Count`는 칩 순서에만 쓰고 동네의 신호로 사용하지 않는다. 이 우선순위 때문에 더 높은 평균 점수의 동네가 선택되지 않는 경우도 진단 결과에 남긴다.

도장 칸의 가게·취향 후보·원 안 조회/저장 수는 허용된 동네들의 합집합에서 가게 ID를 중복 제거해 집계한다. 현재처럼 동네별 수를 단순 합산하면 겹치는 원을 추가하는 것만으로 칩 숫자와 순위가 부풀 수 있다. 도시 전체 `region*Count`와의 기존 결합 규칙은 유지하며, 동네 선택에 쓰는 각 원의 통계는 별도로 유지한다. 이 집계 보정은 B와 C에 동일하게 적용하고, A 대비 칩 순위 변화는 코스 선택 효과와 구분해 기록한다.

0곳 초안은 선택하지 않는다. 전부 비었으면 기존 빈 응답 계약을 지킨다. 현재 `chainWithinHop`은 첫 가게부터 가까운 순서로 잇는 휴리스틱이므로, 비교 결과를 도시 전체의 최적 코스라고 부르지 않는다.

## 중복과 재사용 계약

동네 수가 늘어도 사용자가 보던 결과와 버튼의 의미는 유지되어야 한다.

| 요청 | 새 정책의 처리 |
|---|---|
| 같은 시트 재열기 | 동네를 다시 비교하기 전에 같은 도장 칸의 최신 유효 추천을 찾아 재사용 |
| 같은 시트에서 일부 가게 담기 | 기존 선택 동네에 고정해 빈 자리를 다시 구성. 유효한 기존 묶음 가게는 다시 후보로 허용 |
| 다른 세션에서 열기 | 도장 칸 전체의 이미 추천된 가게를 제외하고 동네를 새로 비교 |
| 다시 받기 | 동네 고정. 같은 회원·코스·도장 칸·일차의 과거 추천 가게를 제외 |
| 다음 동네로 이동 | 구체 동네를 `exactArea=true`로 요청. 같은 도장 칸의 과거 가게는 계속 제외 |
| 소진 후 새 세션 | 도장 칸 전체에서 미노출 후보가 없음을 확인한 경우에만 과거 추천 제외를 풀고 다시 계산. 코스에 담긴 가게·기록 제외 정책은 유지 |

제외 이력은 프로필·선택 정책·카탈로그 버전을 가리지 않는다. 개인별·코스별·일차별 경계는 유지하며, 공동 편집자의 추천 이력을 섞지 않는다. 과거 버전의 AREA 행도 실제 `course_area_id`를 같은 도장 칸으로 묶어 중복 제외에 사용한다. 앵커 모드의 이력 정책은 이번에 합치지 않는다.

`nextArea`는 시범 도장 칸 안에서 이 회원·일차의 제외 집합을 적용하고 실제 남은 후보가 있는 다른 동네만 제안한다. 이전에 추천한 동네라고 일차와 무관하게 영구 제외하는 현재 조회를 그대로 쓰면 안 된다. 새 정책으로 평가한 동일 비교 기준을 사용하며, 같은 도장 칸에 없으면 기존의 같은 시·도 다른 칸/앵커 안내로 넘어간다. 다른 도장 칸의 순서 정책은 바꾸지 않되 빈 후보는 건너뛴다.

`lastBatch`는 선택한 동네에 대한 기존 의미를 유지한다. 도시 전체에 다른 동네가 남아 있어도 false로 바꾸지 않는다. 현재 앱은 부분 결과의 `lastBatch`에서 다시 받기를 숨길 수 있고, 다음 동네 안내는 빈 응답에서 처리한다. 이번 구현은 도시 전체를 순회하는 새 UX를 약속하지 않는다. 그 기능을 원하면 별도 FE 계약으로 다룬다.

## 내부 스키마와 활성화

공개 DTO는 유지한다. 정책 버전을 Gemini의 `provider`, `model`, `prompt_version`에 끼워 넣지 않는다. `RecommendationResult`의 미지 필드도 이유 API가 읽고 다시 쓰면서 유실될 수 있으므로 메타데이터 저장 위치로 쓰지 않는다.

초기 내부 스키마 안은 다음과 같다.

| 위치 | 새 필드 | 용도 |
|---|---|---|
| `course_area` | `expansion_group` nullable 문자열 | 신규 동네 묶음의 노출 제어. 기존 행은 null |
| `recommendation` | `selection_scope_area_id` nullable FK | 선택한 동네와 별도로 도장 칸 대표 행 ID 보존 |
| `recommendation` | `selection_policy_version` nullable 문자열 | 비교·제외 정책과 관련 설정의 버전 |
| `recommendation` | `area_catalog_version` nullable 문자열 | 해당 요청의 허용 동네 ID·좌표·반경·지역 조건·정렬 순서 해시 |

기존 행의 null은 LEGACY로 읽고 대규모 백필을 선행하지 않는다. 새 정책 행에는 세 값을 함께 저장한다. 대표 행의 정체성은 유지한다. 카탈로그 버전은 가게 프로필 데이터 버전을 대신하지 않는다. 프로필 적재 기준·설정 스냅샷은 오프라인 비교 결과에 별도로 기록한다.

재사용 키는 회원·코스·대표 행·일차·프로필 버전·선택 정책 버전·카탈로그 버전을 포함한다. 실제 동네 고정 요청은 그 동네까지 필터한다. 요청 가게 수·최신 자격·코스 변경에 따른 유효성 검사는 기존처럼 수행한다. 정책 또는 카탈로그가 바뀌면 같은 세션에서도 이전 정책 결과를 새 정책 결과로 오인해 재사용하지 않는다.

명시적 재추천은 이전 추천 ID의 동네를 유지하면서 현재 유효 정책으로 새 결과를 만들 수 있다. 구버전 메타가 없거나 새 정책을 끈 상태에서도 기존 ID를 이유 조회·피드백·담기에 사용할 수 있어야 한다.

새 동네는 처음에 `is_active=false`로 시드한다. 모든 서버가 공통 `NeighborhoodCatalog`를 사용한 뒤 활성화한다. 이 접근 계층은 컨텍스트 칩, 첫 선택, 비교 후보, 다음 동네에 동일한 expansion group 허용 규칙을 적용한다. 비활성 실험 동네가 칩 개수나 점수에 섞이지 않게 한다.

독립 설정 두 개를 둔다: 동네 확장 그룹 허용과 선택 방식 LEGACY/COMPARE. 확장만 켜고 기존 선택을 쓰는 B 실험이 가능해야 한다. 설정으로 확장을 끄면 새 요청의 카탈로그에서만 제외하고, 이미 저장된 결과의 이유·피드백·담기 및 해당 동네의 명시적 재추천은 유효한 활성 행을 계속 읽을 수 있게 한다. 행을 삭제하거나 좌표를 즉시 덮어써 롤백하지 않는다. 구버전 바이너리로 돌아가야 한다면 먼저 확장 행을 안전하게 비활성화하는 별도 절차를 검증한다.

## 지연과 운영 제약

시범 도장 칸별 비교 상한은 6개 동네다. 초과하면 일부를 임의로 자르지 않고 해당 칸의 COMPARE 활성화를 막아 LEGACY로 처리하며 계측한다. 신규 카탈로그는 이 제한을 넘기지 않게 검수한다.

신호 조회와 이력 조회는 요청당 공유하고, 후보 랭킹 조회는 일괄 쿼리 최대 2회로 제한한다. 이름·사진 등 비싼 표시 재료는 가능한 한 최종 선택 뒤에 읽는다. `poolFor`를 무제한 반복하거나 동네마다 스레드를 띄우지 않는다. SQL 타임아웃이 트랜잭션을 실패 상태로 만든 뒤 같은 트랜잭션에서 LEGACY를 재시도하는 구현도 금지한다. 초기 실패 처리는 기존 오류 경로를 유지하고 설정 롤백으로 대응한다.

단위 테스트의 순수 비교기는 DB·LLM을 부르지 않는다. 운영 shadow 실행은 기본으로 두지 않고 랩 비교부터 수행한다. API p95 증가 허용치는 **동일 환경 기준선 대비 200ms 이내를 초기 검증 목표**로 두되, 검증 전 충족한다고 주장하지 않는다. 기존 서비스 SLO가 더 엄격하면 그 기준을 따른다.

## 검증과 완료 조건

같은 데이터·회원 입력·세션·코스·제외 집합으로 다음 세 가지를 비교한다.

| 비교군 | 동네 목록 | 선택 방식 | 확인할 효과 |
|---|---|---|---|
| A | 현재 | 현재 | 기준선 |
| B | 확장 | 현재 | 공간 후보 추가 효과 |
| C | B와 동일 | 코스 비교 | 동네 선택 변경 효과 |

오프라인 비교는 현재 카탈로그 시뮬레이션으로 명시한다. 과거 로그에 현재 프로필을 적용한 결과를 과거 성과 재현이라고 부르지 않는다. 현재 설문의 유효 조합, 종류·태그 선호, 무신호, LABEL 결측, 기존 가게·조회·저장·이력 조건을 고정 시나리오로 만든다. 운영 추천 행이나 피드백에 가상 결과를 저장하지 않는다.

- 도시별 추가 고유 후보 수와 특성별 커버리지를 제시한다. 분모 0·주소 불일치·프로필 결손은 제외 사유와 수를 남긴다.
- 요청 가게 수 충족률, 실제 선택 가게의 공통 점수·취향 지표, 종류 일치, 고유 가게 노출, 동네 편중, 재추천 중복률, 거리, 쿼리 수·p50/p95를 A/B/C별로 낸다.
- 개인정보나 회원 ID를 메트릭 라벨에 넣지 않는다. 버전·모드·사유처럼 제한된 값만 라벨로 쓴다. 샘플별 비교 로그는 제한된 랩 결과로 관리한다.
- 0곳 응답, 부분 결과, 소진, 다음 동네 제안을 요청 단위로 계측한다. 저장된 추천 행 수만으로 소진율을 추정하지 않는다.
- 요청 1~6곳, 동네 간 중복, 같은 시트 재열기, 프로필/카탈로그 변경, 이전 정책 추천 ID, Gemini 이유 갱신 후 메타 보존, 공동 편집 권한을 검증한다.
- 장소 제한·완성 가게 수·조회·저장 신호가 같은 C 초안은 공통 비교 점수가 더 높은 허용 초안을 놓치지 않는다. 그러나 평균 맛 적합도·실제 만족도는 별도 지표로 평가한다.
- 선택 변경으로 충족률이 떨어지거나, 취향 개선 없이 지연·동선만 늘면 해당 도시의 C를 켜지 않는다. B만 유효하면 동네 확장만 먼저 반영할 수 있다.

운영 완료는 시범 도시의 카탈로그·비교 결과·호환성·성능·설정 롤백 검증을 갖추고 활성화한 때다. spec/plan 작성이나 기존 테스트 통과만으로 #742를 닫지 않는다. 전국 확대와 새 동네 자동 갱신 배치는 시범 결과 이후 별도로 결정한다.
