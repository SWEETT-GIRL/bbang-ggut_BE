# 코스 추천 지역 커버리지와 동네 선택 Plan

작성일: 2026-10-12 · 상태: 실행 전 · 요구사항: [Spec](course-area-coverage-742-spec.md) · 관련 이슈: [742](https://github.com/SWEETT-GIRL/bbang-ggut_BE/issues/742)

> **선행 단계 추가:** [구역 모델 비교와 경계 도입](course-area-model-comparison-742.md)에 따라 지역 소속 정합성, 공식 경계 샘플, 도시 전체 대안 D의 랩 실험을 먼저 수행한다. 아래 P0~P6은 고정 원 확장안을 선택할 경우의 계획으로 보존한다. D를 채택하면 동적 코스 scope·다음 동네 API 계약과 비용 상한을 확정한 뒤 구현 단계를 갱신한다. 시드 확장이나 FE 변경 불필요를 현재 확정 사항으로 해석하지 않는다.

지역 검증의 첫 작업은 유입 경로별 주소 투영 규칙 확인이다. 일반 3단계·시와 구를 포함한 4단계·세종처럼 중간 단계가 없는 주소·읍면리·도로명 사례를 구분한다. BE parser와 dataops resolver의 차이를 확인하고, 기존 값이 동 이름이 아니라는 이유로 바로 보정 대상으로 삼지 않는다.

**수원·성남·고양에서 동네 확장과 코스 비교의 효과를 분리 검증하고, 확인된 범위부터 적용한다.** 기존 Gemini 이유 API와 앱 요청·응답 형식을 유지한다. 구현·시드 활성화·운영 배포는 이 문서 작성과 별도 단계다.

## 구현 가능성 판정

현재 `course_area`는 한 도장 칸에 여러 동네를 담을 수 있고, 추천 응답도 실제 선택된 동네 ID를 반환한다. 코스 후보 행에는 점수와 좌표가 이미 있으며, 프론트는 그 ID로 다시 받기와 다음 동네 요청을 처리한다. 따라서 핵심 구조를 교체할 필요는 없다.

추가 구현의 중심은 저장 없는 코스 초안, 요청 전체에서 같은 비교 점수, 도장 칸 단위 이력·재사용, 버전과 활성화 제어다. 성능과 실제 추천 개선 폭은 오프라인 실험 전에는 확정할 수 없다. 2026-10-12의 기존 main 추천·개인화 테스트 338건 통과는 기존 코드의 기준선이며, 새 설계의 검증 결과가 아니다.

## 의존 순서와 산출물

```text
P0 기준선과 후보 중심 산출
  → P1 저장 없는 코스 구성 분리
  → P2 카탈로그와 정책 버전 저장
  → P3 일괄 후보 조회와 코스 비교
  → P4 재사용과 중복 제외 및 다음 동네
  → P5 A/B/C 평가와 비활성 시드 확정
  → P6 staging 검증과 시범 활성화
```

단계별 커밋 또는 PR로 나눌 수 있지만 P3만 켜고 P4를 나중에 붙이지 않는다. 비교 기능은 재사용·중복 제외·버전 경계까지 준비된 뒤 활성화한다. 기존 로컬 `fix/734-day-count-follows-dates`의 수정과 미추적 9월 설계 문서는 이번 구현에 섞지 않는다. 구현 시작 시 최신 원격 기준의 적절한 checkout을 선택한다.

| 단계 | 작업 영역 | 검토 가능한 결과 | 활성화 조건 |
|---|---|---|---|
| P0 | SQL·랩 분석 | 도시별 후보 중심과 기준선 | 데이터 적합성 확인 |
| P1 | BE 서비스 | 기존 출력이 같은 순수 코스 구성기 | 기존 회귀 테스트 통과 |
| P2 | BE 스키마·카탈로그 | nullable 버전 필드, 그룹별 노출 제어 | 구행·구앱·이유 API 호환 |
| P3 | BE SQL·선택기 | 일괄 후보 조회와 결정론적 비교 | 점수 비교·조회량 검증 |
| P4 | BE 이력·재사용 | 도장 칸 중복 제외와 세션 계약 | 상태 전이 회귀 검증 |
| P5 | 랩·시드 | A/B/C 평가표, 검수한 비활성 동네 | 효과·동선·비용 통과 |
| P6 | staging·운영 | 기존 앱 연동, 계측, 설정 롤백 | 시범 검증 후 제한 활성화 |

## P0 기준선과 추가 동네 후보

시작 입력은 [측정 SQL](../reports/recommendation-coverage-20261012.sql)과 [전체 집계](../reports/recommendation-coverage-20261012.json)다. 실행일에 새 스냅샷을 만들고 이전 결과를 덮어쓰지 않는다.

1. 세 도시의 좌표·주소·프로필·라벨·현재 상권을 랩 분석에 필요한 범위로 준비한다. 사용자 원문·비밀키·운영 전체 덤프를 산출물에 포함하지 않는다.
2. 도시별 기존 원의 합집합과 원 밖 적격 가게를 재계산한다. 가게를 여러 원에 중복 집계하지 않는다.
3. 원 밖 가게 좌표를 중심으로 1,200m 내 추가 커버 수를 계산한다. 한 원씩 추가했을 때의 증가량과 중복률을 출력한다.
4. 밀집도 후보와 라벨 특성별 후보를 함께 비교한다. 기본안은 기존 동네 포함 최대 6개다. 증가량이 없으면 더 추가하지 않으며, 상한까지 채우는 것을 목표로 삼지 않는다.
5. 각 중심의 후보 수·라벨 보유율·프로필 없는 가게 수와 예시 동선을 기록한다. 좌표나 이름을 과거 #742 표에서 복사해 확정하지 않는다.
6. 현재 목록과 같은 조건에서 A를 재생한다. 기존 인기·취향 점수·후보 15개·경로 규칙을 기록한다.

제안 산출물은 `scripts/lab/course-area-coverage-candidates.sql`, `docs/reports/course-area-coverage-candidates-<date>.json`이다. 실제 구현 파일명은 기존 구조에 맞춰 확정한다. 성수·인천의 주소 어휘 보정은 이 실험에 임의로 포함하지 않는다.

통과 조건: 기존 집계와 차이가 있으면 데이터 시점·자격·반경·주소 조건으로 설명된다. 추가 중심의 행정 소속과 실제 동네 이름을 확인할 수 있다. 시범 지역의 새 후보가 기존 프로필·라벨을 통해 평가 가능한지 드러난다.

## P1 코스 초안 구성 분리

주요 변경 대상은 `CourseRecommendationCommandService`의 `poolFor`, `assemble`, `chainWithinHop`이다.

- `AreaCourseDraft`를 생성하는 순수 구성기를 추출한다. 입력은 고정된 후보 행·상권 제약·요청 수, 출력은 순서·거리·완성 수·폴백·진단값이다.
- 저장, 피드백, 룰 문장 생성, `ReasonMetrics`, Gemini 호출은 구성기에서 제외한다.
- 선택된 초안 한 개를 기존 결과 DTO와 저장 엔티티로 바꾸는 경로를 둔다. 최종 `assemble`에서 후보 조회나 경로 구성을 반복하지 않는다.
- LEGACY 경로를 추출한 구성기에 연결하되 결과 순서·거리·빈 응답·`lastBatch`가 변하지 않게 한다.

검증은 빈 후보, 요청 1~6곳, 구간 상한으로 조기 종료, 같은 거리의 결정론적 순서, 최종 선택 한 건만 저장·계측되는 경우에 집중한다. 코드 모양을 그대로 검사하는 테스트보다 기존 출력과 경계 사례를 고정한다.

## P2 카탈로그와 버전 경계

주요 변경 대상은 `CourseArea`, `CourseAreaRepository`, `Recommendation`, `RecommendationRepository`, 설정, Flyway다.

1. `course_area.expansion_group`과 `recommendation.selection_scope_area_id`, `selection_policy_version`, `area_catalog_version`을 nullable로 추가한다. 정확한 길이·인덱스는 조회 설계와 함께 확정하되 hash는 잘리지 않게 한다.
2. 새 추천의 세 메타 값은 함께 채우고 구행 null은 LEGACY로 읽는다. 앵커에는 적용하지 않는다. 메타를 `result` JSON이나 LLM `prompt_version`에 넣지 않는다.
3. 회원·코스·대표 행·일차·프로필·정책·카탈로그를 필터하는 재사용 조회를 만든다. 실제 실행계획과 대상 행 수를 보고 인덱스를 추가한다.
4. `NeighborhoodCatalog`가 컨텍스트, 최초 선택, 비교, 다음 동네의 확장 그룹 허용을 일관되게 적용하게 한다. 대표 행 ID와 그룹 정체성은 유지한다.
5. `enabledExpansionGroups`와 `selectionMode=LEGACY|COMPARE`를 독립 설정으로 둔다. 기본은 확장 없음·LEGACY다. 시범 그룹과 최대 비교 수를 검증한다.
6. 이미 저장된 추천을 읽는 경로는 신규 선택용 카탈로그 필터와 구분한다. 그룹 비활성화 뒤에도 활성 동네를 참조한 기존 이유 조회·담기·피드백·명시적 재추천이 깨지지 않게 한다.
7. `RecommendationContextQueryService`의 도장 칸 통계는 허용 동네의 고유 가게 합집합으로 집계한다. 겹치는 원에서 같은 가게를 두 번 세지 않는지, 기존 도시 전체 신호 결합 규칙이 유지되는지 검증한다. B와 C에 동일하게 적용하고 칩 순위 변화를 별도 기록한다.

실제 PostgreSQL에서 마이그레이션·FK·Hibernate 매핑·구행·신행을 검증한다. H2 단위 테스트만으로 jsonb·PostGIS·인덱스 검증을 대신하지 않는다. 이유 API가 문장을 갱신한 뒤 세 메타 컬럼이 보존되는 회귀 테스트를 포함한다.

## P3 공통 점수와 일괄 코스 비교

주요 변경 대상은 `RecommendationCandidateJdbcRepository`, `LabelCenterParams`, `CandidateStoreRow`, `RecommendationProperties`와 새 순수 비교기다.

- `ScoringContext`에 요청의 유효 LABEL/AXIS/NONE 모드·중심화 상수·프로필·설정값을 고정한다. 신호 통계와 후보 조회가 같은 기준을 사용하게 한다.
- 여러 동네에 대해 기존 후보 점수식을 일괄 계산한다. 원별 통계와 도시 전체 신호 필드는 구분한다.
- 원래 회원 점수와 폴백 정렬 점수를 분리한다. 두 정렬 상위 목록을 한 번 또는 최대 두 번의 일괄 조회로 얻는다. `tasteCandidateCount`는 top 15 밖을 포함한 해당 동네의 실제 제외 적용 후 전체 후보 기준이어야 한다.
- 같은 가게가 여러 원에 들어가면 각 초안의 후보가 될 수 있지만, 행의 평가 기준은 동일해야 한다. 화면용 사진 조회는 가능하면 최종 선택 뒤로 옮긴다.
- `AreaCourseDraft`마다 실제 구성된 가게의 원래 회원 점수 평균을 계산한다. 폴백 점수를 개인화 점수와 직접 비교하지 않는다.
- Spec의 장소 제한과 완성 수→조회→저장→공통 점수→거리→안정 정렬 규칙을 순수 비교기로 구현한다.
- 기준선을 위한 기존 선택 동네도 비교 대상에 반드시 포함한다. 상한 초과 시 일부를 잘라 C라고 부르지 않고 LEGACY 사유를 남긴다.

필수 사례:

| 사례 | 기대 결과 |
|---|---|
| 관심 신호가 같고 많은 후보의 점수가 낮음 | 실제 완성 수가 같으면 평균 공통 점수가 높은 초안 선택 |
| 2곳의 점수는 높지만 다른 동네는 요청한 4곳 완성 | 장소 제한을 지키는 집합 안에서 4곳 우선 |
| 한 동네는 취향 폴백 | 폴백 정렬 점수가 아닌 원래 회원 기준으로 비교 |
| LABEL만 있고 AXIS가 없음 | 새 경로의 개인화 유무 판정이 축 존재에만 묶이지 않음 |
| 라벨 중심화 자료 없음 | 요청 전체가 일관된 AXIS/NONE 기준으로 평가 |
| 같은 일차에 담긴 가게가 있음 | 다른 날·다른 도시의 높은 점수가 장소 제약을 덮지 않음 |
| 점수·거리까지 동률 | 반복 실행에서 같은 동네와 순서 반환 |

## P4 이력과 재사용 상태 전이

주요 변경 대상은 `recommend`, `reuseOrRefresh`, `shownStoreIdsOf`, `retry`, `nextAreaOf`와 저장소 조회다.

1. 도장 칸 최초 요청은 동네 선택 전에 같은 범위의 최신 결과를 조회한다. 실제 동네 고정 요청은 해당 동네 결과만 찾는다.
2. 과거 AREA 행을 회원·코스·도장 칸·일차로 모아 고유 가게 ID를 구한다. 구버전/null 메타 행은 `course_area` 관계로 범위를 판정한다. 다른 회원의 협업 코스 이력을 섞지 않는다.
3. 같은 세션의 유효 결과는 재사용한다. 무효 결과의 빈 자리 구성은 선택된 동네에 고정하며, 그 묶음 가게만 이력 제외에서 뺀다. 코스에 담긴 가게나 자격을 잃은 가게는 다시 허용하지 않는다.
4. 다른 세션은 도장 칸 전체의 미노출 후보로 비교한다. 모든 동네의 미노출 후보가 없을 때만 새 세션의 순환을 허용한다. RETRY에서는 이 제외를 풀지 않는다.
5. RETRY는 이전 ID의 실제 동네와 일차를 지킨다. 한 요청에 RETRY 이벤트 한 건만 남기며 비교 초안 수만큼 남기지 않는다.
6. `nextArea`는 같은 이력 제외로 실제 남은 후보를 검사한다. 이미 추천한 동네 ID를 코스 전체에서 무조건 배제하는 현재 조회는 시범 경로에서 대체한다. 다른 일차의 사용 때문에 오늘 후보가 사라지지 않아야 한다.
7. 과거 버전 ID, 그룹 비활성화, 정책 전환 직전·직후, 일차 변경, 가게 삭제, 동시 추천 요청을 검증한다. 같은 입력의 결정론적 결과를 요구하되 DB에 정확히 한 행만 생기는 새 멱등성 보장은 이번 범위에 추가하지 않는다.

중요한 앱 계약은 그대로다. RETRY는 같은 동네이며, 다음 동네는 `exactArea=true`다. `lastBatch`의 뜻과 다음 동네 안내가 나타나는 시점도 바꾸지 않는다. 전체 도시를 자동으로 순회하는 버튼이 필요해지면 별도 FE 작업으로 분리한다.

## P5 효과 평가와 시드 확정

현재 추천 랩 테스트와 후보 SQL을 재사용하고 #662의 LLM 채점 러너를 기다리지 않는다. 새 평가 도구는 결정론적 집계와 고정 입력 비교만으로 실행한다.

동일 스냅샷에서 A 현재 동네/현재 선택, B 확장 동네/현재 선택, C 확장 동네/코스 비교를 실행한다. 현재 설문의 유효 취향 조합과 무신호·종류·태그·LABEL 결측·이미 담긴 가게·조회·저장·재추천 조건을 명시적인 시나리오로 고정한다.

산출물은 후보 중심 목록, 시나리오별 A/B/C 결과, 도시·취향별 요약, 설정·프로필 입력·데이터 기준의 fingerprint, 쿼리 계획과 지연 분포다. 커버율 상승만 기록하지 않고 다음을 나란히 둔다.

- 새로 추천 가능한 고유 가게와 실제 선택된 고유 가게.
- 요청 수 충족률, 공통 점수, `tasteFit`, 종류 일치, 취향 폴백률.
- 기존 원 밖 가게의 실제 선택 비율, 동네·가게 노출 편중, 중복률.
- 총 거리·최대 구간 거리, 조회 수·반환 행 수·전체 API p50/p95.
- 현재 저장소의 프로필 결손이 개선 효과를 제한하는 지역과 수.

같은 환경에서 웜·콜드 캐시와 정해진 동시 요청 수로 측정한다. A/B/C 실행 순서를 교차해 캐시 이득을 한쪽에만 주지 않는다. DB 집계와 API 지연에 Gemini 시간을 섞지 않는다. 초기 성능 목표는 A 대비 p95 증가 200ms 이내이며, 실제 서비스 SLO를 함께 만족해야 한다.

시드 채택 조건은 신규 후보가 존재하고 예시 동선이 타당하며, 고정 시나리오에서 충족률을 떨어뜨리지 않는 것이다. C는 비교 점수만이 아니라 취향 진단값·노출 편중·동선·지연을 함께 검토한다. 평균이 좋아도 특정 취향군이 일관되게 나빠지면 원인과 정책을 수정한 뒤 재평가한다. 근거가 없으면 중심 추가 또는 C 활성화를 보류한다.

동네 이름·좌표를 검수한 뒤 도시별 확장 그룹을 가진 비활성 시드 마이그레이션으로 고정한다. 데이터 보강이 필요하면 대상 가게와 누락 원인을 dataops 작업으로 분리한다. 재적재 뒤에는 A/B/C를 같은 새 스냅샷에서 다시 비교해 데이터 효과를 섞지 않는다.

## P6 배포와 기존 앱 검증

배포 순서는 스키마 → 기본 OFF인 호환 코드 → 비활성 동네 시드 → staging 활성화 → 시범 도시 활성화다. 모든 운영 인스턴스가 카탈로그 필터를 이해하기 전에 신규 행을 활성화하지 않는다.

staging에서 실제 앱으로 다음 흐름을 확인한다.

1. 도시 칩 선택 → 실제 동네명과 추천 가게 확인 → Gemini 이유 도착.
2. 시트 닫고 다시 열기 → 같은 묶음 유지.
3. 일부 담고 재열기 → 다른 동네로 튀지 않고 유효한 결과 유지/보충.
4. 다시 받기 → 같은 동네, 기존 가게 중복 없음.
5. 후보 소진 → 빈 응답·다음 동네 → `exactArea`로 이동.
6. 다른 일차·공동 편집·프로필 변경 → 권한과 범위 유지.
7. 선택 방식 또는 확장 그룹 OFF → 새 요청 롤백, 기존 추천 ID 기능 유지.

측정용 메트릭은 비교 동네 수, 선택 사유, 빈/부분 결과, 소진, 재사용, 실행 시간이다. 도시·그룹별 결과는 고정된 낮은 수의 값으로 분리하고 회원 ID·가게 ID를 메트릭 라벨로 쓰지 않는다. 사용자 성과는 실제 노출이 확인된 추천의 담기·재추천·부정 피드백으로 본다. 표본이 적으면 효과를 확정했다고 보고하지 않는다.

설정 롤백은 COMPARE를 LEGACY로 전환하고 필요하면 확장 그룹을 신규 선택 목록에서 제외한다. API 실패율·SLO 위반·중복·장소 이동·부분 결과 회귀가 있으면 해당 그룹을 끈다. `course_area` 행 삭제나 기존 추천 결과 삭제로 되돌리지 않는다. 이전 바이너리로 돌아가는 절차는 그룹 OFF만으로 충분하지 않으므로 시드 비활성화와 기존 ID 처리까지 staging에서 별도 검증한다.
