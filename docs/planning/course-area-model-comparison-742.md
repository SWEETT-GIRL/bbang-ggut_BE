# 추천 구역 모델 비교와 경계 데이터 도입

작성일: 2026-10-12 · 상태: 경계 적재·로컬 코스 비교 완료, 서비스 연결 전 · [이슈 #742](https://github.com/SWEETT-GIRL/bbang-ggut_BE/issues/742)

현재 브랜치의 통합 설계는 [Spec/Plan](../../.claude/planning/feat-742-polygon-course-lab.md), 최신 실측은 [코스 비교 결과](../reports/polygon-course-comparison-20261012.md)에 있다. 아래의 미실험 설명은 최초 설계 시점의 기록이며 최신 실험 범위와 결과는 이 두 문서를 우선한다.

**공식 경계는 지금부터 도입할 수 있다. 경계 도형 없이도 기존 가게의 지역 소속과 좌표로 도시 전체 후보를 비교할 수 있다.** 다만 현재 지역 문자열을 정확한 소속으로 가정해서는 안 된다. 권고 방향은 지역 소속을 공식 코드로 정비하고, 코스의 이동 범위는 별도로 계산하는 것이다. 경계 도형은 소속 판정·검증에 사용하며 코스 자체의 경계로 강제하지 않는다.

이 문서는 [기존 Spec](course-area-coverage-742-spec.md)과 [Plan](course-area-coverage-742-plan.md)의 선행 판단을 갱신한다. 기존의 여러 원 확장은 비교 대안으로 보존한다. 도시 전체 방식의 효과·속도·API 호환성은 아직 실험하지 않았다.

진행 상황: [폴리곤 로컬 검증 결과](../reports/region-polygon-lab-20261012.md). 공식 SHP를 확보했고 원본·도형 복구 후보를 분리해 적재했다. 복구 후보에서 수원·성남·고양·세종 로컬 적격 가게 2,802곳이 전부 유일하게 매칭됐다. 추천 품질 실험이나 운영 반영은 아니다. 코드표의 상위 관계는 주소 이름의 모든 중간 단계를 담지 않을 수 있어, 분당구→경기도 관계를 보존하면서 앱의 성남시 범위는 별도로 매핑한다.

## 경계가 없어도 가능한 이유

`store`에는 `region_1st`, `region_2nd`, `region_3rd`와 `geography(Point, 4326)` 가게 좌표가 있다. 신뢰할 수 있는 소속이 이미 있으면 `경기 / 수원시`로 후보 가게를 조회하는 데 수원시 외곽선을 알 필요는 없다. 반면 소속이 없는 임의 좌표를 판정하거나 주소와 좌표를 대조할 때는 공식 경계 또는 역지오코딩 근거가 필요하다.

코스 구성에는 가게 간 거리를 사용한다. PostGIS는 두 좌표 사이 거리 조건을 geography의 미터 단위로 계산할 수 있다. 이는 도로·도보 이동 시간과는 다르다. [ST_DWithin 공식 문서](https://postgis.net/docs/ST_DWithin.html)

예를 들어 수원시 전체 적격 가게를 후보로 확보한 뒤, 서쪽 가게 주변과 동쪽 가게 주변에서 각각 짧은 코스를 만들어 비교한다. 고정된 중심 원 밖이라는 이유로 동쪽 가게를 처음부터 제외하지 않는다. 인접한 두 동의 가까운 가게도 같은 도시 범위 안에서는 한 코스에 들어갈 수 있다.

확인한 저장 형태와 해석상 주의점:

- 성남시 26곳의 `region_3rd`가 분당구 10곳·수정구 12곳·중원구 4곳이다. 사용자가 확인한 배경은 `경기 → 성남시 → 분당구 → 동`처럼 주소가 4단계라는 것이다. 이 집계를 ‘26곳의 주소 오류’로 해석한 앞선 판단은 철회한다. 저장 단계와 공식 구역의 역할을 구분해야 하며, 개별 값의 오류 여부는 원본·유입 경로·당시 투영 규칙과 대조해야 한다.
- 성수동 후보는 `성수동1가` 112곳과 `성수동2가` 107곳으로 저장돼 있다. 앱의 `성수동` 이름과 단순 등호로 연결하면 놓친다.
- 세종처럼 시군구 중간 단계가 없는 주소에는 별도 규칙이 적용된다. 현재 dataops resolver는 `region_2nd = region_3rd = 읍면동`으로 투영한다. 이 반복 자체는 오류가 아니다. 숫자 값 사례는 별도로 원본·파서 확인이 필요한 관측이며, 세종의 정상적인 단계 생략과 한꺼번에 오류로 분류하지 않는다.

dataops의 `scripts/region_resolver.py`에는 이미 좌표 → 카카오 B 법정동 코드 → 버전 있는 공식 기준표 대조 → 앱 3필드 투영 과정이 구현돼 있다. `region_resolution`은 원형 코드·상위 계층·좌표·기준 버전을 보존한다. 그러나 이 코드가 있다는 사실은 기존 운영 가게 전체가 정비됐다는 증거가 아니다. 이번에는 resolver를 실행하거나 데이터 값을 고치지 않았다.

앱 투영은 `성남시 분당구 → 성남시`, `성수동1가·2가 → 성수동`처럼 공식 구역을 합칠 수 있다. 따라서 앱의 세 필드와 공식 경계는 1:1 관계가 아니다. 기존 원형 코드와 앱 구역 사이의 명시적인 매핑이 필요하다.

### 지역 단계와 필드 번호를 분리한다

| 주소 구조 예시 | 보존해야 하는 의미 | 처리 원칙 |
|---|---|---|
| 서울 → 성동구 → 성수동2가 | 시도·구·법정동 | 원형 코드 계층과 앱의 성수동 묶음을 구분 |
| 경기 → 성남시 → 분당구 → 정자동 | 시도·시·구·법정동 | 중간 구를 버리지 않고 보존, 도시 추천은 성남시 상위 소속으로 조회 |
| 세종 → 나성동 | 시도·법정동, 중간 단계 생략 | 없는 구를 만들지 않고 실제 상위 코드 관계 사용 |

이 예시는 주소 계층 설명이며 모든 기존 행이 같은 방식으로 세 필드에 투영됐다는 뜻은 아니다. `region_3rd = 동` 또는 `region_2nd = 시군구`를 전국 공통 규칙으로 강제하지 않는다. 네 번째 문자열 필드만 추가해도 단계 생략·리·앱 표시 묶음은 해결되지 않는다. 추천용 소속은 코드·구역 종류·상위 코드 관계로 식별하고, 기존 세 필드는 검색·표시 호환을 위해 유지하는 안을 우선 검토한다.

확인한 로컬 BE `AddressParser`는 둘째 토큰을 region2nd로 쓰고 셋째 토큰이 읍·면·동·가·리로 끝날 때만 region3rd로 쓴다. 넷째 토큰을 찾아가거나 세종의 읍면동을 셋째 필드에 반복하는 처리는 없다. 반면 dataops resolver는 위 별도 투영 규칙을 가진다. 따라서 현재 parser만으로 과거 26개 행의 생성 경로를 설명하거나 현재의 모든 유입 경로가 통일돼 있다고 가정하지 않는다.

선행 검증에 3단계 주소, 시·구가 함께 있는 4단계 주소, 중간 단계가 없는 세종, 읍면·리, 도로명 주소를 포함한다. 각 사례의 원형 계층·공식 코드·기존 3필드 투영·추천 scope 결과를 대조하고, 정상 변형과 실제 파싱 오류를 나눠 보고한다. 이 단계 전에 운영 지역 값을 일괄 수정하지 않는다.

## 대안 비교

| 기준 | A: 고정 반경 여러 개 | B: 행정·법정동별로 코스 제한 | C: 도시 전체 후보 + 근거리 코스 |
|---|---|---|---|
| 후보 자격 | 등록한 원들의 합집합 | 소속 동에 있는 가게 | 선택한 도시/구역의 적격 가게 |
| 원 밖 가게 | 원을 추가해야 진입 | 해당 동이 지원되면 진입 | 소속이 확인되면 후보가 됨 |
| 경계 도형 필요 | 없음 | 문자열/코드 소속만으로 시작 가능 | 문자열/코드 소속만으로 시작 가능 |
| 인접 동의 가까운 가게 | 같은 원에 있으면 가능 | 동 경계로 잘릴 수 있음 | 같은 선택 구역 안이면 가능 |
| 넓은 동·흩어진 가게 | 원 크기로 일부 제한 | 별도 거리 제약 필요 | 별도 거리 제약 필요 |
| 운영 관리 | 중심·반경·이름을 계속 관리 | 구역·코드·이력 관리 | 구역 정합성 + 탐색 비용 관리 |
| 기존 areaId 계약 | 가장 쉽게 유지 | 동 코드 매핑 필요 | 동적 코스 범위 식별 방식 필요 |
| 판단 | 단기 개선 비교군 | 소속 기준으로 활용 | 우선 검증할 목표 방향 |

경계 폴리곤 도입은 A/B/C 중 하나를 대신하는 추천 알고리즘이 아니다. 공식 구역 소속을 정확하게 관리하는 데이터 기반이다. 폴리곤을 확보해도 좋은 코스를 만드는 문제와 도로 단절 문제는 남는다.

## 도시 전체 방식의 검증용 설계

1. 선택 구역을 표시 이름이 아닌 안정된 내부 scope ID로 식별하고, 공식 코드 집합과 연결한다. 시범은 수원·성남·고양이다. 소속 미확인 가게는 별도 집계해 데이터 누락을 드러낸다.
2. 구역 전체 적격 가게에 동일한 회원 점수·이력 제외를 적용한다. 전 도시 상위 15곳만 먼저 자르면 서로 멀리 떨어진 가게만 남을 수 있으므로 기존 SQL의 반경 필터만 제거하는 변경은 하지 않는다.
3. 랩에서는 각 적격 가게를 출발 후보로 삼고, 좌표 기반 이웃 조회로 여러 코스 초안을 만든다. 기존 1,500m 구간 제한과 1~6곳 요청 조건을 유지해 대조한다. 공간 인덱스/미리 계산한 이웃 관계를 활용하되 요청마다 DB를 가게 수만큼 호출하지 않는다.
4. 코스가 되는지와 회원 점수·조회·저장·동선을 비교한다. 기존 일차의 장소 맥락은 먼저 제한한다. 전역 최적 코스나 모든 가게의 실제 노출을 보장하지 않는다.
5. 전체 출발 후보 실험을 기준으로 제한된 탐색을 비교한다. 공간 셀별 후보, 관심 가게 주변 후보 등을 합치는 방식의 누락률과 비용을 측정한다. 동네 개수 6개나 전체 top K를 그대로 가져와 새로운 고정 사각지대를 만들지 않는다.
6. 연속 구간이 짧아도 전체 코스가 길어질 수 있으므로 총 거리·최대 구간·코스 전체 퍼짐·도로 단절 사례를 함께 검토한다. 새 총 거리 상한은 실험 후 결정하며 거리만으로 도보 가능성을 확정하지 않는다.

밀도 군집화를 채택하더라도 군집을 공식 동 경계로 부르지 않는다. 밀도 기반 군집은 소수 가게를 잡음으로 분류할 수 있고, 길게 연결된 큰 군집도 코스 자체는 아니다. 초기 설계에 DBSCAN 도입을 필수로 두지 않는다. [PostGIS DBSCAN 문서](https://postgis.net/docs/ST_ClusterDBSCAN.html)

## 기존 앱 계약에서 추가로 풀어야 할 부분

현재 `areaId`는 영속된 `course_area` 행이다. RETRY는 `previousRecommendationId`가 있지만 다음 동네 요청은 `areaId + exactArea=true`를 사용한다. 도시에 동적으로 만든 코스를 기존 동네 행으로 가장하면 재추천 범위·제목·다음 동네가 잘못될 수 있다.

- 선택한 도시 scope와 생성한 지역 코스 scope를 구분한다. 코스 scope는 최소한 생성 기준·공간 범위/후보 집합·버전을 저장해 같은 시트와 다시 받기의 위치를 유지해야 한다. 삭제·자격 상실 등 최신 제외는 계속 적용한다.
- 동적 scope를 일반 `course_area`에 요청마다 생성하는 방식은 기본안으로 삼지 않는다. 도시 대표 ID와 추천에 저장된 scope, 또는 명시적 scope token을 비교한다.
- `nextArea`의 식별자와 표시 이름, `exactArea`, `lastBatch`의 의미를 FE와 함께 확정해야 한다. 현재 API를 수정 없이 유지할 수 있다고 아직 단정하지 않는다.
- 동일 회원·코스·도시 scope·일차의 중복 제외, 정책 버전, 최종 한 건만 저장, 기존 Gemini 이유 경로 등 기존 Spec의 공통 원칙은 유지한다.

## 공식 경계를 지금 도입하는 방법

국토교통부는 법정구역 경계의 도형·속성 정보를 제공하며, 공공데이터포털은 SHP 형태 파일과 브이월드 제공 경로를 안내한다. 도입할 자료는 실제 좌표를 가진 SHP/GeoJSON/WFS 피처여야 한다. 지도 이미지인 WMS만 확보해도 경계 판정이 가능하다고 간주하지 않는다. [전국법정구역 표준데이터](https://www.data.go.kr/data/15029173/standard.do) · [행정구역도 WMS/WFS](https://www.data.go.kr/data/15059008/openapi.do)

현재 dataops가 B 법정동을 기준으로 하므로 법정구역 경계를 우선 검토한다. SGIS의 행정동 경계를 같은 코드 체계라고 가정해 붙이지 않는다. 도입할 자료의 코드체계·기준일·좌표계·이용조건을 확인한 다음 기존 공식 코드 기준표와 버전을 맞춘다.

권고 적재 구조는 별도 지역 참조 테이블이다. 기존 `store.region_*` 문자열 칼럼에 좌표 배열을 넣지 않는다.

```text
공식 경계 원본 + 출처/기준일/해시/좌표계
  → region_boundary(code, code_system, level, parent_code, version, MultiPolygon)
  → 가게 좌표와 대조한 소속 근거
  → 앱 구역(scope) ↔ 공식 코드 집합 매핑
  → 추천 후보 조회
```

실행 순서:

1. 경기 시범 세 도시의 공식 경계 샘플을 내려받고 원본을 보존한다. 현행 파일의 실제 기준일을 확인한다. 경계 자체를 가게 좌표의 외곽선으로 추정해 공식 구역으로 사용하지 않는다.
2. 코드·상위 계층·좌표계를 검증하고 PostGIS MultiPolygon으로 적재한다. 원본 CRS가 다르면 실제 변환하고 SRID 이름만 바꾸지 않는다. 여러 조각·섬·구멍을 보존하고 geometry 유효성을 확인한다.
3. 가게 좌표가 도형 내부 또는 경계에 들어오는지 판정한다. 예를 들어 `ST_Covers(boundary, point)`는 경계선도 포함한다. 0개 또는 복수 구역에 걸리는 사례는 미해소/모호 상태로 남기고 이름이나 가장 가까운 중심만으로 확정하지 않는다. [ST_Covers 공식 문서](https://postgis.net/docs/ST_Covers.html)
4. 기존 resolver의 법정동 코드·조회 좌표·기준 버전과 비교한다. 경계와 역지오코딩이 다르면 어느 것이 최신이고 좌표가 정확한지 검토한다. 기존 `region_resolution` 근거를 덮어쓰지 않는다.
5. 공식 하위 구역들의 코드 집합을 앱의 수원시·성남시·고양시로 연결한다. 성수동 같은 합성 표시 구역도 코드 집합으로 표현한다. 한 문자열을 경계 이름에 억지로 맞추지 않는다.
6. 소속 정정 예정 수·기존 값과 불일치·미해소·복수 일치 보고서를 먼저 만든다. 운영 필드 수정은 기존 dataops 반영 절차로 분리하고 이번 분석에서는 수행하지 않는다.

최초 확인 시 두 레포에 경계 파일은 없었으나, 이후 사용자의 브이월드 로그인으로 2026-09-09 전국 SHP를 확보했다. API 키 발급 없이 공식 파일 다운로드 경로로 로컬 검증을 수행했다. 실제 파일 기준일·원본 오류·도형 복구 결과와 제한은 위 검증 기록에 남겼다. 계정 생성·키 발급·유료 신청은 수행하지 않았다.

## 비교 실험과 결정

기존 A/B/C 평가 이름은 유지하고 새 군 D를 추가한다.

| 실험 | 지역 후보 범위 | 코스 선택 |
|---|---|---|
| A | 현재 원 | 현재 방식 |
| B | 확장한 원 | 현재 방식 |
| C | B와 같은 원 | 완성 코스 비교 |
| D | 도시 전체 | 여러 출발 후보에서 근거리 코스 비교 |

주소·코드 정비 효과와 알고리즘 효과를 섞지 않는다. 먼저 같은 현재 스냅샷으로 A/B/C/D를 비교하고, 정비된 공통 스냅샷에서도 전체를 다시 실행한다. 경계 도입의 효과는 소속 일치율·미해소율·불일치 사례로 별도 평가한다.

지표는 적격 후보 커버리지, 실제 선택 가게 커버리지, 취향군별 점수·종류 일치, 충족률, 중복률, 총 거리·최대 구간·퍼짐, p50/p95다. 도시 전체를 후보로 삼아 구조적 커버가 높아져도 일부 시작점만 탐색하면 실제 노출은 좁을 수 있으므로 두 커버리지를 구분한다.

권고 실행 순서는 **지역 소속·공식 코드 현황 확인 → 경계 샘플 확보와 소속 대조 → D의 랩 비교 → API 범위 식별 계약 → 최종 Spec/Plan 확정 → 구현**이다. 경계 확보가 지연돼도 검증된 코드/주소 소속을 이용한 D의 랩 실험은 진행할 수 있다. 대안 A~D 중 어느 것이 운영에서 우수한지는 아직 실측하지 않았다.
