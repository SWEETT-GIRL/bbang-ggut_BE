# 월간 빵일지 백엔드

관련 작업: [백엔드 #822](https://github.com/SWEETT-GIRL/bbang-ggut_BE/issues/822),
[프론트 #122](https://github.com/SWEETT-GIRL/daedongbbangmap/pull/122).
기준은 2026-10-01 프론트의 `docs/monthly-report-backend-handoff.md`와 `src/features/monthly-report/model.ts`다.

어드민 생성·미리보기·발행·푸시 예약과 S3 이미지 등록은 [어드민 연동 문서](monthly-report-admin.md)를 참고한다.

## 이번 구현

`GET /reports/monthly/{yearMonth}/me`는 Bearer 토큰의 회원에 대해 저장된 스냅샷을 조회한다.
회원 ID를 경로나 요청 파라미터로 지정할 수 없다. 기존 `ApiResponse`의 `data`에 보고서를 담는다. 기존 발행본은 schemaVersion 1, 빵력 정책으로 새로 생성하는 발행본은 2다.
개인 통계 6장과 표지가 대상이며 공동 결산·이용시간·배지·서버 공유 이미지 생성은 이번 계약에 없다.

| 상황 | HTTP | 응답 코드 |
| --- | --- | --- |
| 정상 발행본 | 200 | 기존 성공 코드, data에 전체 보고서 |
| 잘못된 월 | 400 | MONTHLY_REPORT4001 |
| 인증 없음 | 401 | 기존 인증 오류 |
| 행 없음 또는 WITHHELD | 404 | MONTHLY_REPORT4041 |
| FAILED | 503 | MONTHLY_REPORT5031 |
| payload 손상, 회원·월 불일치 | 500 | MONTHLY_REPORT5001 |
| DB 등 기타 서버 실패 | 500 | 기존 서버 오류 |

- 월은 `2000-01`~`2099-12`의 `YYYY-MM`만 받는다. 아직 발행되지 않은 현재·미래 월은 404다.
- 삭제된 회원은 기존 `MemberReader` 규칙으로 조회가 차단된다. 발행 대상은 월말 전에 가입한 현재 일반 회원(`USER`)이다. 게스트·블로그 봇·탈퇴 회원은 제외한다. 대상 조회와 발행 직전 검사에 적용했다.
- 필수 수치는 nullable wrapper로 역직렬화하고 검증한다. 누락을 0으로 바꾸지 않으며 문자열·소수·음수·안전한 정수 범위 초과를 거절한다.
- `comparison.currentRecords`와 요약 기록 수, 버전별 능력치 계약과 총합, artwork의 캐릭터·행성·유형 일치를 검증한다.
- 전월 집계가 없으면 `comparison.previousRecords: null`로 발행한다. 필드 자체는 필수다. 프론트는 비교 카드만 생략하고 나머지 보고서를 표시한다.
  전월 활동이 실제 0이면 숫자 `0`으로 보내 비교 카드를 표시한다. `currentRecords`는 계속 필수이며 요약 기록 수와 일치해야 한다.
  프론트 응답 검증과 카드 목록에 null 처리를 연결했다. 비교 카드를 생략하므로 공유 진입에서도 제외된다. 앱 연동을 배포한 뒤 null을 포함한 보고서를 발행한다.
- 기존 schemaVersion 1의 `totalScore: null`, `abilities: null`은 그대로 전달한다. 버전 2는 계산된 빵력을 필수로 저장한다. 실제 활동 0은 0으로 전달한다.
- 조회 응답에는 `Cache-Control: no-store`를 붙인다. 조회 시 원시 활동을 다시 집계하지 않는다.
- `nickname`은 조회 시 현재 회원의 닉네임으로 반환한다. 닉네임 변경은 응답에만 반영하고 저장된 통계는 갱신하지 않는다.
- 빵 사진은 발행 시 선택한 원본 기록 ID와 사진 참조 UUID로 조회한다. 현재 원본/리사이즈 키를 반환하므로
  명시적으로 연결한 사진 교체가 반영된다. 현재 사진에 보고서와 같은 빵 종류의 태그가 있어야 한다.
  태그 삭제·종류 변경, 사진 삭제, 본인 원본 기록과 연결 불일치 시 null이다. 비공개 기록도 본인은 볼 수 있다.
- 사진 조회는 숫자·순위·대표 사진의 출처를 다시 집계하지 않는다. 사진 출처를 복원하지 못한 구버전 보고서는 기존 키의 소유권·존재와 해당 사진의 현재 빵 종류를 확인한다.

## 빵력과 유형 정책 (`bread-power-v1`)

빵력은 해당 월의 활동량에 비례해 계속 증가한다. 월별 값이며 이전 달 빵력을 누적하지 않는다.

| 활동 | 집계값 | 빵력 |
| --- | --- | --- |
| 둘러본 빵집 | 해당 월 상세 조회한 서로 다른 가게 수 | × 1 |
| 저장한 빵집 | 해당 월 저장하고 월말에도 남은 서로 다른 가게 수 | × 3 |
| 계획한 빵집 | 해당 월 추가하고 월말에도 남은 서로 다른 계획 가게 수 | × 5 |
| 빵로그 | 해당 월 섭취했고 월말에 존재한 기록 수 | × 7 |

- 총 빵력은 네 기여도의 합이다. 코스 수와 빵 태그 수에는 별도 가산점을 주지 않는다.
- 유형은 기여도가 가장 높은 활동으로 정한다. 동점은 기록 → 계획 → 저장 → 조회 순서다.
- 네 활동이 모두 0이면 `seed`, 총 빵력과 네 기여도는 0이다.
- 로그만 10개면 70, 100개면 700, 200개면 1,400 빵력이다. 1,000에서 멈추지 않는다.
- `MonthlyReportActivityPolicy`가 집계 후 초안의 점수·유형을 대체한다. 유형이 달라지면 초안의 전용 artwork를
  제거해 다른 유형 그림이 표시되지 않게 한다. 캐릭터와 행성은 준비된 초안의 값을 보존한다.
- `raw_metrics.activityPolicy`에 정책 버전·가중치·기여도·동점 순서·총점·유형을 기록한다.
  이미 발행된 회원·월은 이 계산을 다시 실행하지 않는다.
- JavaScript 안전한 정수 범위를 넘는 잘못된 입력은 발행을 실패시킨다. 범위 안으로 잘라 저장하지 않는다.

### 프론트 응답 계약 변경

새 발행본은 `schemaVersion: 2`다. 필드명 `totalScore`와 `score`는 유지하고 의미는 빵력으로 정의한다.
버전 2의 `abilities`와 `totalScore`는 필수이며, 각 능력치에는 `maxScore`가 없다.
기존 버전 1 발행본은 저장된 점수·상한·미집계 null을 그대로 반환한다.

예: 조회 80곳, 저장 20곳, 계획 10곳, 로그 200개인 경우:

```json
{
  "type": "record",
  "totalScore": 1590,
  "abilities": {
    "explore": {"score": 80},
    "save": {"score": 60},
    "plan": {"score": 50},
    "record": {"score": 1400}
  },
  "artwork": null
}
```

앱은 총합을 `1,590 빵력`으로 표시하고 개별 게이지에는 숫자를 표시하지 않는다.
게이지 길이 변환은 빵력과 분리한다. 프론트에 `score / (score + 100)`을 적용했다.
100은 절반 길이가 되는 기준이며 만점이 아니다. 모든 회원과 활동에 같은 기준을 사용하고, 원본 빵력은 바꾸지 않는다.
앱은 버전 1·2를 함께 읽으며 기존 버전 1의 게이지 비율과 총점 명칭은 유지한다.
화면·공유 미리보기, 0 및 1,000 초과 빵력을 시뮬레이터에서 확인했다.
**연동된 앱을 배포한 뒤 버전 2 보고서를 발행한다.** 코드 반영과 운영 배포는 구분한다.

## 내 보고서 목록

`GET /reports/monthly/me?page=0&size=12`

- 동일한 Bearer 인증을 사용한다. 본인의 PUBLISHED만 보고서 월 내림차순으로 반환한다.
- 기본값은 page=0, size=12다. page는 0 이상, size는 1~100이며 범위 밖이면 400/MONTHLY_REPORT4002다.
- 데이터가 없으면 200과 `content: [], hasNext: false`를 반환한다. WITHHELD/FAILED는 목록에 포함하지 않는다.
- 목록에는 월·발행 시각·상세 경로·발행 당시 캐릭터를 담는다. 다음 페이지는 page를 1 증가시킨다.
- `character`는 상세와 같은 `{ code, name, imageKey }`이며 저장된 발행 시점 열에서 읽는다.
  현재 사용자 선택이나 카탈로그와 조인하지 않는다. `imageKey`는 CDN 키이며 없으면 null이다.
  클라이언트는 구버전 응답에 character가 없거나 null이면 중립 폴백을 표시한다.
- `publishedAt`은 UTC ISO-8601 문자열, `link`는 앱 내부 경로다. 응답은 `Cache-Control: no-store`다.

```json
{
  "success": true,
  "code": "COMMON200",
  "message": "요청에 성공했습니다.",
  "data": {
    "content": [
      {
        "yearMonth": "2026-09",
        "publishedAt": "2026-10-01T01:00:00Z",
        "link": "/reports/monthly/2026-09",
        "character": { "code": "cat", "name": "냥이", "imageKey": null }
      }
    ],
    "hasNext": false
  }
}
```

## 저장과 발행 연결점

`monthly_report_member`의 기본 키는 `(member_id, year_month)`다.
`payload`, `raw_metrics`는 JSONB, `generated_at`, `published_at`은 TIMESTAMPTZ다.
상태는 `WITHHELD`, `FAILED`, `PUBLISHED`를 구분한다.

`MonthlyReportMember` Entity는 `MonthlyReportMemberId(memberId, yearMonth)` 복합키를 사용한다.
`MonthlyReportRepository`는 `JpaRepository`이며 상세는 Entity, 목록은 필요한 열만 읽는 JPA projection/Slice로 조회한다.
발행본에는 변경 메서드를 두지 않고 Hibernate `@Immutable`로 일반 dirty checking 갱신을 막는다.
동시 발행을 막는 PostgreSQL upsert는 Spring Data의 native query로 유지한다.
사진 조회는 `BreadRecordTagRepository.findMonthlyReportPhotoTags`의 JPQL fetch join으로 현재 태그·사진·원본 기록·메뉴 분류를 가져온다.
집계와 동일한 `resolvedCategory()`로 빵 종류를 확인하므로 메뉴 분류 보완 규칙도 일치한다.

### 발행 당시 캐릭터·행성 보존

Entity에 `characterCode`, `characterName`, `characterImageKey`, `planetCode`, `planetName`을 저장한다.
현재 MemberWorld나 카탈로그와의 연관관계로 두지 않으며, 조회 때 현재 선택·진행도·이름을 다시 가져오지 않는다.
통계·능력치·전용 artwork 코드/버전/키는 최종 payload에 그대로 보관한다.
payload에 남아 있는 발행 당시 nickname은 조회 응답에서 사용하지 않고 현재 회원의 닉네임으로 대체한다.

발행 upsert가 검증된 payload에서 다섯 열을 함께 추출해 저장하고, DB 제약과 조회 검증이 둘의 불일치를 막는다.
발행된 회원·월에 다시 호출해도 캐릭터·행성과 payload를 덮어쓰지 않는다.
어드민 경로는 초안 생성 시점의 세계관을 저장하고 미리보기와 발행본에 동일하게 사용한다. 과거 월말 세계관을 복원하지 않는다.

`V20261005222046__add_monthly_report_appearance.sql`은 기존 발행 payload에서 다섯 열을 채운다.
현재 프로필을 사용해 과거 값을 추정하지 않는다. 코드뿐 아니라 표시 이름과 이미지 키도 복사하므로
카탈로그 이름이나 사용자 선택이 바뀌어도 과거 보고서의 값은 유지된다.
이미지 파일 자체가 바뀌지 않게 하려면 기존 계약대로 버전이 포함된 불변 CDN 키를 사용한다.
삭제된 개인 빵 사진을 응답에서 가리는 기존 정책은 유지한다.

`MonthlyReportPublicationService.publish(...)`는 기존 내부 배치에서 호출하며 최초 발행 시 즉시 푸시를 요청한다.
어드민 HTTP API는 초안을 생성·저장하고 미리보기 후 발행한다. 이 경로는 `publishWithoutNotification(...)`으로
발행본을 저장한 뒤 알림함과 푸시 예약을 같은 트랜잭션에 기록한다.

### 빵 종류 집계와 생성 연결

`MonthlyReportGenerationService.publishFromDraft(...)`는 초안에 기록 수·기록한 빵집 수·빵 종류·전월 비교를
실제 데이터로 채워 발행 서비스를 호출한다. 어드민 경로는 `prepare(...)`로 집계만 실행하며
`MonthlyReportAppearanceReader`가 현재 캐릭터·행성을 읽고 `MonthlyReportPreparation`이 이미지 등록부를 연결한다. 빵력과 유형은 실제 집계값으로 계산해 초안을 대체한다.
빵집 상세 조회 수는 적재된 조회 신호에서, 동네·저장·계획·코스는 월말 이력에서 계산해 초안 값을 대체한다.
이미 PUBLISHED인 회원·월이면 집계 서비스를 호출하지 않고 false를 반환한다.

`MonthlyReportSourceReader`가 원천 이력의 월말 직전 마지막 버전으로 기록·태그·사진 식별자·분류를 읽고,
`MonthlyReportBreadAggregationService`가 이 공통 원천을 집계한다.
본인의 기록은 `eatenAt >= 해당 월초 AND eatenAt < 다음 월초` 범위로 제한한다.
월말에 존재한 기록만 포함하므로 `createdAt < 다음 월초`와
`deletedAt IS NULL OR deletedAt >= 다음 월초`를 함께 적용한다. 월말 후 삭제된 로그는 통계에 남지만 사진은 조회 시 숨긴다.
기존 빵로그와 같은 한국 시간 LocalDateTime 기준이며 본인의 비공개 기록도 포함한다.
모든 집계가 같은 원천 스냅샷을 사용한다. 원천 읽기는 별도 REPEATABLE_READ 트랜잭션에서 처리한다.

- 태그 1개를 기록된 빵 1회로 센다. 같은 기록의 여러 태그도 각각 세며 실제 섭취 수량을 추정하지 않는다.
- `BreadRecordTag.resolveCategory()`를 재사용한다. 태그가 구체 분류이면 그대로, 빵·기타이면 당시 메뉴 분류로 보완한다.
- 전체 `summary.breads`는 미분류를 포함한 태그 수다. 빵·기타로 남은 태그는 종류별 순위에서 제외하고
  `raw_metrics.breadAggregation.uncategorizedTags`에 따로 남긴다.
- 종류별 순위는 횟수 내림차순, 동점이면 이름 오름차순이다. 대표 사진 선택은 횟수에 영향을 주지 않는다.
- 대표 사진은 같은 종류의 **최고였던 빵으로 선택된 태그**를 우선한다. `lovedBreads`와 구버전 `lovedBread`를 확인한다.
  이 중 가장 최근 eatenAt, 기록 ID 내림차순, 사진 순서·사진 ID·태그 ID 오름차순으로 결정한다.
  최고였던 빵이 없으면 같은 종류의 일반 기록에 같은 최신순 규칙을 적용한다.
- 사진 키는 존재하는 640 → 320 → 1024 리사이즈 키 → 원본 순으로 선택한다.
- 발행 시 `raw_metrics.breadPhotoSources`에 종류별 `{ recordId, photoReferenceId }`를 저장한다.
  새로 생성한 `payload.breads[].imageKey`는 null이며, 조회 시 사진 출처로 현재 키를 채운다.
  구버전 발행본에 남은 초기 파일 키도 출처가 있으면 식별자로 사용하지 않는다.
- 사진을 교체해도 참조 UUID를 유지하고, 그 사진에 같은 빵 종류의 태그가 있으면 수정된 사진을 보여준다.
  태그 이름이나 ID는 달라져도 된다. 태그가 없어지거나 다른 종류로 바뀌면 null로 가린다.
  사진 삭제 시에도 null로 가리며, 같은 로그의 다른 사진을 다시 선택하지 않는다. 횟수·순위는 발행 당시 값을 유지한다.
  현재 null만으로 로그 삭제와 사진 누락을 구분할 수 없으므로 화면 문구는 ‘사진을 볼 수 없어요’를 권장한다.
- 집계 버전 `bread-history-v3`, 사진 선택 기준 `loved-then-latest-eaten`, 전체·미분류 태그 수를 원시 메타데이터에 저장한다.

### 기록한 빵집과 전월 비교

`MonthlyReportRecordAggregationService`가 공통 원천 스냅샷의 기록 수·기록한 빵집 수를 계산한다.
태그와 별도로 기록 단위로 세므로 한 로그의 태그 수만큼 기록 수가 늘어나지 않는다.
가게 ID가 있으면 같은 ID를 1곳으로 세고, ID가 없으면 기록마다 각각 1곳으로 센다. 직접 입력한 이름은 비교하지 않는다.
예: A가게 ID로 3건, 같은 직접 입력 이름으로 2건을 남기면 기록 5건·기록한 빵집 3곳이다.
빵집 상세 조회 수는 이 집계에 포함하지 않는다.

전월 수치는 같은 회원의 직전 월 PUBLISHED payload의 `summary.records`를 재사용한다.
전월 원본 로그를 다시 세지 않는다. 발행본이 없거나 FAILED/WITHHELD면 `previousRecords: null`이다.
raw_metrics에는 `recordAggregation`의 버전·기록 수·빵집 수·전월 수치와 출처를 저장한다.

### 월말 이후 빵로그 수정·삭제

수정 전 섭취일·가게·지역·최고였던 빵·태그·메뉴 분류·사진 UUID를 이력으로 복원한다.
원본 태그·사진이 하드 삭제되어도 이력이 유지되므로 기록 수와 빵 종류 수를 월말 기준으로 계산한다.
이력 수집 이후에는 태그가 원래 0개였던 기록과 삭제 때문에 태그가 없어 보이는 기록도 구분한다.
대표 사진은 당시 출처를 유지한다. 현재 로그·사진·해당 종류의 태그가 없으면 조회 응답의 이미지 키만 null이다.

마이그레이션 전에 이미 없어진 이력은 복원할 수 없다. 지원 시작 시각보다 먼저 끝난 월은
`SOURCE_HISTORY_UNAVAILABLE`로 생성을 중단한다. 현재 상태나 0으로 대체해 발행하지 않는다.
이미 발행된 월은 원천 읽기 전에 건너뛰므로 이력 지원 범위 변경으로 재계산하거나 숨기지 않는다.

### 저장·계획·공동 코스의 월말 집계

`MonthlyReportSourceReader`가 저장·직접 계획의 월말 이전 마지막 상태를 선택한다.
그중 해당 월에 생성된 관계만 세므로 이전 달부터 보유한 가게는 제외한다. 월중 삭제한 관계는 제외하고,
월말 이후 삭제한 관계는 유지한다. 재추가했으면 마지막 관계의 생성 시각을 사용한다.

코스는 월말 당시 소유자에게 귀속한다. 해당 월에 생성해 월말에도 남은 코스를 세며,
코스에 담은 가게는 해당 월에 추가한 관계 중 월말에 남은 것만 포함한다.
코스 자체가 월말 전에 삭제됐다면 그 가게도 제외한다. 이전 달 코스에 이번 달 추가한 가게는 포함한다.
친구가 내 코스에 추가한 가게도 내 통계에 포함한다. 여러 코스와 직접 계획의 가게 ID는 합집합으로 한 번만 센다.
소유권 이관은 코스의 변경 이력으로 복원하므로 추가·제거 이벤트의 행위자를 짝짓지 않는다.

생성 서비스가 계산된 `saved`, `planned`, `courses`를 payload와 raw_metrics에 함께 채운다.
`viewed`는 아래의 월간 상세 조회 집계로 채운다.

### 둘러본 빵집과 동네

- `MonthlyReportViewedStoreAggregationService`는 `user_store_interaction`의 STORE_VIEW에서
  해당 회원·월의 서로 다른 storeId 수를 센다. 월은 occurredAt 기준이고 createdAt 적재 시각과 구분한다.
  여러 날 같은 가게를 조회해도 한 곳이며 저장·계획·다른 회원·익명 신호는 제외한다.
- `user_interaction_ingest_day`는 성공한 적재 날짜를 저장한다. 기존 일별/수동 적재 서비스가 모든 원천을 처리한 뒤
  같은 트랜잭션에 기록하므로 실패하면 함께 롤백된다. 아직 끝나지 않은 당일·미래 날짜는 완료로 기록하지 않는다.
  월 전체 날짜가 완료돼야 집계하며, 하루라도 빠졌으면 MONTHLY_REPORT5033으로 발행을 중단한다.
  완료된 월에 조회 신호가 없다면 실제 0으로 반환한다. 적재 재실행은 같은 날짜 표식을 갱신한다.
- 이 표식은 DB에 수집된 요청 로그의 적재 완료를 뜻한다. 기존 비동기 요청 로그 수집의 유실·늦은 도착까지 보장하지 않는다.
  기존 적재의 성공 여부를 소급해서 추측하지 않으므로 새 마이그레이션 적용 후 필요한 날짜를 재적재해야 한다.
- `MonthlyReportTownAggregationService`는 원천 스냅샷의 regionKey를 시도·시군구와 동네로 분리한다.
  시도 표기는 기존 RegionFormatter로 통일한다. 같은 이름도 지역이 다르면 유지하며 지역·이름 순서로 정렬한다.
  세종_도담동처럼 두 조각인 값도 허용한다. 결측·빈 조각·읍면동리가 단위가 없는 시군구까지만의 값은 제외한다.
  현재 가게 주소로 보완하지 않으며, 월말 후 로그가 삭제되어도 당시 동네는 남는다.
- 생성 서비스는 조회·동네 집계 버전과 결과를 raw_metrics에 남긴다. 발행본 재시도는 집계나 적재 확인을 다시 하지 않는다.

### 발행 대상 순회

`MonthlyReportTargetReader.nextPage(yearMonth, afterMemberId, size)`는 마지막 처리 회원 ID 다음부터 읽는다.
현재 USER·미탈퇴·월말 전 가입 조건과 해당 월 PUBLISHED 없음 조건을 적용한다.
활동 테이블과 조인하지 않으므로 활동 0건 회원도 포함하며 FAILED/WITHHELD는 재시도 대상이다.
처리 중 앞선 회원의 발행으로 대상 수가 줄어도 다음 회원을 건너뛰지 않는다. 배치 크기는 1~1000이다.
미종료 월은 거절한다. 최종 발행 서비스도 현재 회원 유형·가입 시각을 다시 확인한다.
어드민 조립기가 이 대상 조회로 회원을 순회하며 세계관·통계·빵력·등록된 이미지를 포함한 초안을 생성한다.
초안이 준비된 회원의 실행·실패·재시도는 아래 작업 처리 경로로 연결했다.

### 공통 적재와 독립된 보고서 작업

조회 기록은 기존 개인화 적재를 공유한다. 보고서 배치가 전월 전체를 무조건 다시 적재하지 않는다.
추천 계산과 보고서 실행은 별도 경로이며 서로의 성공을 기다리지 않는다.

1. `MonthlyReportJobService.enqueue`가 검증된 초안·원시 메타데이터·산식 버전을 등록한다.
   미종료 월은 거절하며 일반 회원·가입 시각을 검사한다. 회원·월당 한 작업이고 재등록으로 덮어쓰지 않는다.
   이미 발행된 보고서도 등록하지 않는다. 초안의 점수·유형은 실제 발행 시 집계값과 확정된 빵력 정책으로 대체한다.
2. `MonthlyReportBatchService.runDue`가 처리할 시각이 된 작업을 월별로 읽는다. 원천 이력 지원 범위를 확인한 뒤
   `MonthlyReportIngestRecoveryService.ensureComplete`가 완료되지 않은 날짜만 복구한다.
3. 날짜 복구는 기존 `UserInteractionIngestCommandService.ingestMissingDay`를 호출한다.
   기존 일별 적재와 같은 advisory lock을 얻은 뒤 완료 여부를 다시 확인한다.
   다른 실행이 먼저 완료했다면 건너뛴다. 각 날짜를 따로 커밋하므로 중간 실패 후에도 성공한 날짜를 다시 처리하지 않는다.
   추천 프로필 재계산을 추가로 호출하지 않는다.
4. 해당 월의 적재가 완료되면 준비된 작업을 회원 ID 순서로 읽는다. 한 회원씩 별도 트랜잭션에서 처리하며
   `FOR UPDATE SKIP LOCKED`로 다른 실행이 처리 중인 작업을 건너뛴다. 현재 회원 상태도 다시 검사한다.
5. 실제 보고서 생성·발행은 `MonthlyReportJobPublisher`의 별도 트랜잭션이다. 실패하면 발행을 롤백한 뒤
   작업 상태·오류 코드·재시도 시각을 저장한다. 성공한 다른 회원과 원천 적재는 롤백하지 않는다.
6. 발행 커밋 후 작업 완료 기록 전에 프로세스가 중단되어도 다음 실행이 PUBLISHED를 확인하고 작업만 완료한다.
   보고서와 알림을 다시 만들지 않는다. 실패 표시 쿼리도 이미 발행된 보고서를 덮어쓰지 않는다.

`monthly_report_job`은 초안과 실행 상태를 저장하고 `monthly_report_member`는 조회할 보고서를 저장한다.
작업의 READY / FAILED / COMPLETED / CANCELLED를 발행 스냅샷 상태와 구분한다.
작업 Entity는 행 잠금 아래 JPA 변경 감지로 갱신한다. 오류 메시지·원본 데이터 대신 오류 코드만 저장한다.
회원별 생성 실패는 보고서에도 FAILED로 표시해 상세 조회에서 기존 503 응답을 유지한다.
공통 적재 또는 이력 지원 범위 문제는 월 단위로 대기하며 회원별 시도 횟수를 늘리지 않는다.

기본 재시도는 최초 시도 포함 최대 5회이며, 실패 후 30/60/120/240분 뒤부터 다시 처리할 수 있다.
실제 실행은 다음 스케줄 호출 시점이다. 상한에 도달한 실패는 DB에 남고 자동 실행에서 제외하므로 오류 확인이 필요하다.
DB 장애로 작업 상태 자체를 저장하지 못하면 해당 트랜잭션을 롤백하고 다음 실행에서 다시 읽는다.

설정:

```properties
# '-'는 비활성. 실행 시각과 재시도 주기를 정한 뒤 cron을 설정한다.
monthly-report.batch.cron=-
monthly-report.batch.page-size=100
monthly-report.batch.max-attempts=5
monthly-report.batch.retry-delay-minutes=30
```

스케줄러는 준비된 미완료 작업의 월을 조회하므로 전월 작업이 늦어져도 이후 실행에서 처리할 수 있다.
월 전체 또는 회원 전체를 하나의 트랜잭션에 넣지 않는다. 현재 순차 처리에서도 작업·발행·원천 읽기의
중첩된 별도 트랜잭션이 최대 3개 연결을 사용하므로, 병렬화를 추가할 때 연결 풀 크기를 함께 검토한다.

운영 스케줄과 DB는 이번 작업에서 변경하지 않았다. 위 경로는 기존 내부 배치이며 즉시 푸시를 유지한다.
어드민 생성·미리보기·예약 푸시는 별도 runs 경로로 연결했고 기존 내부 배치의 cron을 켤 필요가 없다.

### 사진 수정 요청과 보고서 연결

기존 빵로그 수정은 사진 행을 삭제하고 다시 생성한다. 변하는 photo.id 대신 `bread_record_photo.reference_id`를
추가해 같은 사진의 파일 교체와 재정렬을 추적한다. 새 사진은 새 UUID, 기존 사진은 동일 UUID를 사용한다.
한 UUID는 현재 사진 행 한 건에만 존재하도록 DB 유니크 인덱스를 둔다.
`originalPhotoId`는 사진 교체 관계만 유지한다. 메뉴 태그는 수정 요청으로 다시 생성되므로 별도로 확인해야 한다.

`BreadRecordPhotoRequest.originalPhotoId`는 선택 필드이며, 상세 응답의 `photos[].id`를 사용한다.
프론트는 기존 사진의 편집·교체 요청에 이 값을 함께 보내야 한다. 기존 키를 그대로 쓰는 구버전 요청은 키로
연결을 유지한다. 새 키인데 originalPhotoId가 없으면 새 사진으로 취급하며 순서로 교체 관계를 추정하지 않는다.

```json
{ "fileName": "edited.jpg", "contentType": "image/jpeg", "awsKey": "bread-records/members/123/images/new-key",
  "sortOrder": 0, "width": 800, "height": 600, "originalPhotoId": 42 }
```

- 원본 ID는 수정 중인 본인 로그의 사진이어야 한다. 같은 원본을 여러 요청 사진에 중복 연결할 수 없다.
- 새 로그 생성에 원본 ID를 보내거나 원본이 없으면 400/BREAD_RECORD_INVALID_PHOTO_REFERENCE다.
- 파일 키가 바뀌면 기존 리사이즈 키와 완료 상태는 이어받지 않고 새 파일 처리 상태를 사용한다.
- 사진을 삭제하고 별도 사진을 추가하는 경우 originalPhotoId를 보내지 않는다. 보고서의 삭제된 사진을 다른 사진으로 대체하지 않는다.
- 프론트의 originalPhotoId 전송 연결은 별도 반영이 필요하다. 응답 imageKey 구조와 기존 업로드 API는 유지한다.

`V20261005222047__add_bread_photo_reference.sql`은 사진 UUID를 채우고,
`V20261005222048__link_monthly_report_bread_photos.sql`은 기존 보고서의 사진 키가 본인 사진 한 건에만
대응하는 경우 출처를 연결한다. 삭제된 사진이나 여러 기록에 공유된 키의 출처는 추측하지 않는다.

`MonthlyReportPayloadCodec.write`는 DTO를 JSON 문자열로 직렬화하고, `read`는 저장된 문자열을 DTO로 역직렬화한다.
두 경로 모두 계약 검증을 수행한다. HTTP 응답 JSON 직렬화는 Spring MVC가 별도로 처리한다.
schemaVersion 1은 기존 `score <= maxScore` 검증을 유지한다. 버전 2는 활동 기여도 합계를 검증하고 `maxScore`를 받지 않는다. 빵력에 사업상 상한은 없다.

### 발행 쿼리의 선택

유니크 키와 함께 조건부 upsert를 사용하면 최초 삽입, 보류·실패 갱신, 이미 발행된 행 보존을 한 문장으로 처리한다.
`save()`도 유니크 제약·잠금·충돌 재시도를 조합하면 구현할 수 있다. 먼저 조회하고 save만 하는 방식은 두 요청이
동시에 ‘없음’을 읽는 경쟁을 해결하지 못한다. save 자체에는 ‘이미 발행된 행은 보존한다’는 조건도 없다.
현재 방식은 PostgreSQL에 의존하고 JPA 생명주기·dirty checking을 거치지 않는 단점이 있다.
native 변경 전 flush, 변경 후 영속성 컨텍스트 clear와 실제 PostgreSQL 테스트로 이를 보완한다.

1. 호출 배치가 대상 회원, 원천 이력의 완전성, 전월 집계 유무, 산식 정책을 확인한다. 전월 집계만 없으면 비교 수치를 null로 두고 발행한다.
2. 월 종료 이후에 집계한 payload, 원시 집계와 검증 메타데이터, 산식 버전, 집계 시각을 넘긴다.
3. 서비스는 응답 계약과 회원·월, KST 월 종료 시각, 필수 메타데이터를 검증한다.
4. PostgreSQL의 `INSERT ... ON CONFLICT ... WHERE status <> 'PUBLISHED'`로 발행한다.
5. 최초 발행은 true, 이미 발행된 월은 false다. 동시 호출도 한 건만 성공한다. 보류·실패 행은 완성된 결과로 발행할 수 있다.
6. 최초 발행한 회원에게만 같은 트랜잭션에서 알림을 적재한다. 커밋 후 기존 PushEventListener가 FCM 발송을 처리한다.

기존 발행본을 재시도로 덮어쓰지 않는다. 숫자 정정·재발행은 정책 확정 후 별도 경로로 추가한다.
`raw_metrics`는 비어 있지 않은 객체여야 하지만 현재 서비스가 원천 데이터의 완전성을 판정하지는 않는다.
향후 배치가 지켜야 할 선행 조건을 이 서비스의 형식 검증으로 대신해서는 안 된다.

## 발행 알림과 상세 이동

- 기존 내부 배치는 발행 직후 푸시를 요청한다. 어드민 경로는 발행 때 알림함을 적재하고 `pushAt`에 푸시를 예약한다.
  null이면 푸시 없이 발행한다. 자동 생성 설정을 켜면 매월 1일 전월 초안을 등록하지만 발행 승인은 어드민이 한다.
- 수신자는 보고서 소유자 한 명이다. 기존 NOTICE 타입으로 알림함과 푸시에 같은 제목·본문·상세 경로를 사용한다.
- 제목은 `9월 빵일지가 도착했어요` 형태다. FCM data에 `type: NOTICE`, `notificationId`, `link: /reports/monthly/2026-09`를 보낸다.
- PushDispatcher는 저장된 deepLink를 data.link에 넣는다. 알림함 목록의 link와 같은 경로가 된다.
- 프론트의 `src/services/push/index.tsx`는 data.link를 우선 사용한다. 백그라운드 탭과 콜드스타트 모두 보고서 상세를 열 수 있으며, 콜드스타트는 초기 화면 결정 후 이동한다.
- 기존 알림 수신 설정·활성 FCM 토큰 확인을 재사용한다. 수신 거부·토큰 없음은 푸시를 건너뛰고 알림함과 보고서는 남긴다.
- 알림 적재 실패 시 발행도 롤백된다. 커밋 전에는 푸시를 보내지 않는다. 재발행 호출은 새 알림/푸시 이벤트를 만들지 않는다.
- FCM 발송 결과는 기존 notification_delivery에 기록한다. FCM 실패가 발행을 되돌리지는 않는다.

기존 내부 배치의 즉시 발송 경로는 비동기 이벤트를 사용한다. 어드민 경로는 `monthly_report_push`에 예약을 저장하고
실패를 자동 재시도하며 최종 실패는 수동 재시도할 수 있다. 재발행 API 호출로 푸시를 강제 재전송하지 않는다.

마이그레이션은 보고서 테이블 생성, 캐릭터·행성 보존, 사진 UUID 추가, 기존 보고서 사진 출처 연결,
월말 원천 이력·기준 데이터·변경 트리거 설치, 일별 적재 완료 표 생성, 보고서 작업 표 생성 순서다.
운영은 기존 저장소 규칙에 따라 스키마 적용 후 애플리케이션을 배포한다. 이번 작업에서 운영 DB는 변경하지 않았다.

   전월 초안 자동 등록, 어드민 승인, 예약 푸시·실패 재시도까지 구현했다. 환경별 자동 생성 활성화와 개발 서버 실제 검증이 남아 있다.

### 확정한 방향과 남은 선택

- 저장·계획은 **해당 월에 추가했고 월말에도 남은 서로 다른 빵집**으로 확정했다. 이전 달부터 보유한 관계는 제외한다.

저장 표본은 **현재 남은 관계**이므로 월말 상태의 확정 통계가 아니다. 코스 수는 계획 빵집 수와 다른 지표다.
일반 회원의 9월 빵로그 185건 중 가게 ID 없이 직접 입력한 기록은 2건이었다.

아래는 빵력 정책 확정 전 논의한 예시이며 채택하지 않았다. 게이지 제안은 능력치당 같은 상한을 두고, 양수 활동 분포로 축별 기준량을 정한 뒤 산식 버전 동안 고정하는 방식이다.
예를 들어 `round(25 * min(1, log(1 + 활동량) / log(1 + 기준량)))`이면 기준량 10일 때
활동량 0/1/3/6/10은 점수 0/7/14/20/25가 된다. 낮은 활동량도 표시되고 많은 활동의 증가폭은 완만해진다.
25점, 기준량 10, 로그 산식은 모두 논의용 예시다. 개인별 최대 활동량을 만점으로 삼거나 매달 최고 회원에 따라
척도를 바꾸면 활동량 차이와 월별 변화를 읽기 어려우므로 제안하지 않는다.

## 검증

```sh
./gradlew test --tests 'sweetgirl.croissant.monthlyreport.*'
```

PostgreSQL 전용 테스트는 임시 스키마를 만들고 삭제한다. 테스트용 DB 연결만 제공한다.

```sh
MONTHLY_REPORT_TEST_JDBC_URL=jdbc:postgresql://127.0.0.1:포트/테스트DB \
MONTHLY_REPORT_TEST_DB_USER=테스트사용자 \
MONTHLY_REPORT_TEST_DB_PASSWORD=테스트비밀번호 \
./gradlew test -PlabTests --tests '*MonthlyReportRepositoryTest'
```

계약·HTTP 테스트는 본인 인증, 월 형식, 누락/미집계/0, 합계 오류, 다른 회원 payload, 삭제 사진,
404/500/503 구분을 확인한다. PostgreSQL 테스트는 실제 마이그레이션, JSONB 저장, 회원·월 분리,
동시 발행, 재시도 보존, 실패 후 발행, FK/상태 제약과 사진 소유권을 확인한다.
목록의 회원·상태 필터, 최신순·페이지 분리, 빈 목록, 커밋 후 이벤트와 롤백 시 알림 취소도 검증한다.
푸시 테스트는 FCM을 모의 객체로 대체해 data.link와 수신 거부를 확인한다. 실제 기기 발송은 수행하지 않는다.
JPA 매핑을 실제 PostgreSQL 스키마와 validate하며, 캐릭터 선택·행성 진행도·카탈로그 이름 변경 후 재조회,
발행 재시도, JSON과 열 불일치 거절, 기존 발행본의 스냅샷 열 백필을 검증한다.


## 월말 원천 이력 저장

`V20261005222049__create_monthly_report_source_history.sql`은 원본 테이블의 현재 상태를 기준 이력으로 적재하고
INSERT/UPDATE/DELETE 트리거를 설치한다. 원본 변경과 이력은 같은 트랜잭션에서 함께 커밋하거나 롤백한다.
이력 실패를 무시하지 않는다. 운영 DB에 이 마이그레이션을 적용하는 작업은 아직 수행하지 않았다.

- 대상: 빵로그·태그·사진 식별 정보, 저장 빵집, 직접 계획, 코스·코스 빵집 관계.
- 최고였던 빵 목록 변경, 메뉴 분류 변경·재분류도 태그/기록 이력으로 남긴다.
- 파일 키, 사진 파일, 닉네임, 메모는 복제하지 않는다. 보고서 사진은 원본 기록 ID·사진 UUID로 현재 상태를 확인한다.
- 게스트 이관처럼 소유자가 바뀌면 새 소유자 버전을 기록한다. 직접 계획의 복합키가 바뀌면 이전 키의 삭제 표식도 남긴다.
- `monthly_report_source_history`는 source_type/source_key별 변경 시각과 JSONB 상태를 갖는다. 삭제는 payload null 표식이다.
- 변경 시각은 DB 관측 시각을 KST timestamp로 저장한다. 같은 시각의 버전은 id로 순서를 정한다.
  트랜잭션 커밋 시각을 기록하는 방식은 아니므로 월 경계를 걸친 긴 트랜잭션의 변경은 각 문장의 관측 시각으로 판단한다.
- `MonthlyReportSourceHistory` Entity와 JpaRepository로 읽는다. 최신 버전 판정에는 다른 소유자의 버전·삭제 표식도 포함한다.
  이를 빼면 이관·삭제 전 상태가 다시 나타날 수 있다. 자식은 월말 당시 부모의 소유권으로 범위를 정한다.
- `MonthlyReportSourceReader`는 월말 이전 마지막 버전을 읽어 당시 기록·태그·분류·관계를 조립한다.
  원본 테이블의 현재 상태로 과거 내용을 추정하지 않는다.
  별도 REPEATABLE_READ 읽기 트랜잭션으로 여러 원천 조회 사이의 일관성을 유지한다.
- `monthly_report_history_coverage.covered_from` 이전에 끝난 월은 원천 이력으로 복원하지 않는다.
  마이그레이션 전에 사라진 데이터는 백필할 수 없다. 이미 발행된 보고서는 원천 조회 없이 보존한다.

생성 서비스는 원천을 한 번 읽고 기록·빵·저장·계획·코스를 같은 상태로 계산한다.
이력 수집 시작 시각과 각 집계 버전을 raw_metrics에 남긴다. 원천 읽기를 마친 뒤 발행 서비스가
보고서와 알림을 같은 쓰기 트랜잭션에서 저장한다. 동네도 같은 원천 스냅샷에서 계산하고,
둘러본 빵집은 적재 완료를 확인한 뒤 조회 신호에서 계산한다. 세계관 값은 아직 초안에서 받으며 빵력·유형은 실제 집계로 계산한다.

마이그레이션은 원본 쓰기를 잠깐 잠그고 기준 적재와 트리거 설치를 같은 트랜잭션에서 수행해야 한다.
기존 운영 규칙대로 스키마를 먼저 적용하고 애플리케이션을 배포한다. 이력 트리거를 비활성화하거나 원본을 TRUNCATE하는
별도 운영 작업은 지원 이력의 연속성을 깨뜨리므로 이력 정책과 함께 검토해야 한다.


## 어드민 계층과 회귀 검증

어드민 생성·승인·재시도는 `MonthlyReportAdminCommandService`, 조회는 `MonthlyReportAdminQueryService`가 담당한다. 이미지와 운영 현황도 Command/Query 서비스를 분리한다. Controller는 전용 record 응답만 반환하며 기존 JSON 필드명은 유지한다. S3 업로드 URL 발급·파일 확인은 `MonthlyReportAssetUploadService`, DB 등록은 `MonthlyReportAssetCommandService`로 나눈다.

`.github/workflows/monthly-report-tests.yml`은 dev/main 대상 PR마다 격리 PostgreSQL에서 월간 보고서 전체 테스트와 알림·사진 수정·적재 회귀 테스트를 실행한다. `-PlabTests`를 지정하여 실제 Flyway 마이그레이션, 동시 실행, 처리권 회수, 감사 시각 테스트도 포함한다. 실제 SecurityConfig와 관리자 API 키 필터를 적용한 MVC 테스트에서 조회·발행·재시도의 인증 실패와 요청 검증을 확인한다. FCM과 S3는 모의 객체를 사용하며 실제 발송·업로드는 하지 않는다.
