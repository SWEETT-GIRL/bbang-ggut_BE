# 실제 취향 프로필과 코스 맥락을 포함한 로컬 개선

2026-10-12 · `feat/742-polygon-course-lab` · 기준 `origin/dev@7b6e651d` · 운영 미반영

**실제 로컬 프로필 18개를 사용한 324개 상황에서 개선안은 모두 4곳/6곳을 채우며 거리·제외 조건을 지켰다.** 취향 점수 우선 경로에 가까운 순서의 경로와 조건을 만족하는 기존 경로를 추가로 비교했다. 전 단계의 합성 실험과 분리해 해석한다.

## 이번에 바꾼 로직

1. 도시 전체의 모든 출발점에서 점수 우선 경로를 만든다(D_TIGHT).
2. 같은 출발점에서 가까운 순서의 경로도 만든다. 점수만 먼저 고르면 남은 거리 예산으로 좋은 조합을 못 만드는 경우를 보완한다.
3. 기존 방식의 코스가 같은 도시·제외·구간·총거리 조건을 만족하면 비교 후보에 포함한다.
4. 요청 가게 수 → 공통 종합 점수 합 → 총거리 순으로 선택한다(D_HYBRID). 동일 조건 안에서 기존에 찾은 더 좋은 코스를 버리지 않는다.
5. 이미 담은 가게를 가정한 상황에서는 해당 가게를 제외하고 **그 가게에서 첫 추천까지의 거리도** 구간·총거리 제한에 포함한다.
6. 가까운 가게의 순서를 좌표 스냅샷마다 미리 준비한다. 같은 거리라면 요청의 점수 정렬 순서를 적용한다. 제외된 가게와 이미 고른 가게는 건너뛴다.

여전히 전역 최적화가 아닌 여러 출발점의 탐욕 탐색이다. 새 로직은 랩 코드에만 있으며 운영 API가 호출하지 않는다.

## 입력과 비교군

- 취향 축 없음 / 취향 축만 있음 / 축과 빵 종류 선호 있음의 3층에서 각 6개, 총 18개 로컬 프로필을 선택했다.
- 시범 도시 방문 기록이 많은 프로필을 먼저 고르고 동점은 회원 ID 순으로 정했다. **대표성 있는 무작위 표본이 아니며 QA 계정을 따로 제외하지 않았다.**
- 실제 `TasteQuery.of`와 후보 저장소를 사용해 태그·종류 필터와 방문 기록 제외를 적용했다. AXIS 기본 설정이다. 기록 제외가 실제 발생할 수 있는 도시·프로필 상황은 전체 324건 중 78건이었다.
- 18개 프로필 × 3개 도시 × 4/6곳 요청 × 3개 상황 = 324건. 비교군 3개로 총 972개 코스 결과다.
- FRESH: 빈 코스의 최초 추천. CONTROL은 기존 원·상위 15·최근접 연결이다.
- ADDED_STORE: 현재 원 안의 최상위 미방문 가게를 사용자가 담았다고 가정한다. 실제 저장된 코스의 재현이 아니다. CONTROL은 현행 알고리즘에 해당 가게 제외만 적용한다.
- RETRY_FROZEN: 최초 HYBRID의 첫 가게를 중심으로 1,200m 범위를 고정한다. 모든 비교군의 최초 노출 합집합을 공통 제외한다. **이 상황의 CONTROL은 같은 새 범위에서 기존 top-15/최근접 함수를 실행한 대조군이며 운영 RETRY API가 아니다.**
- 총 직선거리 실험 상한은 4곳 1,500m, 6곳 2,500m. 담은 가게가 있을 때 첫 연결도 포함한다. 도보 거리·시간은 아니다.
- 세종은 동/읍 칩 의미를 보존하기 위해 이번 도시 알고리즘 비교에서 제외했다.

## 결과

각 행은 54건이며 모든 비교군이 54/54개 코스를 완성했다. 아래 점수는 원래 프로필의 공통 종합 점수 평균이다. 취향 축이 없는 경우도 포함하고, 중립 점수로 폴백해 선택한 경우에도 비교에는 원래 프로필을 사용했다.

| 상황 | 요청 | CONTROL 점수 | 기존 D_TIGHT 점수 | D_HYBRID 점수 | D_HYBRID 평균 총거리 |
|---|---:|---:|---:|---:|---:|
| 최초 추천 | 4곳 | 1.020 | 1.081 | 1.081 | 1,209m |
| 최초 추천 | 6곳 | 1.005 | 1.048 | 1.051 | 2,181m |
| 한 가게 담음 | 4곳 | 0.988 | 0.990 | 0.994 | 1,344m |
| 한 가게 담음 | 6곳 | 0.980 | 0.964 | 0.978 | 2,263m |
| 같은 범위 재추천 모의 | 4곳 | 0.889 | 0.958 | 0.959 | 1,141m |
| 같은 범위 재추천 모의 | 6곳 | 0.850 | 0.886 | 0.889 | 1,971m |

D_HYBRID는 D_TIGHT보다 **21건에서 종합 점수가 높고 303건은 같았다. 하락은 0건**이다. 동일 점수라도 경로가 더 짧을 수 있으며, 이전 후보를 함께 비교하기 때문에 이 보존은 알고리즘의 구조적 성질이다. 실제 만족도 개선이나 통계적 유의성을 뜻하지 않는다.

최초 4곳 추천은 기존 방식 대비 53건 점수 상승·1건 동일이었다. 축이 있는 입력의 평균 코사인은 0.848 → 0.892다. 최초 6곳은 50건 상승·3건 동일·1건 하락이었다. 모든 경우가 개선된다고 주장하지 않는다.

한 가게를 담은 상황에서 CONTROL은 새 총거리 실험 상한을 4곳 22/54건, 6곳 12/54건 넘었다. 담은 가게→첫 추천 구간도 각각 3건이 1,500m를 넘었다. 현행 API는 이 연결을 제약하지 않으므로 현행 명세 위반으로 단정하지 않고 새 설계가 다루는 차이로 본다.

D_TIGHT·D_HYBRID는 총거리와 첫 연결 제한을 전부 지켰다. 담기 후 6곳에서는 D_HYBRID 점수가 CONTROL보다 평균 약 0.0019 낮다. 이동 제약을 추가하면서 생긴 교환 관계이며, 거리를 무시하는 비교군의 점수를 그대로 목표로 삼지 않는다.

## 계산 최적화

가까운 순서 경로를 만들 때 매번 전체 도시 후보를 훑는 대신, 거리순 이웃 목록을 한 번 준비해 사용하도록 바꿨다. 동거리 후보는 요청별 점수 순서로 골라 의미를 보존했다.

최적화 전후 **972개 결과의 가게 순서·점수·상황별 지표가 시간 항목을 제외하고 모두 같음**을 대조했다. 최초 추천의 HYBRID 계산 p95는 4곳 약 77ms, 6곳 약 117ms였고 최종 실행에서는 각각 약 12.8ms·26.4ms로 줄었다. 정확한 실행별 값은 [집계 JSON](polygon-member-comparison-20261012.json)의 `optimization`에 기록한다.

이 수치는 **DB 조회·거리 행렬·이웃 정렬·API·Gemini를 제외**한다. 전처리도 비용이 있으므로 운영 요청마다 도시 전체 거리 행렬을 만든다는 설계가 아니다. 운영에서는 소속 버전과 좌표 변경을 반영하는 공간 조회/캐시 비용을 별도로 검증해야 한다.
