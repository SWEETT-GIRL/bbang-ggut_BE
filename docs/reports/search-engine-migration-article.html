Part 1

월 $130짜리 검색, 하루 300건

빵긋의 가게 검색은 AWS OpenSearch Service 위에 있었다. t3.medium.search 데이터 노드 2개(2 AZ), gp3 20 GiB × 2 — 대략 월 $130~140. 개발 도메인은 이미 지웠고, 남은 운영 도메인이 인프라 비용의 큰 몫이었다.

그런데 트래픽은 작다. 운영 request_log 30일치를 세어 보면 검색 1,857건 + 자동완성 5,236건 = 하루 300~1,000건. 데이터도 크지 않다. 가게 45,444건(20 MB), 메뉴 440,579건(190 MB), 가게 구명(alias) 1,661건, 지역 사전 10,228건.

운영 기준선 (30일, e2e)건수p50p95p99
GET /stores/search1,857125ms392ms949ms
GET /stores/autocomplete5,23628ms166ms823ms

같은 VPC의 WAS에서 잰 값. 검색 e2e에는 OpenSearch 질의 외에 가게·썸네일·대표메뉴를 RDB에서 채우는 4개 쿼리(hydration)가 포함된다.

선택지는 둘이었다. (A) EC2에 오픈소스 OpenSearch를 직접 띄우거나, (B) 검색을 PostgreSQL로 옮기거나. 처음 계획은 "속도를 재서 결정"이었는데, 코드를 읽고 나니 속도로는 갈리지 않을 게 뻔했다 — 이 규모에선 둘 다 충분히 빠르다. 진짜 축은 기능 동등성, 재작성 비용, 운영 부담, 비용이었다.

결정을 가른 건 제품 판단이었다. 메뉴·카테고리 검색을 빼고 가게명·지역만 남긴다. 그러면 OpenSearch가 하던 일 중 무거운 부분(nested 메뉴 44만 건, inner_hits, 빵 사전 매칭)이 통째로 사라지고, 남는 건 4.5만 행짜리 이름 부분일치와 지역 조인뿐이다. 그 정도면 RDB로 충분하다.

Part 2

tsvector가 아니라 pg_bigm인 이유 — 실측으로

"PostgreSQL 전문검색 = tsvector"라는 통념부터 확인했다. 운영 가게명 45,339건에 to_tsvector('simple', name)을 걸어 보면 답이 바로 나온다.

성심당 본점             → '성심당' '본점'
쏠베이커리 양산트리마제점   → '쏠베이커리' '양산트리마제점'
콜드버터베이크샵         → '콜드버터베이크샵'

RDS에는 한국어 형태소 분석기(mecab, nori)가 없다. simple 파서는 공백으로만 자르고, 한국어 가게명은 붙여 쓰니 토큰 하나가 통째다. tsvector는 토큰의 정확·접두 일치만 하므로 중간 부분일치가 불가능하다. 게다가 가게명의 29%(13,229건)가 공백을 포함하는데 사용자는 "성심당본점"처럼 붙여 치거나 "브릭 베이글"처럼 띄워 친다.

실제 검색어tsvector 정확tsvector 접두정규화 부분일치비고
성심당본점001가게명은 "성심당 본점" — 띄어쓰기 차이로 실패
브릭 베이글001가게명 "브릭베이글" — 반대 방향도 실패

정규화 = 소문자화 + [^0-9a-z가-힣] 제거. 지금 OpenSearch가 한국어에서 실제로 의존하는 것도 이 정규화 + ngram이었다.

그래서 답은 "tsvector 대신 n-gram 부분일치"다. OpenSearch에 빗대면 tsvector ≈ text 필드(토큰 일치), pg_bigm ≈ 지금 쓰는 ngram(min_gram 2) 필드. pg_bigm은 문자열을 2글자 조각으로 GIN 인덱스에 넣어 LIKE '%몽심%'이 인덱스를 타게 하는 확장으로, RDS PostgreSQL 18에서 1.2를 제공한다.

pg_bigm vs pg_trgm — 2글자 검색어가 갈랐다

형제 확장 pg_trgm(3-gram)은 코어 contrib라 어디에나 있다는 장점이 있다. 하지만 검색 로그의 상위 검색어에는 "몽심·대구·성심·수원" 같은 2글자가 많고, trgm은 3글자 미만 패턴에 인덱스를 못 쓴다. 랩 PG(운영 덤프 복제본, 45k 가게)에서 인덱스 변형별로 재 봤다.

인덱스 변형별 이름 부분일치 지연 (p50, ms — 15회, 랩 PG)

2글자 검색어에서 pg_trgm은 인덱스를 못 타 seq scan(17.9ms), pg_bigm은 0.36ms. 3글자 이상은 둘이 같다.

인덱스 없음pg_bigmpg_trgm

인덱스 크기도 bigm 3.7 MB vs trgm 7.4 MB(가게명). 이 결과로 pg_bigm으로 확정했다. 랩 머신(M-시리즈)은 운영 RDS보다 훨씬 빨라 절대값이 아닌 상대 비교로만 봐야 한다 — 같은 seq scan이 운영에선 43ms였다.

"그래도 tsvector + pg_trgm 하이브리드면 되지 않나?"

전환 중에 받은 반론이다. 요지는 "가게명·지역·카테고리를 setweight로 합친 tsvector 생성 컬럼 + GIN, 한국어 약점은 pg_trgm으로 보완, 랭킹은 ts_rank" — 일반론으로 대부분 맞고, 결론(n-gram 하이브리드)은 우리가 실측으로 도달한 지점과 같다. 갈리는 곳은 우리 사용자가 무엇을 검색하느냐에서 나온다.

스키마 — 앱 코드가 정규화를 유지하지 않게

정규화 문자열은 STORED 생성 컬럼으로 두었다. 가게를 저장하는 코드가 정규화를 알 필요가 없고, 규칙(lower + [^0-9a-z가-힣] 제거)이 DB·OpenSearch 분석기·Java 파서 세 곳에서 동일하다는 게 비교의 전제가 된다.

CREATE EXTENSION IF NOT EXISTS pg_bigm;
ALTER TABLE store
  ADD COLUMN name_normalized varchar(100)
    GENERATED ALWAYS AS (regexp_replace(lower(name), '[^0-9a-z가-힣]', '', 'g')) STORED,
  ADD COLUMN address_normalized varchar(255) GENERATED ALWAYS AS (…) STORED,
  ADD COLUMN popularity_score double precision NOT NULL DEFAULT 0;
CREATE INDEX idx_store_name_normalized_bigm   ON store USING gin (name_normalized gin_bigm_ops);
CREATE INDEX idx_store_name_normalized_prefix ON store (name_normalized text_pattern_ops);  -- 자동완성 접두
-- + address bigm, alias bigm/prefix, region alias prefix, popularity_score desc

인기도(구독수 + 전국랭킹 점수 + 조회수)는 OpenSearch 문서의 popularityScore를 store.popularity_score 컬럼으로 옮기고, 마이그레이션에서 1회 백필한 뒤 주간 배치와 어드민 수동 갱신이 집계 UPDATE 한 방으로 덮어쓴다. 랩에서 확장 생성부터 인덱스 7개·백필까지 2.35초.

쿼리 — 후보 → 점수 → 정렬

SQL은 세 단으로 짠다. 후보는 조건별로 인덱스를 탈 수 있는 단순 SELECT를 UNION/INTERSECT로 합쳐 뽑는다. name LIKE … OR EXISTS(alias …)처럼 한 덩어리로 쓰면 인덱스를 못 타고 14ms seq scan이 되는 걸 랩에서 확인했기 때문이다.

케이스예후보 집합
지역 + 이름"망원 브릭", "서울 테디뵈르하우스"지역 매핑 가게 ∩ 이름토큰마다 (name ∪ alias 부분일치)
지역만"성수동", "대구"지역 매핑 가게 ∪ 검색어 전체 이름 부분일치
이름만"브릭베이글", "우드 앤 브릭"이름토큰마다 ∩ (name ∪ alias)
폴백 A (기존)"한남에그타르트"붙여 쓴 토큰을 분해해 재파싱 후 재검색
폴백 B (신규)"천안시 서북구"사전에 없는 지역어는 1차 0건일 때 address_normalized 부분일치

랭킹은 OpenSearch의 function_score(multiply·sum)와 같은 꼴을 설명 가능한 계단으로 옮겼다. 파라미터는 전부 바인드, 사용자 입력이 SQL 문자열에 들어가는 곳은 없다.

score = (greatest(name_score, alias_score) + region_score + address_score)
        × (1 + 0.3·ln(1 + popularity) + gauss(distance))

name_score  = 정확 100 · 접두 80 · 포함 60      -- 검색어 전체와 각 이름 토큰 중 최고 계단
alias_score = 같은 계단 × 0.75                  -- 구명(개명 전 이름)은 한 단계 낮게
region      = 40 × 매핑 weight(0.3~1.0)         -- 핫플 1.0 · 동 0.9 · 역 0.8 · 구 0.5 · 시 0.3
gauss(d)    = exp(−(max(0, d−500m))² / (2σ²)), σ: scale 3km·decay 0.5  -- OpenSearch와 동일 파라미터

거리는 PostGIS geography <->(구면 거리), 정렬은 relevance = 점수, distance = 거리 후 점수, popularity = 인기도 후 점수. 페이지는 size+1을 읽어 hasNext를 정확히 계산한다(예전 hits.size()==pageSize 추정은 마지막 페이지가 딱 맞아떨어질 때 빈 다음 페이지를 약속했다).

일부러 넣지 않은 것. OpenSearch 어댑터는 외부 시스템 장애를 빈 결과로 감싸 200을 돌려준다. PostgreSQL 엔진은 DB 예외를 삼키지 않는다 — RDB 장애는 앱 전체 장애라 숨길 이유가 없고, 숨기면 원인을 늦게 안다.

Part 4

실측이 잡아 준 것들

숫자보다 값진 건 러너가 도는 동안 튀어나온 문제들이었다. 전부 랩에서 잡혀 운영에는 가지 않는다.

  • 원거리 exp() underflow. 망원에서 대전(150 km)의 성심당을 검색하면 거리 감쇠 exp(-1700)이 되는데, PostgreSQL은 이걸 0이 아니라 오류로 낸다. 지수를 700에서 자른다.
  • 거리 계산 8배. 후보 2,714건('베이커리')에 ST_Distance(회전타원체) 18ms → geography <->(구면) 2.2ms. 오차는 원거리 0.3%로 감쇠·정렬에 무의미.
  • 구명 점수 조인. "걸린 구명을 모아 LEFT JOIN"은 행수 추정이 1로 빗나가 중첩 루프 × Materialize(2,750 × 101)로 풀렸다. 가게별 상관 서브쿼리(store_id 인덱스)로 바꿔 28 → 20ms.
  • "성심당"은 지역이었다. 검색 결과에 REGION 매칭이 섞여 나오길래 추적하니 성심당이 랜드마크 지역으로 사전에 등록돼 있었다. 두 엔진이 같은 사전을 쓰니 결과도 같았다 — 버그가 아니라 데이터.

정직하게 읽으면. 엔진 시간은 절반이지만 e2e는 10%밖에 안 줄었다. 검색 응답의 대부분은 검색이 아니라 그 뒤 RDB 조립이었다. "속도로는 갈리지 않는다"는 처음 판단이 맞았고, 이 전환의 실제 가치는 비용 0·인프라 한 덩어리 제거·설명 가능한 랭킹이다. 남은 e2e를 줄이려면 다음 과제는 엔진이 아니라 조립 쿼리다.

Part 6

운영으로 — 그리고 노드를 끄기까지

  1. PR 머지·배포, 기본 엔진은 그대로 opensearch. 부팅 시 Flyway가 마이그레이션(확장·생성 컬럼·인덱스·백필)을 적용한다. CREATE EXTENSION pg_bigm은 RDS 마스터 계정 권한 — postgis를 만든 계정이면 된다.
  2. search.engine=postgres로 바꿔 재배포. 파라미터 오버라이드는 운영에서 잠겨 있으므로 API 계약은 변하지 않는다.
  3. 1~2주 request_log p50/p95(기준선 125/392ms), search_misses, search.query{outcome} 관찰. 문제가 보이면 프로퍼티 하나로 opensearch로 되돌린다.
  4. 이상 없으면 OpenSearch 제거 PR — external/opensearch 패키지, 색인 이벤트·재색인 배치·주간 점수 배치, 의존성 — 그리고 도메인 삭제. 월 $130~140이 0이 되는 시점.

남은 리스크

  • 품질 회귀 — OS의 부스트 튜닝을 그대로 옮긴 게 아니라 다시 정의한 것이다. 겹침률과 실패 로그로 감시하고, 롤백은 프로퍼티 하나.
  • 랩 ≠ 운영 — 랩은 M-시리즈 맥, 운영은 소형 RDS. 절대값은 운영에서 다시 잰다. RDS 파라미터 random_page_cost(SSD인데 기본 4)를 1.1로 낮추면 인덱스 중첩 루프가 선택되는 것도 확인해 뒀다.
  • 테스트 인프라 — pg_bigm은 공식 이미지에 없어 SQL 검증은 랩 PG를 향한 통합 테스트(@Tag("lab"), -PlabTests)로 분리했다. CI는 단위 테스트(빌더 9·엔진 11·라우터 6 등)만 돈다.

배운 것

  • "tsvector냐 OpenSearch냐"는 잘못된 이분법이었다. 한국어 부분일치의 실제 자리는 n-gram이고, PG 안에서는 pg_bigm이 그 자리를 채운다.
  • 속도 비교는 결정의 근거가 아니라 검증이었다. 결정을 가른 건 "메뉴 검색을 뺀다"는 제품 판단이었고, 실측은 그 판단이 안전하다는 걸 보여 줬다.
  • 랩을 운영 복제본으로 만든 덕에 실험이 자유로웠고, 러너를 돌리는 동안 나온 세 가지 버그(underflow·거리·조인)가 운영 대신 랩에서 터졌다.
