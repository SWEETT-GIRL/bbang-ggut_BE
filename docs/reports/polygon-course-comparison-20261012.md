# 도시 전체 후보와 근거리 코스 로컬 비교

2026-10-12 KST · `feat/742-polygon-course-lab` · 기준 `origin/dev@7b6e651d` · 운영 미반영

**도시 전체 후보 + 여러 출발점의 코스 비교는 유망하다. 범위만 넓히고 상위 15곳을 연결하는 변경은 피해야 한다.** 총거리 제한을 둔 실험에서도 4곳 요청 102건 모두 완성됐으며, 평균 취향 코사인은 0.776에서 0.892로 높아졌다. 실제 회원 만족도가 아닌 합성 취향 입력의 오프라인 점수다.

## 비교 조건

- 공식 경계 복구 후보 `2f83cb96f1184150859238e4835df12d`, 기준표 2026-09-26. [경계 검증](region-polygon-lab-20261012.md).
- 로컬 가게 최신 갱신일 2026-09-19. 운영의 10월 커버리지와 직접 비교하지 않는다.
- 이번 소속 추출은 기존 지역 문자열로 먼저 자르지 않고 전체 적격 가게 좌표와 시범 폴리곤을 대조했다. 수원 1,015·성남 692·고양 835·세종 260개로 이전 표본과 같았고 복수 구역 매칭은 없었다.
- **코스 비교는 수원·성남·고양만** 수행했다. 세종의 기존 도장 칸은 도담동·조치원읍이므로 전체 세종으로 확대하면 사용자가 선택한 범위가 달라진다. 같은 도시 칩처럼 취급하지 않았다.
- 4축 ±0.8 조합 16개와 취향 없음 1개 = 합성 입력 17개. 3개 도시 × 17개 입력 × 제외 없음/공통 제외 있음 = 요청 수별 102건.
- 공통 제외는 `storeId % 5 == 0`인 가게를 모든 비교군에서 제외하는 결정적 실험이다. 실제 기록·저장·조회·이전 추천 이력이나 실제 RETRY 재현이 아니다. 빈 코스 기준이다.
- 요청 1·4·6곳, 비교군 4개 = 총 1,224개 결과. SQL·좌표·설정·제외 입력을 공유한다.
- 기존 `RecommendationCandidateJdbcRepository`의 실제 점수 SQL을 사용했다. AXIS 기본 설정이며 태그·종류 없는 합성 취향이다. 운영 런타임 설정이나 라벨 방식의 우월성을 검증한 것이 아니다.
- 기존 A의 후보 상한 15, 취향 후보 3곳 미만 폴백, `chainWithinHop` 함수를 재사용했다. D도 구간 상한 1,500m와 동일 점수·자격을 사용한다. 폴백 발생 시 선택 점수와 비교 점수를 혼동하지 않도록 모든 결과를 원래 합성 취향의 공통 점수로 평가했다.

| 비교군 | 방법 |
|---|---|
| A | 현재 원·지역 보조 조건 → 상위 15 → 기존 최근접 연결 |
| CITY_TOP15 | 도시 전체 → 상위 15 → 기존 최근접 연결 |
| D | 도시 전체의 모든 가게를 출발점으로 삼고, 매 단계 거리 제한 안의 점수 높은 가게를 연결. 가게 수 → 공통 점수 합 → 총거리 순으로 코스 선택 |
| D_TIGHT | D와 같되 총 직선거리 상한을 추가. 4곳 1,500m, 6곳 2,500m. 아직 채택하지 않은 실험값 |

D는 여러 출발점에서 탐욕적으로 코스를 만들며 전역 최적 경로를 보장하지 않는다. 막다른 선택을 되돌리는 탐색은 없다. 실제 운영용 후보 조회·탐색 범위 저장·API는 아직 구현하지 않았다.

취향 코사인은 축이 있는 96건만 집계한다. 거리·완성률은 102건 모두다. CITY_TOP15의 높은 점수와 짧은 거리는 **미완성 코스도 섞인 값**이므로 다른 군보다 좋다는 의미가 아니다.

4곳 D_TIGHT는 기존 원 밖 가게를 408개 선택 슬롯 중 221개에 포함했고, 서로 다른 가게 252곳을 선택했다(A 177곳). 이것은 이 입력 세트에서 실제 선택된 가게 수이며 모든 도시 가게의 노출을 보장하지 않는다. 공통 종합 점수는 A 대비 100건 상승·1건 동일·1건 하락했다. 하락 1건의 평균 점수 차이는 약 -0.0113이다.

## 속도와 검증 범위

로컬 단일 실행에서 코스 선택만의 p95는 4곳 D 약 2.3ms, D_TIGHT 약 15.1ms, 6곳 D 약 4.7ms, D_TIGHT 약 25.7ms였다. **SQL·거리 행렬 준비·네트워크·API 저장·Gemini 호출을 제외한 값**이다. JIT와 캐시의 영향을 받으며 운영 응답 속도나 SLA 근거로 쓰지 않는다. Java 러너는 평가용으로 전체 후보를 가져온다. DB 조회와 전처리를 포함한 운영 성능 검증은 남았다.

읽기 전용 repeatable-read 트랜잭션과 고정 로컬 접속을 사용하고, Docker Unix socket으로 얻은 DB system ID와 JDBC 연결 ID를 대조한다. 입력 추출과 실험 사이의 가게 개수·최신 갱신일·프로필 최신 계산일도 대조했다. 신규 도구는 운영 테이블에 쓰지 않는다.

최종 `./gradlew build`에서 포맷·Checkstyle 검사와 기본 테스트 2,360건(실패·오류 0, 건너뜀 4)을 확인했다. 별도의 랩 비교 테스트도 통과했다.

모든 결과에서 중복 가게·요청 개수 초과·1,500m 초과 구간이 없는지 검사했다. D/D_TIGHT는 도시 소속과 공통 제외 조건을 확인하고, D_TIGHT는 총거리 상한도 확인했다. 원 안 공통 가게의 점수가 기존 저장소와 동일함을 검증했다.

## 다음 구현 판단

1. **지역 소속은 폴리곤, 코스는 거리·취향으로 결정하는 방향을 유지한다.** 동 경계를 코스 제한선으로 쓰지 않는다.
2. 총거리 제한을 함께 설계한다. 실험의 1.5/2.5km는 직선거리이며 도보 경로·도로 단절·실제 소요 시간과 다르다. 확정 정책이 아니다.
3. 실제 취향·기록 제외·조회/저장 신호·이미 담은 장소가 있는 공통 입력으로 비교를 넓힌다. 합성 입력의 코사인 향상을 만족도 향상으로 표현하지 않는다.
4. 도시 scope와 선택한 지역 코스 scope를 구분해 `areaId`, `exactArea`, `nextArea`, RETRY·동일 시트 재열기의 의미를 설계한다. 기존 API 필드를 삭제하거나 이름을 바꾸지 않는다.
5. 공식 변동분과 운영 시점 데이터 대조, 신규 가게 소속 갱신, 버전·롤백, DB 쿼리와 거리 전처리 성능을 검증한 뒤 시범 적용한다.

현재는 로컬 실험 완료다. 운영용 추천 알고리즘 연결·배포·이슈 완료 처리는 하지 않았다. 브랜치별 통합 설계는 [Spec/Plan](../../.claude/planning/feat-742-polygon-course-lab.md)에 둔다.
