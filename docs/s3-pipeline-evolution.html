STAGE 1 · AS-IS

현재 구조

단일 버킷 · 서버 검증 없음 · CDN 없음 · 이미지 상태 없음

업로드 이미지 등록 흐름

sequenceDiagram participant C as 클라이언트 participant BE as Backend participant S3 as S3 단일 버킷 participant DB as PostgreSQL C->>BE: ① presigned URL 요청 (mimeType) BE-->>C: ② presigned URL + awsKey 반환 C->>S3: ③ PUT 원본 파일 직접 업로드 Note over C,S3: ⚠ 서버 검증 없음 — MIME·크기 클라이언트 선언에 의존 S3-->>C: 200 OK C->>BE: ④ POST 이미지 등록 (awsKey) BE->>DB: ⑤ INSERT imageFile (awsKey 저장) DB-->>BE: 저장 완료 BE-->>C: ⑥ 200 OK
⚠ 문제점 MIME 타입은 클라이언트 선언 값만 신뢰 — 악성 파일 업로드 가능
리사이즈 없음 → 원본 대용량 이미지를 그대로 서빙
이미지 상태 없음 → 업로드 중 이미지도 즉시 노출

조회 이미지 응답 흐름

sequenceDiagram participant C as 클라이언트 participant BE as Backend participant DB as PostgreSQL participant S3 as S3 단일 버킷 C->>BE: GET /stores/{id}/images BE->>DB: SELECT awsKey (상태 필터 없음) DB-->>BE: awsKey 목록 반환 BE-->>C: S3 직접 URL 목록 반환 Note over BE,C: https://s3.ap-northeast-2.amazonaws.com/{bucket}/{key} C->>S3: 이미지 GET (S3 직접 접근) S3-->>C: 이미지 데이터
⚠ 문제점 S3 버킷 URL이 클라이언트에 직접 노출
CDN 없음 → 매번 Origin S3에서 풀링 (레이턴시 + 비용)
상태 필터 없음 → PENDING/FAILED 이미지도 함께 반환
↓
STAGE 2 · 서버 비동기

서버 내 비동기 처리 (@Async)

staging / final 버킷 분리 · 매직바이트 검증 · Thumbnailator 리사이즈 · CloudFront CDN

업로드 이미지 등록 흐름

sequenceDiagram participant C as 클라이언트 participant BE as Backend participant ST as S3 staging participant DB as PostgreSQL participant POOL as imageProcessingExecutor
(corePool=2 · max=5 · queue=50) participant FN as S3 final C->>BE: ① presigned URL 요청 BE-->>C: ② staging presigned URL + awsKey C->>ST: ③ PUT 원본 파일 ST-->>C: 200 OK C->>BE: ④ POST 이미지 등록 (awsKey) rect rgb(219, 234, 254) Note over BE,DB: HTTP 요청 스레드 (동기) BE->>DB: ⑤ INSERT imageStatus = PENDING DB-->>BE: commit 완료 BE-->>C: ⑥ 200 즉시 반환 end rect rgb(237, 231, 255) Note over POOL,FN: @Async(imageProcessingExecutor) — 백엔드 스레드풀 BE-)POOL: ⑦ 비동기 트리거 (commit 직후) POOL->>ST: ⑧ 파일 다운로드 (S3 GetObject) ST-->>POOL: 파일 바이트 스트림 Note over POOL: USER 요청: 매직바이트 검증
ADMIN 요청: 검증 스킵 alt 검증 실패 (USER only) POOL->>ST: 원본 삭제 (DeleteObject) POOL->>DB: UPDATE imageStatus = FAILED else JPEG · PNG (리사이즈 지원) POOL->>POOL: Thumbnailator 리사이즈 (max 1280px) POOL->>FN: PutObject (동일 awsKey) POOL->>ST: 원본 삭제 (DeleteObject) POOL->>DB: UPDATE imageStatus = DONE else WebP · HEIC (리사이즈 미지원) POOL->>FN: CopyObject (동일 awsKey) POOL->>ST: 원본 삭제 (DeleteObject) POOL->>DB: UPDATE imageStatus = DONE end end
⚠ 한계 — 이 방식의 부하 지점 다운로드 부하: 백엔드 서버가 S3에서 원본 파일을 직접 내려받아 메모리에 올림 → 대용량 이미지·동시 업로드 시 힙 압박
CPU 부하: Thumbnailator 리사이즈는 CPU 집약 작업 — API 서버와 스레드풀을 공유하므로 경쟁 발생
스레드풀 고갈: queue=50 초과 시 RejectedExecutionException → 업로드 실패
스케일 아웃 비효율: 이미지 처리를 위해 API 서버 전체를 스케일 아웃해야 함

조회 이미지 응답 흐름

sequenceDiagram participant C as 클라이언트 participant BE as Backend participant DB as PostgreSQL participant CDN as CloudFront CDN participant FN as S3 final C->>BE: GET /stores/{id}/images BE->>DB: SELECT awsKey WHERE imageStatus = DONE DB-->>BE: DONE 상태 awsKey 목록 반환 Note over DB,BE: PENDING · FAILED 이미지는 응답에서 제외 BE-->>C: CDN URL 목록 반환 Note over BE,C: https://cdn.bbanggut.com/{awsKey} C->>CDN: 이미지 GET alt 캐시 히트 CDN-->>C: 즉시 이미지 응답 else 캐시 미스 CDN->>FN: Origin Fetch FN-->>CDN: 원본 파일 CDN-->>C: 이미지 응답 (엣지 캐시 저장) end
✓ 개선 포인트 CloudFront CDN 경유 → S3 버킷 URL 비노출, 엣지 캐싱으로 레이턴시 감소
imageStatus = DONE 필터 → 처리 전 이미지는 자동 은닉
↓
STAGE 3 · AWS Lambda

AWS Lambda 이벤트 처리

S3 이벤트 트리거 · 서버리스 처리 · 백엔드 부하 완전 분리 · CloudFront CDN

업로드 이미지 등록 흐름

sequenceDiagram participant C as 클라이언트 participant BE as Backend participant ST as S3 staging participant DB as PostgreSQL participant LB as AWS Lambda
(img-processor) participant FN as S3 final C->>BE: ① presigned URL 요청 BE-->>C: ② staging presigned URL + awsKey C->>ST: ③ PUT 원본 파일 Note over ST: s3:ObjectCreated:* 이벤트 발생 ST-->>C: 200 OK C->>BE: ④ POST 이미지 등록 (awsKey) rect rgb(219, 234, 254) Note over BE,DB: HTTP 요청 스레드 (동기) — 기존보다 더 가벼워짐 BE->>DB: ⑤ INSERT imageStatus = PENDING DB-->>BE: commit 완료 BE-->>C: ⑥ 200 즉시 반환 end rect rgb(209, 250, 229) Note over ST,FN: AWS Lambda — S3 이벤트 자동 트리거 · 독립 실행 환경 ST-)LB: ⑦ S3 Event Notification (PutObject) Note over LB: Lambda 자동 확장 — 동시 업로드 수만큼 병렬 실행 LB->>ST: ⑧ GetObject (awsKey) ST-->>LB: 파일 바이트 스트림 Note over LB: USER 요청: 매직바이트 검증
ADMIN 요청: 검증 스킵
(awsKey prefix 또는 S3 메타데이터로 판별) alt 검증 실패 (USER only) LB->>ST: DeleteObject LB->>BE: ⑨ PATCH /internal/images/{awsKey}/status
body: {status: "FAILED"} BE->>DB: UPDATE imageStatus = FAILED else JPEG · PNG (리사이즈 지원) LB->>LB: Sharp 리사이즈 (max 1280px)
(Node.js) 또는 Pillow (Python) LB->>FN: PutObject (동일 awsKey) LB->>ST: DeleteObject LB->>BE: ⑨ PATCH /internal/images/{awsKey}/status
body: {status: "DONE"} BE->>DB: UPDATE imageStatus = DONE else WebP · HEIC (리사이즈 미지원) LB->>FN: CopyObject (동일 awsKey) LB->>ST: DeleteObject LB->>BE: ⑨ PATCH /internal/images/{awsKey}/status
body: {status: "DONE"} BE->>DB: UPDATE imageStatus = DONE end end
✓ Lambda 방식의 이점 백엔드 부하 0: 다운로드·리사이즈 모두 Lambda가 담당 — API 서버 힙·CPU 영향 없음
자동 수평 확장: 동시 업로드 N건 → Lambda N개 병렬 실행 (기본 동시성 1000)
스레드풀 불필요: @Async / imageProcessingExecutor 설정 제거 가능
독립 배포: 리사이즈 로직 변경 시 Lambda만 재배포 → API 서버 무중단
비용 효율: 유휴 시 비용 0 (요청 수·실행 시간 기준 과금)

조회 이미지 응답 흐름

sequenceDiagram participant C as 클라이언트 participant BE as Backend participant DB as PostgreSQL participant CDN as CloudFront CDN participant FN as S3 final C->>BE: GET /stores/{id}/images BE->>DB: SELECT awsKey WHERE imageStatus = DONE DB-->>BE: DONE 상태 awsKey 목록 반환 Note over DB,BE: PENDING · FAILED 이미지는 응답에서 제외 BE-->>C: CDN URL 목록 반환 Note over BE,C: https://cdn.bbanggut.com/{awsKey} C->>CDN: 이미지 GET alt 캐시 히트 CDN-->>C: 즉시 이미지 응답 else 캐시 미스 CDN->>FN: Origin Fetch (S3 final) FN-->>CDN: 원본 파일 CDN-->>C: 이미지 응답 (엣지 캐시 저장) end
✓ 조회 흐름은 Stage 2와 동일 Lambda 도입 후에도 조회 경로는 변경 없음 — CloudFront → S3 final
Lambda 처리 완료(imageStatus = DONE) 이후에만 CDN URL 노출

3단계 비교 요약

AS-IS vs 서버 비동기 vs Lambda 핵심 차이점

항목 ① AS-IS ② 서버 비동기 (@Async) ③ AWS Lambda
S3 버킷 단일 원본 그대로 저장 staging + final 처리 완료 후 이관 staging + final 동일 (Lambda가 이관)
이미지 처리 주체 없음 Backend 서버 @Async 스레드풀 AWS Lambda 서버리스·독립 환경
트리거 방식 — TransactionSynchronization
afterCommit() → @Async 호출		 S3 ObjectCreated 이벤트
→ Lambda 자동 실행
파일 다운로드 없음 Backend 서버 힙 메모리에 올림 Lambda 별도 실행 환경 (512MB~10GB)
리사이즈 라이브러리 없음 Thumbnailator (Java) Sharp (Node.js) 또는 Pillow (Python)
백엔드 부하 낮음 (처리 없음) 높음 CPU·메모리 공유, 스레드풀 경쟁 최소 PENDING 저장 + 콜백 수신만
수평 확장 — API 서버 전체 스케일 아웃 필요 Lambda 자동 확장 동시성 최대 1000
배포 독립성 — 리사이즈 로직 변경 = API 서버 재배포 Lambda만 재배포 API 서버 무중단
파일 검증 없음 매직바이트 (Backend 인메모리) 매직바이트 (Lambda 내부)
이미지 상태 없음 PENDING → DONE/FAILED PENDING → DONE/FAILED
Lambda → 콜백 API → DB
이미지 서빙 S3 직접 URL CDN 없음 CloudFront 엣지 캐싱 CloudFront 동일
비용 구조 S3 스토리지·요청 비용 EC2/ECS 고정 비용 (항상 on) 요청 수·실행 시간 과금
유휴 시 비용 0
추가 구현 필요 — @Async 설정, ThreadPoolTaskExecutor Lambda 함수, S3 이벤트 설정,
PATCH /internal/images/{awsKey}/status 내부 API
