# 월간 빵일지 어드민 연동

## 사용 흐름

이 문서는 어드민 웹에서 호출할 **백엔드 API**다. 어드민 화면은 별도로 연결해야 한다.

1. S3에 표지·유형 카드를 업로드하고 이미지 버전별로 등록한다.
2. 대상 월과 이미지 버전을 지정해 생성 작업을 등록한다.
3. 진행 상태와 회원별 오류를 확인하고, 준비된 보고서를 미리 본다.
4. 발행 API를 호출한다. 준비된 통계·캐릭터·행성·이미지를 그대로 발행한다.
5. `pushAt`을 지정했다면 해당 시각 이후 푸시 작업이 발송한다. 누르면 `/reports/monthly/YYYY-MM`으로 이동한다.

보고서 발행과 푸시 예약은 구분한다. `pushAt`이 다음 날이어도 발행 처리가 끝난 보고서는 즉시 앱에서 조회된다.
발행은 회원별로 커밋되므로 전체 회원에게 동시에 공개되는 방식은 아니다.

**9월 보고서를 10월 1일에 발행하지 못했어도 `2026-09`를 지정해 실행할 수 있다.**
다만 9월 말 상태를 복원할 원천 이력이 있어야 한다. 이력 수집 시작이 10월 1일 이후라면
현재 상태로 9월 통계를 추정하거나 0으로 채우지 않고 `MONTHLY_REPORT5032`로 중단한다.
조회 기록 적재는 기존 개인화 적재를 공유하며 완료되지 않은 날짜만 복구한다. 추천 계산을 다시 실행하지 않는다.

## 인증

모든 경로는 `/api/admin/monthly-reports`로 시작하며 `X-Admin-Key` 헤더가 필요하다.
서버의 `admin.api-key`와 비교한다. 헤더 누락·불일치는 401, 서버 키 미설정은 **로컬을 포함해 503**이다.
키는 어드민 서버에 보관하고 일반 사용자 앱이나 공개 웹 번들에 넣지 않는다.

## 이미지 업로드·등록

PNG 또는 WebP, 0바이트 초과·20MiB 이하를 사용한다. 등록 시 S3 HEAD로 존재·Content-Type·크기를 확인한다.
이미지 디코딩이나 해상도 검사는 수행하지 않는다. 앱에서 필요한 비율·여백을 맞춘 파일을 준비한다.

| 종류 | `kind` | `characterCode` | `planetCode` | `variant` |
| --- | --- | --- | --- | --- |
| 월별 표지 | `COVER` | 세계관 DB에 등록된 코드 | 빈 문자열 | `01`~`12` |
| 유형 카드 | `TYPE` | 세계관 DB에 등록된 코드 | 세계관 DB에 등록된 코드 | `explore`, `save`, `plan`, `record`, `seed` |

생성 대상 회원의 캐릭터·행성에 필요한 조합을 준비한다. 누락된 조합은 회원별 생성 실패로 표시하므로
카드를 추가 등록한 뒤 실패 회원만 재시도할 수 있다. 이미지 버전은 `v1`, `2026-09-v1` 같은 소문자·숫자·하이픈이다.

### 1. 업로드 URL 발급

`POST /assets/upload-urls`

```json
{
  "version": "v1",
  "kind": "COVER",
  "characterCode": "cat",
  "planetCode": "",
  "variant": "09",
  "contentType": "image/png"
}
```

`data`에 `imageKey`, `uploadUrl`, `headers`가 반환된다. `uploadUrl`에 파일 바이트를 PUT하고
반환된 **Content-Type과 If-None-Match 헤더를 모두** 보낸다. URL은 10분간 유효하다.
브라우저에서 직접 업로드하면 S3 CORS에 어드민 출처, PUT, 두 헤더를 허용해야 한다.

발급하는 키:

```text
monthly-reports/assets/{version}/covers/{characterCode}/{month}-{UUID}.png
monthly-reports/assets/{version}/types/{characterCode}/{planetCode}/{type}-{UUID}.webp
```

### 2. 업로드한 파일 등록

`POST /assets`에 같은 요청 값과 반환된 `imageKey`를 보낸다.
등록 결과는 `GET /assets?version=v1`로 확인한다. 응답의 `imageKey`는 CDN 전체 URL이 아닌 객체 키다.

업로드 URL은 기존 객체 덮어쓰기를 거절한다. 동일 버전·종류·캐릭터·행성·variant의 등록은 같은 키이면 멱등 처리하고,
다른 키로 바꾸려 하면 409다. 디자인 변경에는 새 버전을 사용한다. 이미 발행된 이미지 파일은 삭제·덮어쓰기하지 않는다.
직접 S3에 올릴 때도 위 경로를 지키면 등록할 수 있으며 UUID 없는 `{variant}.png`도 허용한다.
직접 S3 권한으로 파일을 덮어쓰는 행위까지 애플리케이션이 차단하지는 않으므로 버전 키를 보존해야 한다.

## 보고서 API

아래 경로 앞에 `/api/admin/monthly-reports`를 붙인다. 응답은 기존 `ApiResponse.data`를 사용한다.

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| POST | `/{month}/runs` | 작업 생성, 202 |
| GET | `/{month}/runs/{id}` | 작업 상태·회원별 상태 건수 |
| GET | `/{month}/runs/{id}/members?page=0&size=20` | 회원 ID·상태·시도 횟수·오류 코드, Slice |
| GET | `/{month}/runs/{id}/preview/{memberId}` | 생성된 보고서 미리보기, Cache-Control: no-store |
| POST | `/{month}/runs/{id}/publish` | 발행 승인, 202 |
| POST | `/{month}/runs/{id}/retry` | 실패 작업 재시도, 202 |

### 생성

`POST /2026-09/runs`

```json
{"assetVersion": "v1"}
```

KST 기준 종료된 월만 허용한다. 반환된 `id`로 진행 상태를 조회한다.
월당 작업 하나이며 같은 버전으로 중복 요청하면 기존 작업을 돌려준다. 다른 버전 요청은 409다.
이 구현에는 작업 취소·버전 교체·성공한 초안 재생성 API가 없다. 버전을 잘못 등록했다면 발행 전에 별도 정정 작업이 필요하다.

작업 상태:

- `PREPARING`: 원천 확인·누락 적재 복구·대상 회원 순회·초안 저장.
- `REVIEW`: 순회 완료. 준비된 초안을 확인할 수 있다. 실패 회원이 남아 있으면 발행 승인은 409다.
- `PUBLISHING`: 승인한 초안을 회원별 발행 중.
- `COMPLETE`: 처리 완료. 푸시 완료를 뜻하지 않는다.
- `BLOCKED`: 공통 원천 오류 또는 회원별 발행 실패. 오류 원인을 해결하고 retry를 호출한다.

회원 상태는 `PENDING`, `PREPARED`, `FAILED`, `PUBLISHED`, `SKIPPED`, `PUBLISH_FAILED`다.
발행 전에 탈퇴·회원 유형 변경 등으로 대상에서 제외되면 `SKIPPED`가 될 수 있다.
이미 발행된 회원·월은 다시 계산하거나 덮어쓰지 않는다.

### 미리보기와 보존 시점

통계는 대상 월말 기준이다. 캐릭터와 행성은 **회원별 초안 생성 시점의 현재 세계관**을 저장한다.
과거 월말의 세계관을 복원하는 기능은 아니다. 미리보기 이후 캐릭터를 변경해도 준비된 초안과 발행본은 동일하다.
세계관에 아직 진입하지 않은 회원은 기본 마스코트와 기존 행성 진행도 계산을 사용한다.

닉네임과 개인 빵 사진은 미리보기·실제 조회 모두 현재 값을 반영한다. 사진은 원본 기록 ID·사진 UUID와
같은 종류의 현재 태그를 확인하며 삭제·종류 변경 시 숨긴다. 통계 수치와 사진 출처는 다시 선택하지 않는다.

새 선택 필드 `coverImageKey`가 표지 객체 키다. `activity.artwork.imageKey`는 확정된 유형 카드 키다.
기존 발행본의 표지 키가 없으면 필드는 생략된다. **앱에서 coverImageKey를 읽어 표지를 표시하는 연동은 별도 필요하다.**

### 발행과 푸시 예약

`POST /2026-09/runs/{id}/publish`

```json
{"pushAt": "2026-10-06T01:00:00Z"}
```

예시는 한국 시간 10월 6일 오전 10시다. 최초 승인 시 미래 시각을 넣는다.
`{"pushAt": null}` 또는 `{}`이면 알림함에만 적재하고 푸시는 예약하지 않는다.
같은 pushAt으로 중복 승인하면 기존 작업을 반환하며 예약 시각을 바꾸는 요청은 409다.
최초 발행본·알림·푸시 예약을 같은 DB 트랜잭션에 저장한다. 실패하면 모두 롤백한다.

푸시는 예약 시각 이후 워커가 처리한다. 보고서 생성·발행 지연이나 서버 중단이 있으면 발송도 늦어질 수 있다.
기존 수신 설정·활성 토큰·FCM dispatcher를 사용한다. 발송 실패는 최대 5회 시도하며
실패 후 5/10/15/20분 뒤부터 재시도한다. 성공한 알림은 다시 보내지 않는다.
다만 FCM 수신 성공 직후 DB 기록 전에 프로세스가 종료되면 중복 전달될 수 있다.
FCM과 DB 사이의 원자적 커밋은 보장하지 않는다.

`COMPLETE`는 보고서 처리 완료다. 푸시 상태는 `monthly_report_push`와 `notification_delivery`에서 확인한다.
최대 횟수 이후 자동 재시도는 종료된다. 푸시 상태 조회·수동 재전송 어드민 API는 아직 없다.

### 실패 후 재시도

`POST /2026-09/runs/{id}/retry`는 body가 없다.

- `REVIEW`의 생성 실패 회원만 다시 준비한다. 성공한 초안은 유지한다.
- 원천 부족으로 `BLOCKED`라면 원천 확인부터 다시 한다. 복원 불가능한 과거 이력은 재시도로 해결되지 않는다.
- 발행 실패라면 저장된 초안을 그대로 다시 발행한다. 통계·이미지를 재계산하지 않는다.
- 이미 완료된 작업은 재시도할 수 없다. 기존 발행본의 숫자 정정·재발행 API는 제공하지 않는다.

## 저장 구조·스케줄

| 테이블 | 역할 |
| --- | --- |
| `monthly_report_asset` | 버전별 이미지 조합과 불변 키 |
| `monthly_report_run` | 월별 진행 상태·마지막 회원 ID·예약 시각 |
| `monthly_report_draft` | 회원별 미리보기 payload·원시 메타데이터·처리 상태 |
| `monthly_report_member` | 앱에서 읽는 최종 발행본 |
| `monthly_report_push` | 알림 ID별 발송 시각·재시도 상태 |

JPA Entity/Repository를 사용한다. 월별 등록은 UNIQUE+조건부 INSERT, 워커는 `FOR UPDATE SKIP LOCKED`로
중복 처리를 방지한다. 재시작 시 DB에 저장된 위치에서 계속한다. 준비된 모든 payload를 메모리에 모으지 않는다.

```properties
monthly-report.admin.poll-delay-ms=5000
monthly-report.admin.push-delay-ms=10000
```

스케줄러는 어드민이 등록·승인한 작업만 실행한다. 매월 1일 작업 자동 등록과 자동 승인은 하지 않는다.
기존 `monthly-report.batch.cron=-` 경로는 호출자가 완성 초안을 넣는 내부 배치이며 즉시 푸시 방식을 유지한다.
어드민 예약 발행에는 새 runs API를 사용한다. 운영 스케줄, S3 CORS, 운영 DB, 실제 FCM 발송은 이번 코드 작업에서 변경하지 않았다.
