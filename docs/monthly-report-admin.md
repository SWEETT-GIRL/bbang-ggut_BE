# 월간 빵일지 어드민 연동

## 사용 흐름

이 문서는 어드민 웹에서 호출할 **백엔드 API**다. 어드민 웹 PR #20의 `/monthly-reports` 화면에서 연결한다.

1. S3에 표지·유형 카드를 업로드하고 이미지 버전별로 등록한다.
2. 대상 월과 이미지 버전을 지정해 생성 작업을 등록한다.
3. 진행 상태와 회원별 오류를 확인하고, 준비된 보고서를 미리 본다.
4. 발행 API를 호출한다. 준비된 통계·캐릭터·행성·이미지를 그대로 발행한다.
5. `pushAt`을 지정했다면 해당 시각 이후 푸시 작업이 발송한다. 누르면 `/reports/monthly/YYYY-MM`으로 이동한다.

보고서 발행과 푸시 예약은 구분한다. `pushAt`이 다음 날이어도 발행 처리가 끝난 보고서는 즉시 앱에서 조회된다.
발행은 회원별로 커밋되므로 전체 회원에게 동시에 공개되는 방식은 아니다.

**9월 보고서를 10월 1일에 발행하지 못했어도 `2026-09`를 지정해 실행할 수 있다.**
이력 수집 시작이 10월 1일 이후라도 최초 발행 경로로 생성한다. 저장·계획은 기존 인터랙션과 성공한
요청 로그, 남아 있는 관계의 생성일을 합쳐 9월 말 상태를 복원한다. 코스는 남은 행의 생성·삭제일을 사용한다.
빵로그·태그는 생성 시점에 남은 데이터 중 9월 말 이전에 작성하고 9월에 섭취한 기록을 사용하므로, 수정 전 내용까지
복원하는 것은 아니다. 활동 0건 회원도 0으로 생성한다. 원천 초기화 자체가 누락된 경우는 계속 5032로 중단한다.
수정 배포 후 기존 5032 작업은 `실패 건 재시도`로 이어갈 수 있다. 이미 준비·발행한 보고서는 재계산하지 않는다.
조회 기록 적재는 기존 개인화 적재를 공유하며 완료되지 않은 날짜만 복구한다. 추천 계산을 다시 실행하지 않는다.

## 인증

모든 경로는 `/api/admin/monthly-reports`로 시작하며 `X-Admin-Key` 헤더가 필요하다.
서버의 `admin.api-key`와 비교한다. 헤더 누락·불일치는 401, 서버 키 미설정은 **로컬을 포함해 503**이다.
키는 어드민 서버에 보관하고 일반 사용자 앱이나 공개 웹 번들에 넣지 않는다.

## 이미지 업로드·등록

PNG 또는 WebP, 0바이트 초과·20MiB 이하를 사용한다. 등록 시 S3 HEAD로 존재·Content-Type·크기를 확인한다.
이미지 디코딩이나 해상도 검사는 수행하지 않는다. 앱에서 필요한 비율·여백을 맞춘 파일을 준비한다.

| 종류 | `kind` | `characterCode` | `planetCode` | `variant` |
| --- | --- | --- | --- | --- |
| 월별 표지 | `COVER` | 세계관 DB에 등록된 코드 | 빈 문자열 | `01`~`12` |
| 목록 얼굴 | `FACE` | 세계관 DB에 등록된 코드 | 빈 문자열 | `smile`, `wink`, `neutral`, `closed` |
| 유형 카드 | `TYPE` | 세계관 DB에 등록된 코드 | 세계관 DB에 등록된 코드 | `explore`, `save`, `plan`, `record`, `seed` |

생성 대상 회원의 캐릭터·행성에 필요한 조합을 준비한다. 누락된 조합은 회원별 생성 실패로 표시하므로
카드를 추가 등록한 뒤 실패 회원만 재시도할 수 있다. 이미지 버전은 `v1`, `2026-09-v1` 같은 소문자·숫자·하이픈이다.

### 커버 캐릭터 이미지 계약

커버는 제목·닉네임·배경까지 합친 카드 전체가 아니라 **표지에 배치하는 캐릭터 그림**이다. 제목과 배경은 앱에서 그린다.
캐릭터 그림의 투명 여백을 유지한 PNG/WebP를 사용하고, 앱에서는 비율을 보존해 contain으로 표시한다.
서버는 확장자·Content-Type·용량을 검사하며 픽셀 크기나 투명 여부는 검사하지 않는다.

- 선택 키: `assetVersion + COVER + characterCode + 빈 planetCode + 두 자리 월`.
- 월은 보고서 `yearMonth`의 월이다. 9월 보고서를 10월에 발행해도 `09` 그림을 선택한다.
- 캐릭터는 초안에 저장한 `character.code`를 사용한다. 현재 조회자의 선택 캐릭터로 바꾸지 않는다.
- 어드민 입력 파일명: `cat/09.png` 또는 `cat__09.png`. 서버는 UUID가 포함된 최종 S3 키를 발급한다.
- 응답: 최상위 `coverImageKey`에 CDN 상대 키를 보낸다. `character.imageKey`는 기본 정면 그림, `activity.artwork.imageKey`는 유형 카드 그림이다.
- 발행 시 저장한 이미지 키·버전을 보존한다. 동일 버전 파일을 바꾸지 않고 새 버전으로 등록한다.
- 새 초안에 필요한 커버가 등록되지 않았으면 생성 실패로 남긴다. 기존 발행본은 coverImageKey가 없을 수 있다.

```json
{
  "yearMonth": "2026-09",
  "character": {"code": "cat", "name": "냥이", "imageKey": "world/cat/front.png"},
  "coverImageKey": "monthly-reports/assets/v1/covers/cat/09-example.png"
}
```

앱은 `coverImageKey`를 보존하고 CDN 커버를 먼저 표시한다. 월별 커버 240개는 런타임에서 참조하지 않는다.
누락·실패·8초 로딩 지연 시 보고서에 저장된 같은 캐릭터의 기존 기본 정면 이미지로 폴백한다.
번들에 없는 캐릭터는 `character.imageKey`를 사용하고, 그것도 실패하면 이름과 중립 아이콘을 표시한다.
월별 원본은 업로드용으로 보관하며 앱에 월별 폴백 이미지를 포함하지 않는다. 해당 앱 수정은 로컬 커밋 상태로 배포가 필요하다.

### 어드민에서 표지·얼굴·유형 카드 등록

- 파일·폴더 선택은 `S3 업로드 → 서버의 파일 확인 → monthly_report_asset 등록`까지 완료해야 성공이다.
- 표지는 `covers/cat/09.png`, 얼굴은 `faces/cat/smile.png`, 유형 카드는 `types/cat/earth/record.png`처럼 준비한다.
  `cat__09.png`, `cat__smile.png`, `cat__earth__record.png`도 자동 인식한다. 각 파일의 종류·캐릭터·월·표정을 확인한다.
- 같은 버전의 기존 조합은 덮어쓰지 않는다. 교체할 때는 새 버전의 전체 필요한 이미지 조합을 준비한 뒤 그 버전으로 새 초안을 생성한다.
- S3 업로드만 성공하면 완료로 표시하지 않는다. 등록 실패 항목은 같은 키로 DB 등록만 재시도한다.
- 이미 S3에 직접 올린 개발 파일은 ‘이미 S3에 올린 파일 연결하기’에서 객체 키를 한 줄씩 넣는다.
  현재 버전과 맞는 경로인지 검토한 뒤 등록한다. 예: `monthly-reports/assets/v1/faces/cat/smile.png`.
  S3 파일이 없거나 형식·크기가 맞지 않으면 서버가 거절한다. S3 전체 목록을 조회하거나 다른 버킷 파일을 가져오지는 않는다.
- 새 초안은 표지·유형 카드와 함께 해당 월의 얼굴 이미지도 필수로 확인한다. 부족하면 ASSET_MISSING으로 실패하므로 등록 후 재시도한다.
- 표정은 기존 앱과 같은 캐릭터·월 계산으로 선택한다. 캐릭터 스냅샷에 `faceImageKey`를 저장하고 목록·상세 응답에 동일하게 보낸다.
  이후 등록부나 앱 환경변수가 달라져도 이미 발행한 얼굴 키는 유지된다. 이전 발행본의 필드는 없을 수 있다.
- 앱은 등록된 얼굴 키를 우선하고 이전 발행본에는 기존 얼굴 CDN 규약을 사용한다. 이미지 로딩 실패 시 기존 캐릭터 폴백을 유지한다.
- 배포 순서: `V20261006160000__allow_monthly_report_face_assets.sql`과 백엔드 → 어드민 → 앱 연동.
  이 마이그레이션은 FACE 종류 허용만 추가하며 기존 COVER/TYPE과 보고서를 수정하지 않는다.

### 1. 업로드 URL 발급

`POST /assets/upload-urls`

```json
{
  "version": "v1",
  "kind": "COVER",
  "characterCode": "cat",
  "planetCode": "",
  "variant": "09",
  "contentType": "image/png"
}
```

`data`에 `imageKey`, `uploadUrl`, `headers`가 반환된다. `uploadUrl`에 파일 바이트를 PUT하고
반환된 **Content-Type과 If-None-Match 헤더를 모두** 보낸다. URL은 10분간 유효하다.
브라우저에서 직접 업로드하면 S3 CORS에 어드민 출처, PUT, 두 헤더를 허용해야 한다.

발급하는 키:

```text
monthly-reports/assets/{version}/covers/{characterCode}/{month}-{UUID}.png
monthly-reports/assets/{version}/types/{characterCode}/{planetCode}/{type}-{UUID}.webp
```

### 2. 업로드한 파일 등록

`POST /assets`에 같은 요청 값과 반환된 `imageKey`를 보낸다.
등록 결과는 `GET /assets?version=v1`로 확인한다. 응답의 `imageKey`는 CDN 전체 URL이 아닌 객체 키다.

업로드 URL은 기존 객체 덮어쓰기를 거절한다. 동일 버전·종류·캐릭터·행성·variant의 등록은 같은 키이면 멱등 처리하고,
다른 키로 바꾸려 하면 409다. 디자인 변경에는 새 버전을 사용한다. 이미 발행된 이미지 파일은 삭제·덮어쓰기하지 않는다.
직접 S3에 올릴 때도 위 경로를 지키면 등록할 수 있으며 UUID 없는 `{variant}.png`도 허용한다.
직접 S3 권한으로 파일을 덮어쓰는 행위까지 애플리케이션이 차단하지는 않으므로 버전 키를 보존해야 한다.

## 보고서 API

아래 경로 앞에 `/api/admin/monthly-reports`를 붙인다. 응답은 기존 `ApiResponse.data`를 사용한다.

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| GET | `/{month}/runs?page=0&size=20` | 월별 생성 작업 목록, 최근 생성 순. `{content,hasNext}` |
| POST | `/{month}/runs` | 전체 작업 생성, 202 |
| POST | `/{month}/members/{memberId}/runs` | 회원 1명 작업 생성, 202 |
| GET | `/{month}/runs/{id}` | 작업 상태·회원별 상태 건수 |
| GET | `/{month}/runs/{id}/members?page=0&size=20` | 회원 ID·상태·시도 횟수·오류 코드, Slice |
| GET | `/{month}/runs/{id}/preview/{memberId}` | 생성된 보고서 미리보기, Cache-Control: no-store |
| POST | `/{month}/runs/{id}/publish` | 발행 승인, 202 |
| POST | `/{month}/runs/{id}/retry` | 생성·발행 실패 재시도, 202 |
| GET | `/{month}/runs/{id}/operations?page=0&size=20` | 발행·푸시·조회 현황 |
| POST | `/{month}/runs/{id}/members/{memberId}/push/retry` | 최종 실패 푸시만 재시도, 202 |

### 생성

`POST /2026-09/runs`

```json
{"assetVersion": "v1"}
```

KST 기준 종료된 월만 허용한다. 반환된 `id`로 진행 상태를 조회한다.
월·대상별 작업 하나이며 같은 버전으로 중복 요청하면 기존 작업을 돌려준다. 다른 버전 요청은 409다.
이 구현에는 작업 취소·버전 교체·성공한 초안 재생성 API가 없다. 버전을 잘못 등록했다면 발행 전에 별도 정정 작업이 필요하다.

작업 상태:

- `PREPARING`: 원천 확인·누락 적재 복구·대상 회원 순회·초안 저장.
- `REVIEW`: 순회 완료. 준비된 초안을 확인할 수 있다. 실패 회원이 남아 있으면 발행 승인은 409다.
- `PUBLISHING`: 승인한 초안을 회원별 발행 중.
- `COMPLETE`: 처리 완료. 푸시 완료를 뜻하지 않는다.
- `BLOCKED`: 공통 원천 오류 또는 회원별 발행 실패. 오류 원인을 해결하고 retry를 호출한다.

회원 상태는 `PENDING`, `PREPARED`, `FAILED`, `PUBLISHED`, `SKIPPED`, `PUBLISH_FAILED`다.
발행 전에 탈퇴·회원 유형 변경 등으로 대상에서 제외되면 `SKIPPED`가 될 수 있다.
이미 발행된 회원·월은 다시 계산하거나 덮어쓰지 않는다.

### 미리보기와 보존 시점

통계는 대상 월말 기준이다. 캐릭터와 행성은 **회원별 초안 생성 시점의 현재 세계관**을 저장한다.
과거 월말의 세계관을 복원하는 기능은 아니다. 미리보기 이후 캐릭터를 변경해도 준비된 초안과 발행본은 동일하다.
세계관에 아직 진입하지 않은 회원은 기본 마스코트와 기존 행성 진행도 계산을 사용한다.

닉네임과 개인 빵 사진은 미리보기·실제 조회 모두 현재 값을 반영한다. 사진은 원본 기록 ID·사진 UUID와
같은 종류의 현재 태그를 확인하며 삭제·종류 변경 시 숨긴다. 통계 수치와 사진 출처는 다시 선택하지 않는다.

새 선택 필드 `coverImageKey`가 표지 객체 키다. `activity.artwork.imageKey`는 확정된 유형 카드 키다.
기존 발행본의 표지 키가 없으면 필드는 생략된다. 앱의 CDN 커버 연동 커밋을 함께 배포해야 한다.

### 발행과 푸시 예약

`POST /2026-09/runs/{id}/publish`

```json
{"pushAt": "2026-10-06T01:00:00Z"}
```

예시는 한국 시간 10월 6일 오전 10시다. 최초 승인 시 미래 시각을 넣는다.
`{"pushAt": null}` 또는 `{}`이면 알림함에만 적재하고 푸시는 예약하지 않는다.
같은 pushAt으로 중복 승인하면 기존 작업을 반환하며 예약 시각을 바꾸는 요청은 409다.
예약 시각은 PostgreSQL과 동일하게 마이크로초 단위로 정규화한다. 그보다 작은 나노초 부분은 저장·비교 전에 버린다.
최초 발행본·알림·푸시 예약을 같은 DB 트랜잭션에 저장한다. 실패하면 모두 롤백한다.

푸시는 예약 시각 이후 워커가 처리한다. 보고서 생성·발행 지연이나 서버 중단이 있으면 발송도 늦어질 수 있다.
기존 수신 설정·활성 토큰·FCM dispatcher를 사용한다. 발송 실패는 최대 5회 시도하며
실패 후 5/10/15/20분 뒤부터 재시도한다. 성공한 알림은 다시 보내지 않는다.
다만 FCM 수신 성공 직후 DB 기록 전에 프로세스가 종료되면 중복 전달될 수 있다.
FCM과 DB 사이의 원자적 커밋은 보장하지 않는다.

`COMPLETE`는 보고서 처리 완료다. 푸시 상태는 `monthly_report_push`와 `notification_delivery`에서 확인한다.
최대 횟수 이후 자동 재시도는 종료된다. 어드민 operations API에서 확인하고 최종 실패만 수동 재시도할 수 있다.

### 실패 후 재시도

`POST /2026-09/runs/{id}/retry`는 body가 없다.

- `REVIEW`의 생성 실패 회원만 다시 준비한다. 성공한 초안은 유지한다.
- 원천 부족으로 `BLOCKED`라면 원천 확인부터 다시 한다. 복원 불가능한 과거 이력은 재시도로 해결되지 않는다.
- 발행 실패라면 저장된 초안을 그대로 다시 발행한다. 통계·이미지를 재계산하지 않는다.
- 이미 완료된 작업은 재시도할 수 없다. 기존 발행본의 숫자 정정·재발행 API는 제공하지 않는다.

## 저장 구조·스케줄

| 테이블 | 역할 |
| --- | --- |
| `monthly_report_asset` | 버전별 이미지 조합과 불변 키 |
| `monthly_report_run` | 월별 진행 상태·마지막 회원 ID·예약 시각 |
| `monthly_report_draft` | 회원별 미리보기 payload·원시 메타데이터·처리 상태 |
| `monthly_report_member` | 앱에서 읽는 최종 발행본 |
| `monthly_report_push` | 알림 ID별 발송 시각·재시도 상태·전체 시도 횟수 |
| `monthly_report_notification` | 발행본과 기존 알림 ID의 연결. 알림 내용·읽음·발송 결과는 중복 저장하지 않음 |

JPA Entity/Repository를 사용한다. 월별 등록은 UNIQUE+조건부 INSERT, 워커는 `FOR UPDATE SKIP LOCKED`로
중복 처리를 방지한다. 재시작 시 DB에 저장된 위치에서 계속한다. 준비된 모든 payload를 메모리에 모으지 않는다.

```properties
monthly-report.admin.poll-delay-ms=5000
monthly-report.admin.push-delay-ms=10000
```

자동 생성을 활성화하면 KST 기준 전월의 전체 회원 작업을 등록한다. 기본 주기는 매시 5분이므로
매월 1일 00:05에 새 전월을 등록하며, 서버가 중단됐으면 재시작 또는 다음 주기에 보완한다.
등록만 자동화하며 기존 워커는 원천과 이미지를 확인해 초안을 만든 뒤 REVIEW에서 멈춘다.
발행·알림함 등록·푸시 예약은 어드민의 명시적 승인 후 진행한다.

```properties
monthly-report.auto-preparation.enabled=false
monthly-report.auto-preparation.asset-version=
monthly-report.auto-preparation.cron=0 5 * * * *
```

- 활성화할 때 등록한 이미지 버전을 지정해야 한다. 빈 값이나 잘못된 버전이면 서버 시작 시 검증 오류가 난다.
- 동일 월 전체 작업은 DB 유일 제약으로 하나만 유지한다. 수동 생성·여러 서버·재시작이 겹쳐도 중복 작업을 만들지 않는다.
- 먼저 생성된 작업의 이미지 버전과 상태를 유지한다. 이후 설정을 바꿔도 기존 초안이나 발행본을 덮어쓰지 않는다.
- 누락 이미지·월말 이력·조회 적재로 실패한 작업은 자동 등록으로 초기화하지 않는다. 어드민에서 원인을 해결한 뒤 재시도한다.
- 이전에 놓친 더 오래된 월은 어드민에서 수동 생성한다. 자동 등록은 현재 기준 전월만 대상으로 한다.
- GET 작업 목록의 page는 0 이상, size는 1~100이다. 단일 회원 테스트 작업과 전체 회원 작업을 함께 보여 준다.

CD는 저장소 variables `STAGING_MONTHLY_REPORT_AUTO_PREPARATION` / `STAGING_MONTHLY_REPORT_ASSET_VERSION`,
운영은 `PROD_MONTHLY_REPORT_AUTO_PREPARATION` / `PROD_MONTHLY_REPORT_ASSET_VERSION`을 읽는다.
자동화 기본값은 false다. 개발 서버에서 이미지·원천과 단일 회원 발행을 확인한 뒤 활성화하고 재배포한다.
이번 코드 작업에서는 실제 환경 변수나 운영 설정을 바꾸지 않았다.
기존 `monthly-report.batch.cron=-` 경로는 호출자가 완성 초안을 넣는 내부 배치이며 즉시 푸시 방식을 유지한다.
어드민 예약 발행에는 새 runs API를 사용한다. 운영 스케줄, S3 CORS, 운영 DB, 실제 FCM 발송은 이번 코드 작업에서 변경하지 않았다.

### 마이그레이션 버전 정리

이번 PR의 미배포 신규 파일 10개를 `V20261005222045`~`V20261005222054`로 정리했다.
회원별 작업은 `55`, 운영 조회·재시도와 요청 로그 조회 인덱스는 `56`으로 이어진다.
푸시 처리권은 `V20261006055838`, 관리 테이블 감사 시각은 `V20261006055839`로 추가한다.
원격 main의 기존 버전과 중복되지 않으며, 10월 2일 적용 이력 이후에도 순서대로 실행된다.
기존 운영 마이그레이션의 이름이나 SQL은 변경하지 않았다. 기존 번호로 개인 테스트 DB에 적용했다면
재생성한 격리 DB에서 검증한다. 운영 DB의 Flyway 이력을 지우거나 repair로 우회하지 않는다.


## 회원 1명 테스트 발행

`POST /api/admin/monthly-reports/{month}/members/{memberId}/runs`는 지정한 회원만 처리합니다. 전체 발행과 경로를 분리해 구버전 서버에서 단일 대상 옵션을 무시하고 전체 작업을 만들지 않도록 했습니다.

```json
{"assetVersion":"v1"}
```

- 기존 `POST /{month}/runs`는 전체 대상 회원입니다. 응답의 `targetMemberId`가 null이면 전체, 값이 있으면 해당 회원 한 명입니다.
- 월말 전 가입한 현재 일반 회원만 지정할 수 있습니다. 존재하지 않거나 대상 조건에 맞지 않으면 400입니다.
- 전체 작업과 회원별 작업은 별도 ID·초안·진행 상태를 가집니다. 같은 월·대상·버전은 기존 작업을 반환하고 버전 변경은 409입니다.
- 미리보기 → 발행 승인 → 선택한 회원에게 보고서·알림 생성 순서입니다. 테스트 발행도 실제 발행이므로 운영에서는 본인 테스트 계정을 지정합니다.
- `pushAt`은 기본값이 없습니다. null은 푸시 없음, 미래 시각을 전달하면 해당 시각 이후 발송합니다. 어드민은 한국 시간 입력을 UTC로 변환합니다.
- 이후 전체 발행과 중복되더라도 회원·월 발행본과 알림을 새로 만들거나 덮어쓰지 않습니다. 이미 발행된 회원의 미리보기는 실제 발행본을 반환합니다.
- 원천 이력·적재 완료·이미지 검증은 한 명 테스트에서도 동일합니다. 이력이 없는 과거 월을 임의 데이터로 발행하지 않습니다.

## 운영 상태의 범위

현재 진행 상태와 회원 목록 API는 보고서 생성·발행 성공/실패, 시도 횟수와 오류 코드를 제공합니다. `/retry`는 생성·발행 실패를 재시도하며, 이미 성공한 회원을 다시 발행하지 않습니다.

푸시 예약은 별도 테이블에 저장되며 10초 간격으로 처리하고 실패 시 최대 5회 시도합니다. `COMPLETE`는 보고서 발행 처리 완료이지 푸시 전달 완료가 아닙니다. FCM 접수 성공도 실제 기기 표시나 회원 열람을 보장하지 않습니다.

### 운영 조회

`GET /{month}/runs/{id}/operations?page=0&size=20`은 다음 `data`를 반환합니다. page는 0 이상, size는 1~100입니다.

- `published`: 해당 작업 대상 중 발행된 회원 수.
- `viewed`: 발행 후 본인 상세 GET 요청에 200을 받은 회원 수. 반복 조회는 1명으로 집계합니다.
- `notificationOpened`: 기존 `notification_recipient.read_at`이 있는 회원 수.
- `pushCounts`: `PENDING`, `RETRY_WAIT`, `SENT`, `SKIPPED`, `FAILED`, `NOT_SCHEDULED`, `NOT_PUBLISHED`, `UNKNOWN`별 건수.
- `members.content`: `memberId`, `publishedAt`, `firstViewedAt`, `notificationReadAt`, `pushState`, `sendAt`, `nextAttemptAt`, `completedAt`, `totalAttempts`, `manualRetries`, `errorCode`.
- `members.hasNext`: 다음 페이지 여부. 시각은 UTC ISO-8601이며 화면에서 KST로 표시합니다.

보고서 조회는 기존 `request_log`에서 회원 ID·월 경로·GET·200·발행 이후 조건을 만족하는 가장 이른 기록입니다.
관리자 미리보기, 목록, 실패 응답, 다른 회원·월은 제외합니다. 별도 열람 테이블·전송 API는 만들지 않습니다.
로그는 비동기로 저장되므로 지연·누락·삭제의 영향을 받으며, 보존 중인 로그 범위의 최초 성공 조회입니다.
현재 앱의 공통 Amplitude 이벤트는 화면 진입·이탈·체류만 기록합니다. 카드별 도달·공유 이벤트는 별도 보완이 필요합니다.

푸시 결과는 기존 `notification_delivery`, 알림 읽음은 `notification_recipient`에서 조회합니다.
`monthly_report_notification`에는 보고서와 알림을 연결하는 ID만 저장합니다. 이 연결이 없는 이전 발행본은 `UNKNOWN`으로 표시합니다.
수신 설정·활성 토큰·회원 상태로 제외된 푸시는 `SKIPPED`, 푸시를 예약하지 않은 발행본은 `NOT_SCHEDULED`입니다.

### 푸시 재시도

`POST /{month}/runs/{id}/members/{memberId}/push/retry`는 body가 없고 성공 시 202를 반환합니다. 공통 `ApiResponse` 규칙에 따라 null인 `data` 필드는 생략됩니다.
해당 작업에 속한 회원의 자동 시도 5회 최종 실패만 허용하며, 최대 5회의 새 시도를 즉시 예약합니다.
잠금 중·예약 대기·성공·발송 제외는 409입니다. 기존 성공 전달 기록이 있는 경우도 거절합니다.
보고서·알림을 재생성하지 않으며 누적 시도 횟수와 수동 재시도 횟수는 보존합니다.


## 발송·이미지 등록의 장애 처리

- 예약 푸시는 짧은 트랜잭션에서 10분간 유효한 처리권을 저장하고 커밋한 뒤 FCM을 호출한다. 발송 동안 DB 행 잠금을 유지하지 않는다. 결과 저장은 별도 트랜잭션에서 처리권 UUID가 일치할 때만 반영한다.
- 서버 중단으로 남은 처리권은 만료 후 회수한다. 다섯 번째 시도에서 중단된 경우도 최종 실패로 정리하여 수동 재시도가 가능하다.
- FCM 접수 성공이 하나라도 있어야 `SENT`다. 무효 토큰만 있으면 `SKIPPED`, 성공 없이 일시 오류가 있으면 `FAILED`로 처리한다. 이미 저장된 `SENT`는 동시 실패 결과로 덮어쓰지 않는다.
- FCM 연결 제한은 10초, 읽기·쓰기 제한은 각각 20초다. 회원별 토큰 순회는 2분이 지나면 다음 발송을 시작하지 않는다. 이미 진행 중인 SDK 요청은 해당 요청의 제한 시간을 따른다.
- FCM 접수 후 결과 저장 전에 서버가 종료되면 재시도 시 같은 푸시가 중복될 수 있다. DB 처리권만으로 외부 시스템의 정확히 한 번 발송을 보장하지는 않는다.
- S3 확인은 DB 트랜잭션 밖에서 수행하고 검증된 파일만 짧은 등록 트랜잭션에 저장한다. S3 API 전체 호출 제한은 15초, 개별 시도 제한은 5초다.
- 실패 초안 재시도는 JSON 전체를 메모리에 읽지 않고 실패 상태를 일괄 갱신한다.

관리 테이블 `monthly_report_run`, `monthly_report_draft`, `monthly_report_asset`, `monthly_report_push`의 생성·수정 시각을 저장한다. 수정 시각은 DB 트리거로 관리하여 JPA와 직접 SQL 변경을 모두 기록한다. 기존 행의 알 수 없는 과거 시각에는 마이그레이션 적용 시각을 사용한다. 기존 run의 생성 시각은 유지한다.

준비·발행·발송 실패 로그에는 작업 ID, 회원 ID, 알림 ID, 처리 단계, 예외 클래스와 발생 위치를 남긴다. 보고서 본문과 예외 메시지는 진단 로그에 넣지 않는다.


## 월간 보고서 알림 타입

새 발행은 `notification.type = MONTHLY_REPORT`, FCM `data.type = MONTHLY_REPORT`를 사용한다. 제목·본문과 `link: /reports/monthly/YYYY-MM`은 서버가 제공한다. 푸시 예약 여부와 알림 타입은 별개이며 `pushAt`이 null이면 IN_APP, 예약하면 PUSH 채널이다. 일반 알림 수신 설정을 따르고 광고 마케팅 동의를 요구하지 않는다. 월간 보고서 전용 수신 설정이나 필터 API는 이번 변경에 추가하지 않는다.

앱은 알림함에서 ‘월간 보고서’ 분류와 서버 제목·본문을 표시하고 알림함·푸시 모두 해당 월 상세로 이동한다. 링크 누락·잘못된 월이면 보고서 목록으로 이동한다. 기존 일반 NOTICE 공지의 표시와 이동은 유지한다.

기존 보고서 알림이 없다는 운영 전제에 따라 데이터 변환 마이그레이션은 추가하지 않는다. notification.type은 VARCHAR(30)이고 값 목록 CHECK 제약이 없어 전용 enum 값 추가에 스키마 변경이 필요하지 않다. 구버전 앱은 새 타입을 찜으로 표시할 수 있으므로 앱 반영을 확인한 뒤 새 타입의 발행을 시작한다.

### 목록에서 표지 미리 받기

`GET /reports/monthly/me`의 각 항목에 선택 필드 `coverImageKey`를 추가한다. 상세와 같은 발행본 키이며, 기존 발행본에 키가 없으면 null이다. 앱은 최신 항목의 이미지 파일만 CDN에서 미리 받아 메모리·디스크 캐시에 저장할 수 있다. 상세 API를 미리 호출하지 않으므로 상세 GET 기반 열람 기록에 영향을 주지 않는다. 기존 응답 필드는 유지하며 DB 마이그레이션은 필요 없다.
