## 요약

dataops가 운영 DB에 반영하는 변경(가게명·메뉴)이 **오픈서치 색인에 실리지 않는 문제**로
세 가지를 협의하고 싶습니다. ①이 가장 시급합니다 — 검수 완료된 **가게명 변경 1,661건과
메뉴 백필 ~107,000건의 반영이 이것에 걸려** 있습니다.

| # | 안건 | 요청 내용 |
|---|---|---|
| ① | **부분 재색인 수단** | storeId 목록을 받아 해당 가게를 재색인하는 수단 (기존 admin API에 있으면 재사용) |
| ② | **가게명 alias 필드** | store 문서에 구(舊) 상호 배열 필드 추가 + 검색 대상에 포함 |
| ③ | **검색 구성 확인** | 분석기·매치 방식·검색 대상 필드 (질문지 아래) |

## 배경

- dataops는 크롤 판정 결과를 **운영 DB 직접 DML**로 반영합니다 (전용 계정 `dataops_writer`,
  단일 통로 ServingWriter, 모든 쓰기는 apply_log 선기록). admin API를 경유하지 않으므로
  **앱 레이어 색인이 실행되지 않는 것을 확인**했습니다 (주기 재색인 없음도 확인).
- **실사례**: 사용자가 "맘모스베이커리"를 검색했지만 DB에 "맘모스"로 저장돼 있어 미노출.
  08-13 dataops가 네이버 상호로 반영 완료 → 현재 **DB=맘모스베이커리 / 색인=맘모스** 불일치
  상태입니다 (store 292121 — 재색인 수단이 생기면 1순위 반영 대상).
- 대기 물량: 가게명 변경 **1,661건** (1,695건 전수 검수 완료), 메뉴 추가 **~107,313건** (백필).
  메뉴명이 검색 대상이라면 메뉴 백필도 재색인이 필요합니다.

## ① 부분 재색인 수단 (시급)

**질문**
- admin API에 storeId 기준 재색인 트리거가 이미 있나요? 전체 재색인 잡(수동/주기)은요?

**요청** — 기존 수단이 없다면, 아래 중 편한 형태로 (권장순):
1. **`updated_at` 증분 재색인 잡 (일 1회)** — dataops의 모든 운영 쓰기는 `store.updated_at`·
   `menu.updated_at`을 갱신하므로, "`updated_at` > 마지막 재색인 시각" 조건의 증분 잡이면
   **dataops와의 연동 코드가 전혀 필요 없습니다.** 앱 내 변경·수동 수정도 함께 쓸려 들어가는 부수 이득
2. storeId 목록을 받는 재색인 엔드포인트 (내부/admin) — dataops가 apply_log에서 추출한 목록으로 호출
3. 전체 재색인 잡 일 1회

참고: dataops는 로컬 환경이라 VPC 내 오픈서치에 직접 쓸 네트워크 경로가 없고, 설계 원칙
(쓰기 표면 최소화)상으로도 색인 실행은 본 앱 몫으로 두는 것이 맞습니다 — 그래서 위 형태를 요청드립니다.

**규모·빈도**: 초기 1회 대량(이름 1,661곳 + 메뉴 백필 가게 ~7,000곳) + 이후 **일 1회 수준**이면
충분합니다 (검색 최신성이 분 단위일 필요 없음).

**dataops가 제공**: (2안 선택 시) 재색인 대상 storeId 목록 — apply_log(전량 쓰기 기록)에서
증분 추출해 전달합니다. 형식·채널은 편하신 대로 (파일/API/쿼리). 1안이면 제공할 것 없음.

## ② 가게명 alias 필드

이름 변경 1,661건 중 **한글→영문 변경이 상당수**입니다 (예: 헤이도우 → HEY DOUGH).
색인에 새 이름만 남으면 **구명으로 검색하던 사용자가 못 찾게 되는 회귀**가 생깁니다
(맘모스 사례의 정확히 반대 방향).

**제안**: store 문서에 `alias`(구 상호 배열) 필드를 추가하고 검색 대상 필드에 포함.
동의어 사전 방식은 권하지 않습니다 — 가게별 쌍을 전역 사전에 넣으면 사전이 가게 수만큼
자라고, 전역 적용이라 무관한 상호에도 발동하며, 갱신마다 리로드 부담이 있습니다.

**dataops가 제공**: (storeId, 구명 목록) — apply_log의 변경 전 값에서 추출.

**타이밍**: ①과 같은 작업 사이클이면 이상적이지만, 늦어져도 됩니다. 그 경우 한→영 변경 건만
승인 보류하고 나머지부터 반영하겠습니다.

## ③ 검색 구성 확인 (질문지)

alias 설계와 한→영 건 승인 판단에 필요한 입력입니다:

1. store 인덱스 **분석기** — nori 사용 여부, 사용자 사전, 복합어 분해 모드
2. 검색 쿼리 **매치 방식** — operator(AND/OR), match_phrase/prefix 여부, minimum_should_match
3. 검색 **대상 필드** — 가게명 외 메뉴명·주소 포함 여부
4. (참고용) "맘모스베이커리" 질의가 색인 "맘모스"에 안 걸린 원인 — nori라면 "맘모스+베이커리"로
   분해되어 부분 매칭됐을 것으로 예상했는데 안 된 이유 (AND 매치? 분석기 구성?)
