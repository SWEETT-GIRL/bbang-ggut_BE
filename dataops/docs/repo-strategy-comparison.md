# 레포 전략 비교 — 분리 레포 유지 vs 본 앱 BE 멀티모듈

> 작성 2026-08-01 · 결정 기록(ADR 성격)
> 관련 문서: [설계서 v2](./data-freshness-design.md) · [스펙](./data-freshness-spec.md) · [구현 계획](./data-freshness-plan.md)

## 결정 요약

**분리 레포(현행 `bbang-ggut_dataops_BE`)를 유지한다.**

데이터 최신화 시스템(설계서 v2)은 운영 DB와의 결합을 의도적으로 끊는 방향으로 설계되어 있어
멀티모듈의 핵심 이점(코드·엔티티 공유)을 스스로 포기하는 구조다. 반면 멀티모듈 전환 비용
(본 앱 모놀리스 재구성, 릴리스 사이클 결합, 규율 침식 리스크)은 고스란히 남는다.
분리 레포의 유일한 실질 약점인 **운영 스키마 드리프트 미감지**는 스타트업 스키마 대조 체크로
저비용 보완한다(§5).

---

## 1. 배경

- 데이터 최신화 시스템은 현재 별도 레포 `bbang-ggut_dataops_BE`(단일 모듈 Spring Boot 4.0.6,
  `sweetgirl.dataops`, :8090, 로컬 도커 DB :15433)에서 개발 중이다.
- 본 앱 BE는 `bbang-ggut_BE`(단일 모듈 모놀리스 `Croissant`, `sweetgirl.croissant`,
  security·OAuth·Firebase·S3·OpenSearch 포함, checkstyle + git hooks 운영)다.
- 질문: 이대로 별도 레포로 갈 것인가, 본 앱 레포를 멀티모듈로 재구성해
  `dataops` 모듈로 편입할 것인가.

## 2. 평가 기준

| 기준 | 왜 중요한가 |
|---|---|
| 설계 원칙과의 정합 | v2 원칙: 운영 스키마 불가침 · ServingWriter 단일 통로 · 운영 엔티티 비소유(JdbcTemplate) |
| 수명주기 정합 | 본 앱 = 상시 운영 서버 / dataops = 노트북 세션형 — 배포·실행 모델이 다름 |
| 본 앱 레포에 주는 영향 | 검증(피벗) 기간 동안 본 앱 코드는 동결 방침 |
| 실험·폐기 자유도 | dataops는 이미 도메인 4개를 통째로 폐기한 전력이 있는 실험적 내부 도구 |
| 변경 감지 능력 | 운영 스키마가 바뀌었을 때 dataops가 이를 언제 알아차리는가 |
| 빌드·개발 편의 | dataops 서버 기동에 필요한 빌드 무게, 의존성 표면 |

## 3. 비교표

| 비교 축 | 분리 레포 (현행) | 본 앱 BE 멀티모듈 |
|---|---|---|
| 운영 스키마와의 결합 | 논리 참조만(FK·JPA 엔티티 없음) — **설계 원칙 그대로** | `croissant` 엔티티 직접 import가 컴파일러 수준에서 열림 → ServingWriter 단일 통로·apply_log 선기록 규율이 침식되기 쉬움 |
| 수명주기 | 본 앱 릴리스와 완전 무관. 세션형 운영, 상시화 전환도 이 레포 단독 결정 | 상시 서버(본 앱)와 세션형 도구가 한 빌드·한 태그에 동거 |
| 본 앱 레포 영향 | **0** | 단일 모듈 → 멀티모듈 재구성 필요(src 이동, checkstyle·githooks·CI·Dockerfile 전면 조정) — 본 앱 동결 방침과 정면 충돌 |
| 실험·폐기 자유도 | 높음 — 폐기 이력이 본 앱 git 이력을 오염시키지 않음 | 낮음 — 실험 코드가 본 앱 리뷰·이력에 섞임 |
| 빌드·의존성 | 가벼움(web + jpa + flyway 수준). 단독 기동 빠름 | dataops 기동에도 모놀리스 전체 의존성 그래프 동반 |
| 스캐폴딩 공유 | ApiResponse·예외 처리 등 중복 — **이미 지불 완료된 비용**(수백 줄, 변동 거의 없음) | 공유 가능 — 그러나 얻는 것이 사실상 이것뿐 |
| 스키마 드리프트 감지 | 컴파일 타임 감지 없음 — **유일한 실질 약점** (§5로 보완) | 엔티티를 공유하면 컴파일 타임 감지 — 단, 공유하는 순간 첫 행의 결합 문제가 발생 |
| 운영 반영 부수효과(OpenSearch 색인 등) | 해결 못 함 — 프로세스 게이트(3단계 진입 전 색인 경로 확인)로 관리 | 본 앱 서비스 레이어 재사용 시 자동 해결 — 단, 이는 v2에서 폐기한 "admin API 경유"의 부활(§4) |

## 4. 멀티모듈이 이기는 유일한 시나리오 — 그리고 왜 지금은 아닌가

멀티모듈이 실질 우위를 갖는 경우는 하나다: **dataops가 본 앱의 서비스 레이어를 직접 호출해
운영 데이터를 반영하는 구조**로 갈 때. 이러면 직접 DML의 최대 리스크인
OpenSearch 색인·캐시 부수효과 우회 문제가 원천 해소된다.

그러나 이 구조는:

1. v2 전제 2("운영 반영은 admin API 경유가 아니라 직접 DML")를 코드 의존성 형태로 되돌리는 것이다.
2. 본 앱을 core/app 모듈로 분리하는 대규모 선행 리팩터링이 필요하다 — 동결 기간에 불가.
3. dataops 릴리스가 본 앱 빌드·스키마 변경에 종속된다.

설계서는 이 리스크를 이미 **3단계 게이트**("OpenSearch 색인 경로 확인 완료 전 자동 반영 미가동")로
흡수했다. 코드 결합으로 풀 문제가 아니라 확인 절차로 풀 문제다.

## 5. 분리 레포 약점 보완 — 스키마 드리프트 가드

분리 레포에서 운영 스키마 변경(본 앱 팀의 컬럼 추가·개명 등)을 컴파일 타임에 잡을 수 없다.
보완책:

- `ServingReader`/`ServingWriter`가 참조하는 운영 테이블·컬럼 목록을 코드에 상수로 명세하고,
  애플리케이션 기동 시 운영 DB `information_schema.columns`와 대조하는 **스타트업 체크**를 둔다.
- 불일치 시 기동 실패(fail-fast) — "본 앱이 스키마를 바꿨는데 dataops가 모른 채 DML"을 차단한다.
- 구현 위치: `serving/config` (구현 계획 0단계 항목).

## 6. 재검토 트리거

다음 상황이 오면 이 결정을 다시 논의한다.

| 트리거 | 재검토 방향 |
|---|---|
| OpenSearch 색인 경로 확인 결과, 주기 재색인이 없고 앱 레이어 색인뿐이라 직접 DML로는 검색 정합성을 확보할 수 없음이 판명 | 본 앱에 내부 반영 API를 추가하거나(동결 해제 후), 멀티모듈 편입 재평가 |
| dataops 상시화 이전 시 본 앱과 배포 파이프라인·인프라를 통합하게 되는 경우 | 레포 통합의 운영상 이득 재평가 |
| 본 앱 팀과 dataops가 한 팀·한 릴리스 사이클로 통합 | 멀티모듈 재평가 |
