## 1. 목표와 진행 원칙

수집한 변경을 놓치지 않고, 승인·등록·추천 적재가 중간 실패 뒤에도 일관된 상태로 복구되도록 만든다. 이후 주기 실행과 탐색 확대를 붙인다.

이 문서는 v3 전체 작업 계획이다. 현재 FR-02/08의 종류 근거 수명 부분을 구현했으며, 코드 구현·테스트와 운영 전환을 구분한다. 체크박스는 전체 단계의 수용 조건이므로 부분 코드가 추가돼도 일괄 완료 표시하지 않는다. 일회용 격리 DB의 migration/최소 publisher 테스트 외 대상 환경 migration 적용·운영 수집/배치·publish는 실행하지 않았다. 날짜/기간은 담당 인력·실행 환경이 정해지지 않아 확정하지 않으며, 각 단계의 완료 게이트로 진척을 판단한다.

- 기존 코드와 데이터는 유지하고 additive migration으로 이관한다. 초기 plan의 DB 볼륨 초기화는 실행하지 않는다.
- 기능 플래그 기본값은 신규 자동 승인 OFF, 인허가 미연결 등록 OFF다. 안전장치는 수동 승인에도 적용한다.
- 구현 PR, 격리 DB 검증, 대상 환경 dry-run, 제한된 적용, 확대를 구분한다. 운영 dry-run도 SQL 실행·잠금·부하가 있으므로 순수 검증으로 오인하지 않는다.
- 모의 객체 테스트는 상태/정책을, 실제 PostgreSQL 통합 테스트는 유일성·claim·트랜잭션·경쟁 쓰기를 검증한다. 두 DB 장애 경계는 로컬의 별도 DB 연결로 재현한다.
- 새 인프라 제품 도입 없이 시작한다. 각 배치의 입력·상태·재시도 계약부터 고정한다.

## 2. 현재 기준선과 목표의 차이

2026-09-25 검토 당시 `ProposalCommandServiceTest`, `ContentHashServiceTest`, `SnapshotCommandServiceTest`, `CandidateRegisterServiceTest`의 기존 38개 테스트는 통과했다. 이 결과는 v3 장애 시나리오의 충족을 의미하지 않는다.

작업 트리에 `localdata_fetch.py`, `naver_bakery_sweep.py`, `naver_sweep_match.py`의 미커밋 변경이 있었다. `naver_bakery_sweep.py`에는 `--deep` 페이지네이션이 포함돼 있다. 구현 시작 시 변경 내용을 다시 확인하고 보존하며, 기존 변경의 검증/커밋은 v3 구현 변경과 구분한다. 이 계획 작성 자체는 커밋 승인이 아니다.

추가 검토에서 일반음식점 일반 수집은 FULL로 바뀌었지만 월간 delta는 KEYWORD 고정이고, 기준선 치환에 범위/완료도 검사가 없음을 확인했다. 지역도 등록 worker의 지번 3토큰 관행, 별도 B 법정동 보정, BE의 H 행정동 경로가 공존한다. “전량 원본 확보”나 “법정동 규약 의도”를 전체 경로의 구현 완료로 간주하지 않는다. `/private/tmp` venv를 참조하는 재개 스크립트와 모듈 로딩 실패 로그도 확인했으며, 임시폴더 정리라는 원인 자체는 사용자 보고다.

P4-0의 수집/기준선 보호와 영속 런타임 준비는 P0 이후 병행 가능하며 탐색 확대 작업이 아니다. 검증 전에는 부분/키워드 pull로 기존 FULL 기준선을 병합하지 않는다. P1부터 정합성 수정을 시작하되, 장시간 수집의 재개는 runtime preflight와 원본 보존을 확보한 경로에서만 수행한다.

## 4. P1 — 현재 정합성 결함 우선 수정

### P1-1 승인 전에 검증·점유

대상: `ProposalCommandService`, `ChangeProposal`, proposal repository, `ServingWriter`, 테스트.

- [x] 최소 operation 식별자와 APPLYING 상태를 additive migration으로 추가한다. 제안 검증·점유·operation 연결을 로컬 트랜잭션에서 먼저 commit한다.
      → `V20260926100000__proposal_apply_occupancy.sql`(operation_id·apply_started_at·apply_outcome_reason), `ProposalApplyStateService`(REQUIRES_NEW), 부분 유니크를 PENDING·APPLYING 범위로 확장.
- [x] 비승인 상태 호출은 DML 전에 차단하고, 중복 요청은 기존 결과/진행 상태를 반환한다.

- [x] 이 단계부터 성공 결과와 FAILED/UNKNOWN을 저장·조회한다. 응답 유실/프로세스 중단의 미확정 건을 PENDING으로 되돌리지 않고 같은 대상 재실행을 차단한다. 자동 대사는 P3에서 확장한다.
      → `ProposalStatus`에 FAILED(운영 미반영 확정)·UNKNOWN(미확정) 추가. 예외 종류로 가른다: `ProposalException`(DML 전·0행)=FAILED, 그 밖=UNKNOWN. 재실행은 부분 유니크가 막는다.
- [x] 이름·전화·가격·메뉴 삭제 등 UPDATE에 예상 이전 값과 사용자 기여/활성 상태 조건을 넣고 영향 행 수를 검사한다.
      → `ServingWriter` 전 갱신에 `IS NOT DISTINCT FROM`(NULL 채우기 허용) + `store.status <> 'DELETED'` / `menu.deleted_at IS NULL`·`created_by_member_id IS NULL`. 0행은 `SERVING_VALUE_DRIFTED`.
- [ ] 운영 값 변경(CAS 충돌)과 새 근거에 의한 제안 만료를 구분한다. 새 근거 검증이 불완전하면 보류한다.
      → CAS 충돌 쪽만 했다(`VALUE_DRIFTED`). "새 근거에 의한 만료"는 저장된 최신 관측으로 재판정해야 판정되므로 P2의 근거 재생 이후로 미뤘다. 그때까지 0행은 모두 CAS 충돌로 기록되고 사람이 재판정으로 확인한다.
- [x] 개명+alias, 주소+좌표/지역 등 의미상 한 변경의 운영 SQL을 하나의 운영 트랜잭션에 묶는다.

- [x] 지역 근거가 없거나 현재 주소/좌표와 맞지 않는 위치 제안은 주소만 승인하지 않고 보류한다. P4-4 공통 resolver 완성 전에는 legacy 지역 필드 존재만으로 통과시키지 않는다. 기존 `store.region` 제안에도 현재 위치 검증을 적용한다.

- [x] 새 상태를 이해하지 못하는 구버전 승인 스크립트/서버의 쓰기를 차단하는 호환성 게이트를 만든다.
      → DB 트리거가 `PENDING → APPROVED` 직접 전이를 거부한다. 구버전 서버는 점유를 건너뛰므로 운영에 쓰기 전에 막힌다.

검증: AC-06/07 및 AC-26의 보류/rollback. 동시 승인 두 요청, 거절 제안 재승인, 원천값 회귀, 운영값 변경, 조건 불일치 0행, 두 번째 SQL 실패를 포함한다.

### P1-2 전체 재판정 삭제 제거

대상: `ReconcileService`, `ChangeProposalRepository`, proposal 생성자들.

- [x] producer/정책 버전/근거 필드를 추가한다. 기존 producer를 증거로 식별할 수 없으면 LEGACY_UNKNOWN으로 둔다.
      → `V20260926110000__proposal_producer_scope.sql`(producer·target_family·policy_version·reconcile_run_id). `target_family`는 target에서 결정되므로 그대로 채웠고, producer는 (target, source)가 생성자와 1:1인 것만 채웠다. 생성자 전수 확인 결과 6개(ReconcileService / localdata 3종 / region_recompute / store_category_propose / MatchingCommandService)라 로컬 662,160행이 전부 식별됐고 LEGACY_UNKNOWN은 0건이다.
- [x] `deleteByStatus(PENDING)` 전역 삭제를 제거하고 가게·producer·target family 단위 재판정으로 교체한다.
      → `expireOutOfGeneration(store, producer, families, survivors)`. 범위 밖(다른 가게·다른 producer·LEGACY_UNKNOWN·판정하지 않은 묶음·PENDING이 아닌 상태)은 건드리지 않는다.
- [x] 범위 전체 판정 성공 후 기존 세대를 supersede/expire한다. 새 diff가 없어진 경우도 다룬다.
      → 가게별 판정이 끝난 뒤에만 실행한다. 판정 중 예외는 정리에 닿지 못하므로 그 가게의 이전 제안이 남는다. 이번 판정에서 나온 제안 id를 모아 그 밖의 것만 SUPERSEDED로 넘긴다 — diff가 하나도 안 나온 경우도 포함된다.
- [x] APPLYING과 다른 producer의 제안을 보존한다. 같은 target 충돌은 별도 검토 근거로 남긴다.
      → 정리 범위가 PENDING뿐이라 APPLYING은 남는다. `propose`는 같은 target에 다른 producer의 진행 중 제안이 있으면 그것을 supersede하지 않고 이번 제안을 접고, 그 사실을 기존 제안의 review_note와 경고 로그에 남긴다. 결론이 같으면 충돌이 아니다.

## 5. P2 — 관측·신호·변경 감지 분리

대상: snapshot/sync/signal 도메인, `sync_worker.py`, `store_profile_batch.py`, feature 입력부.

### 이번 변경 범위 — FR-02/08 종류 근거 수명

이번에는 `menu_evidence_observation` 불변 원장과 worker 검증 메타데이터, FK 없는 legacy 소멸 근거 사본, Python 공통 분류/상태 판정, profile/feature 근거 일치 검사를 연결한다. content hash가 같은 새 관측도 원장에 남기고 request ID 재전송은 중복 확인으로 세지 않는다. legacy 근거는 승인과 독립적으로 보존하지만 독립 관측 횟수를 추정하지 않는다.

이것은 아래 P2/P5 전체 완료가 아니다. 일반 observation·attempt/lease·파생 작업 예약, 전체 공통 publisher/감사, BE 소비자·캐시·회원 재계산은 기존 게이트로 남는다. 이번 변경의 배포는 **migration → server/worker → 검증된 관측 확보 → 제한 범위 shadow 빌드·차이 검수 → 승인된 publish** 순서를 따른다. 상세 중단/복구 조건은 [전환 절차](./kind-evidence-rollout.md)에 둔다.

현재 실제 메뉴 fixture에는 전체 목록 수가 없어 `menu_complete=false`로 보류한다. identity가 맞고 양성 메뉴를 추출했다고 자동 소멸의 완전성 조건까지 확보한 것은 아니다. 운영 완전성 확인과 표본 확보는 미완료 게이트다.

### P5-2 공통 publisher

- [ ] 이번 부분 구현의 loader가 profile/feature의 같은 evidence cutoff·정책/분류기/원장 fingerprint를 검증하고 불일치·누락 시 쓰기를 막는지 확인한다. 명시적 성공 범위의 WITHOUT_LABELS 무효화만 허용하며, 이것만으로 아래 전체 publisher 항목을 완료 처리하지 않는다.
- [ ] `recommendation_feature_load.py` 공통 scoped publisher와 local publish attempt를 격리 DB에서 검증한다. local intent 선기록, 두 표 단일 commit/rollback, UNKNOWN 차단, 버전 역행 방지, 명시적 무효화 승인/DELETE 권한을 확인한다. 단위 테스트와 실제 DB 경쟁/장애 검증을 구분하고 standalone profile 적재 우회를 막는다.
- [ ] 제한 범위 build/publish를 `--store-ids`로 고정하고 publish 직전 current external ID를 재확인한다. feature 관측 시각은 frozen evidence의 `latest_observed_at`으로 대사한다. advisory lock을 우회하는 구 writer를 중지/전환한 뒤 전체 대상 스키마·권한과 writer 경쟁을 검증한다. 최소 격리 PostgreSQL 테스트 10개 통과는 [전환 절차 검증 기록](./kind-evidence-rollout.md)의 부분 근거이며 이 항목 전체 완료는 아니다.
- [ ] 프로필·라벨 upsert와 무효화 ID를 하나의 운영 DB 트랜잭션으로 반영한다.
- [ ] WITHOUT_LABELS의 feature 삭제를 허용하는 파생 데이터 전용 감사 경로를 구현한다. NULL/0 가짜 라벨은 쓰지 않는다. 원천 테이블에는 이 예외를 적용하지 않는다.
- [ ] INELIGIBLE은 확정 폐업/서비스 제외만 사용한다. 낮은 bakery_score·상권 밖·사용자별 필터 탈락은 기존 profile을 삭제하는 이유로 쓰지 않는다.
- [ ] 대상 환경 publisher 단일 실행, 오래된 run 역행 차단, before-image/산출물 checksum 저장을 구현한다.
- [ ] 비교 검증 실패는 출력 메시지로만 끝내지 않고 rollback/실패 exit로 전파한다. 건수뿐 아니라 전체 범위 fingerprint와 무효화 ID를 대사한다.
- [ ] publish commit 이후 결과 기록 실패는 UNKNOWN으로 남기고 두 표 읽기 대사로 복구한다. 더 최신 run이 있으면 재적재하지 않는다.
- [ ] 기존 두 loader는 공통 publish 진입점으로 위임하고 독립 production commit 경로를 차단한다.

- [ ] 프로필 필수/라벨 선택 join을 검증하고, 라벨 없는 가게의 fallback을 fixture로 확인한다.

- [ ] 기존 회원 취향 집계·캐시가 가게 특성 변경을 언제 반영하는지 문서화한다. 새 무효화 계약이 필요하면 BE 작업을 별도로 식별한다.

- [ ] 등록 수, 후속 작업 완료 수, 프로필 생성 수, 실제 추천 적격 수를 같은 run/cohort로 비교한다.
- [ ] P4-4의 법정동/탐색 단위 정본을 사용해 운영 store가 없는 지역도 모집단에 넣는다. 지역 코드·참조 버전·검색 문자열 대응을 기록하며 H/B 체계를 혼용하지 않는다.
- [ ] `--deep`은 AC-30 재개/완료 검증 후 한정 지역에서 평가한다. 페이지 완주율과 추가 고유 placeId 수를 분리하고 검색 완주를 그 지역 모든 가게의 수집 완료로 보고하지 않는다.
- [ ] 결과 포화 지역·미탐색 지역·검색어별로 제한된 실험을 설계한다. 격자에서도 placeId 중복 제거를 유지한다.
- [ ] 평가 지표는 추가 발견/검증 통과/추천 적격 가게 수, 호출/시간 비용, 오탐/미결정 비율이다. 등록 누적 수만으로 탐색 효율을 비교하지 않는다.

**P7 게이트:** 관련 제품 정책 확정, 이전 단계 정합성 게이트 충족, 실험 모집단과 비용/효과가 재현 가능한 보고서로 남음. 숫자가 부족하면 정책을 확대하지 않고 현재 범위를 유지한다.

## 11. 전환·배포·롤백 순서

1. 코드/데이터/파일 기준선과 복구 가능한 백업을 확보한다.
2. nullable 신규 컬럼·신규 테이블을 추가하고 기존 reader와 호환되는 상태로 배포한다.
3. 기존 값을 출처와 함께 backfill한다. UNKNOWN을 남기고 producer·관측 시각·operation 성공을 추정하지 않는다.
4. 제한된 범위에서 새 읽기/계산 경로를 shadow 실행하고 차이를 검증한다. 운영 쓰기 shadow는 실제 DML을 하지 않는다.
5. 기존 writer를 중지·배출하고 APPLYING/UNKNOWN을 대사한 뒤 새 writer로 전환한다. 두 버전의 writer를 동시에 두지 않는다.
6. 활성 참조/누락/중복을 확인한 뒤 새 유일성·NOT NULL 제약을 강화한다. 레거시 API/필드 제거는 별도 후속 변경이다.

수집 원본은 버전별로 보존하고 기준선 포인터만 검증 후 전환한다. 지역 전환은 dataops resolver뿐 아니라 BE writer/소비자 호환 배포를 함께 확인한다. 의존 작업이 끝나기 전에 기존 FULL 원본을 덮어쓰거나 H 값을 B 정본으로 선언하지 않는다.

롤백은 신규 job/승인/publish 중지 → 진행 중 결과 확인 → UNKNOWN 대사 → 필요 범위 보상 operation 순서다. DB migration을 무조건 되돌리거나 신규 증거를 삭제하지 않는다. 새 상태를 이해하지 못하는 예전 바이너리로 쓰기를 재개하지 않는다. 추천 데이터 복구는 마지막 검증 manifest/before-image로 두 표를 함께 복구하고, 더 최신 변경을 덮지 않는지 확인한다.

## 13. 전체 완료 정의

- [ ] spec AC-01~36의 테스트/실측 근거가 남는다.
- [ ] 공공데이터 대장별 모드·범위·완료도·수집 시각이 추적되고 수집 누락과 매칭 실패가 구분된다. 부분 재수집이 전량 기준선을 축소시키지 않는다.

- [ ] 추천 근거의 변화·소멸이 profile/feature까지 전달되고 반영 결과를 대사할 수 있다.
- [ ] 운영 상태와 결과 불명을 구분하고 검토 범위의 dataops/연동 배치에 지정 writer 밖 활성 쓰기 경로가 없다. BE 사용자 기여 경로는 보존하고 경쟁 쓰기를 검증한다.
- [ ] 정기 실행 중단·환경 손상을 감지하고, 쿼터 대기 후 동일 run 재개 및 원격 백업에서 미완료 상태와 근거 복구가 가능하다.
