## 1. 어떤 문제를 푸는 시스템인가

빵긋 DB의 가게 ~45,000곳은 2026년 5월 카카오 데이터 대량 임포트 이후 갱신된 적이 없었다.
가게는 폐업하고 메뉴와 가격은 바뀌고 새 가게가 열리는데, 점주 입력 채널은 없고 유저 제보는
두 달에 171건(이 속도로 전체 한 바퀴 = 40년). 그래서 **서버가 스스로 외부 소스를 주기 확인해
데이터를 최신으로 유지하는 별도 시스템**을 만들었다.

문제는 세 방향이고, 소스도 그에 맞춰 둘이다:

| 방향 | 질문 | 주 소스 |
|---|---|---|
| 갱신 | 있는 가게의 메뉴·가격·영업시간이 아직 맞나 | 네이버 플레이스 (주기 크롤) |
| 폐업 | ACTIVE 가게가 실제로 살아 있나 | 네이버 검색 부재 × **LOCALDATA 인허가** (다중 신호 교차) |
| 유입 | 우리가 모르는 가게가 있나 | **LOCALDATA 신규 인허가** → 네이버 카테고리 검증 |

## 2. 대원칙 — 운영 DB를 지키면서 고친다

본 앱과 분리된 별도 서버·별도 로컬 DB(:15433)로 돌며, 운영 DB 취급 규율:

| 원칙 | 내용 |
|---|---|
| 스키마 불가침 | 운영 DB에 테이블·컬럼을 만들지 않는다 — 최신화 상태는 전부 로컬 DB에 |
| 쓰기는 단 한 곳 | 운영 DML 은 `ServingWriter` 클래스에만 존재. DB 계정(`dataops_writer`)도 store·menu INSERT/UPDATE 등 최소 표면만 (DELETE 는 계정 권한 자체가 없음) |
| 모든 쓰기는 기록 먼저 | 운영에 쓰기 전 `apply_log`에 전/후 값 선(先)기록 — 롤백·감사 근거. **예외 1개**: 신규 가게 INSERT 는 id 가 생성 후에야 존재하므로 "생성 직후 기록"이며, 실패 회복은 placeId 선점 확인이 담당(중복 INSERT 구조적 불가) |
| 지우지 않는다 | 폐업 처리도 물리 삭제가 아니라 soft delete (`status='DELETED'`) |
| 스키마 드리프트 가드 | 기동 시 참조 컬럼을 운영 information_schema 와 대조, 불일치면 기동 실패 |
| 계정 분리 | 분석·검증은 `dataops_reader`(SELECT 전용), 반영은 `dataops_writer`. 생성 SQL 은 `scripts/dataops_roles.sql`에 박제 — RDS 를 dump/restore 로 재생성하면 role 이 소실된다 (2026-08 실제 발생) |

## 3. 전체 구조 — 두 소스, 한 파이프라인

```
[네이버 플레이스] ──크롤(주기)──> [원본층: 스냅샷] ──diff+정책──> [판정층: proposal] ──승인/자동──> [운영 DB]
                                        ▲                                                  ServingWriter
[LOCALDATA 인허가] ─수집·매칭·검증─> 후보층 ──┬─ 폐업: change_proposal(store.status) ────────┘
     (월간 델타)                            └─ 신규: new_store_candidate → 등록 배치 → 운영 INSERT
                                                                └── 등록 직후 스냅샷 제출로 ▲ 원본층에 합류
```

### ① 수집 — 파이썬 워커들 (판정하지 않는 배달부)

- `sync_worker.py` — 주기 재동기화. 서버의 "지금 볼 차례"(`GET /api/sync-states/due`)를 물어
  네이버 페이지를 1.5초 간격으로 원본 그대로 제출. **작업 큐가 없다** — `store_sync_state.next_due_at`
  이 지난 가게 목록이 곧 작업 목록(티어: 구독·조회 상위 T0 주 2회 / 나머지 T1 주 1회 + 지터).
  노트북에서 켤 때만 도는 세션형 운영이 가능한 이유.
- `localdata_fetch.py` — 인허가 4업종(제과점·휴게음식점·일반음식점·즉석판매) pull. 운영 주기는
  증분 2종: 상태 델타(`DAT_UPDT_PNT`, 폐업 전환 감지)·신규 델타(`LCPMT_YMD`, 월 ~8.3천 건).
- `localdata_new_verify.py` — 신규 후보의 빵집 여부를 **네이버 검색 카테고리로 판별**
  (상호 키워드는 판별기가 못 된다는 게 파일럿 결론). EXIST/REVIEW/NOT_FOUND + 재개형.
- `localdata_register_worker.py` — MATCHED 후보의 플레이스 상세를 fetch 해 등록 배치 API 로 보내고,
  같은 payload 를 스냅샷으로 제출해 신규 가게를 즉시 갱신 파이프라인에 합류시킨다.

공통 규율: 재개형(중단 지점부터), 차단 시 쿨다운 자동 재개, "후보 0건"은 다음 성공 응답 후에만
기록(차단 구간의 가짜 NOT_FOUND 오염 방지). 큐 끝자락에 진짜 미등록이 몰리면 연속무응답 가드가
차단으로 오탐하므로 `--failure-limit` 로 완화 가능(캡차 가드는 유지).

### ② 원본층 — 스냅샷 (증거 보관소)

제출된 원본(`__APOLLO_STATE__` JSON 전체)은 `place_snapshot`에 그대로 쌓인다. 파서 버그가 있어도
재파싱으로 복구 가능. "바뀌었나?"는 **canonical 해시**(의미 필드만 정규화)로 판단 — 페이지 잡음
(당일 영업상태·리뷰 수 등, 실측 재방문의 97.6%가 가짜 변경)을 걸러 실제 변경(~3%)만 쌓는다.

### ③ 판정층 — diff 와 병합 정책 (머리)

변경 감지 시 파싱 결과와 운영 현재값을 필드 단위 비교(`ReconcileService`) 후 **병합 정책**(`MergePolicy`)이 처분을 정한다:

- 안전한 것(가격·신규 메뉴·영업시간·전화) → 자동 반영 후보 *(검증 기간엔 전부 승인함 경유)*
- 위험한 것(가게명=오매칭 신호, 메뉴 소멸=품절 구분 불가, 폐업, 주소) → 승인함(proposal)
- 음료 제외 필터(끝단어 방식)·**출처 우선순위 ADMIN > USER > NAVER > LOCALDATA**
  (`store_field_provenance`) — 관리자·유저 값은 크롤 값이 못 덮는다

### ④ 반영 — 승인함과 기록 (손)

`change_proposal` 승인 시 **apply_log 선기록 → 운영 DML → provenance 기록**. 대량 반영은
같은 골격의 배치 직접 경로(선점 확인·항목별 실패 격리)를 쓴다 — 매칭 반영·신규 등록이 이 패턴.

## 4. LOCALDATA 트랙 — 폐업과 유입 (2026-08 완주)

공공데이터(지방행정 인허가)를 교차 소스로 도입한 트랙. 실측 교훈 셋:

1. **업종 커버리지**: 매칭의 79%가 제과점영업 밖(커피숍·일반음식점·즉석판매) — 4업종을 다 봐야 한다
2. **상호 키워드는 판별기가 못 된다** — 빵집 여부는 네이버 카테고리로 판별
3. **인허가 폐업은 정밀도↑ 재현율↓** — 단독 신호로 행동 금지, 네이버 부재와 교차해야 한다

**폐업 방향** (완결): 매핑 45,339곳 → 검수 파이프라인(교차 중재→표본 게이트→LLM 분류→AUTO 게이트,
사람 눈검수 4건) → 고신뢰 폐업 593곳 → `change_proposal(store.status)` 승인 →
softDelete — 운영·proposal·apply_log 3자 대사 일치.

**유입 방향** (가동): 후보 15,421곳 전수 네이버 검증 → 빵집 확정 7,378 − 기존 중복 238 →
`new_store_candidate(MATCHED)` 7,140 → 등록 배치(`POST /api/candidates/register-batch`):
placeId 선점 확인(있으면 기존 가게로 귀속 — 중복 등재 방지가 등록보다 우선) → `insertStore`
(지번 기반 region 3분류, source 는 본 앱 enum 재사용 `ADMIN_REGISTERED`, 출처는 provenance
LOCALDATA) → sync_state(T1) 편입 → 스냅샷 제출로 메뉴·영업시간·인스타가 proposal 로 유입.
**등록되는 순간부터 기존 갱신 파이프라인의 일원**이 된다.

부산물: 유령 인허가 4,746곳(인허가 '영업'인데 네이버 부재 — 인허가 상태를 그대로 믿으면 안
된다는 실측 근거), 재크롤 풀 ~6,400곳(갓 오픈 미등록 등 — 몇 주 후 재검증).

## 5. 검색과의 관계 — pg_bigm 전환으로 단순해졌다

본 앱 검색이 OpenSearch → **PostgreSQL pg_bigm**(생성 컬럼 `name_normalized` + gin 인덱스)으로
전환되면서(2026-08-20 운영 배포), dataops 의 DML 이 **즉시 검색에 반영**된다. 재색인·인덱스
동기화·폐업 문서 잔류 문제가 근본 소멸 — 폐업 soft delete 는 `status='ACTIVE'` 필터로 즉시
검색 제외되고, 신규 INSERT 는 즉시 검색 노출된다.

## 7. 숫자로 보는 현재 (2026-08-21)

- 운영 가게 ~45,341 − 폐업 593 + 신규 등록 ~7,140 진행 중 → **~51,900곳** 전망 (커버리지 +16%)
- 네이버 매칭률 88.8% (매칭 트랙 반영 후) — 신규 등록분은 placeId 보유로 100%
- 운영 반영 누적: apply_log 기준 메뉴·필드·매칭·폐업·등록 전 트랙 대사 일치, 실패 0 유지
