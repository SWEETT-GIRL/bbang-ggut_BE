## 3. 남은 작업 플랜 (우선순위순)

### P1. 검수 최소화 파이프라인 — 목표: 사람 눈검수 ≤200건

전제 원칙 (**lazy review**, 2026-08-12 실측): REVIEW 8,495 = 인허가 **영업 6,556 + 폐업 1,939**.

- **REVIEW+영업 6,556 → 검수도 확정도 안 함. 단, 후보 쌍은 폐기하지 말고 REVIEW 상태로 보존.** 확정해도 가게는 그대로 ACTIVE라 행동이 안 달라진다. 기록을 지우면 상태 증분(`DAT_UPDT_PNT`)에서 그 레코드가 폐업 전환될 때 "어느 가게의 후보였는지"를 잃어 검수 트리거가 사라진다(그 가게 폐업은 네이버 트랙에만 의존하게 됨). 같은건물 오매핑 의심(주소O·유사<0.5 — 백화점·상가)이 여기 1,352건 있으나 지금 가려낼 이유 없음.
- **REVIEW+폐업 1,939 → 다중 신호 원칙상 지금 행동 가능한 건 네이버 검색 부재(2,502)와의 교집합 291건뿐**:

  | 버킷 | 건수 | 처리 |
  |---|---|---|
  | 유사 ≥0.5 | 204 | 핵심 눈검수 대상 — 두 신호(인허가 폐업 + 네이버 부재) 모두 폐업 지시 |
  | 주소O·유사<0.5 | 56 | 같은건물 오매핑 의심 — 표본 20~25건 검사 후 일괄 기각 유력 |
  | 주소X·유사<0.5 | 31 | 약신호 — 기각 유력 |

  나머지 1,648건(인허가 폐업이지만 네이버에 아직 검색됨)은 인허가 단독 신호로 행동 불가 → 이연. 아래 1번(네이버 교차 중재)이 상당수 자동 정리.

→ 실질 사람 눈검수는 291건, 버킷 표본화까지 적용하면 **~100건 안팎** (목표 ≤200 충족).

1. **네이버 교차 중재 (자동, 눈검수 0)** — ✅ 완료 (08-12, `scripts/localdata_cross_arbitrate.py` → `matching/localdata_arbitration.tsv`). 3자 대조: 인허가 전화=네이버 전화 → 승격 / 인허가 상호≈네이버 상호(sim≥0.85, 우리 DB만 다름 = 개명·법인명) → 승격 / 전화·상호 모두 불일치(sim<0.4) → 기각. **심판 자격은 네이버 트랙 AUTO 후보로 제한**(REVIEW 후보를 심판으로 쓰면 같은건물 오승격 역효과). 결과: 중재 가능 1,359건 중 **승격 588**(영업 540·폐업 48) / **기각 40**(같은건물 오매핑 — 폐업 측 16건은 거짓 폐업 신호 제거) / 보류 731. 매핑 TSV는 재생성 가능 산출물이라 수정하지 않음 — 중재 파일은 오버레이로 다운스트림이 조인. 폐업 승격 48건은 "인허가 폐업 + 네이버 생존" 신호 충돌 → 승계·재인허가 의심으로 상태 델타 감시 대상.
2. **버킷 층화 표본 게이트** — ✅ 완료 (08-12, `scripts/localdata_bucket_gate.py` 표본 추출 → `matching/bucket_gate_samples.tsv` 증거 카드 81건 → 판정 `matching/bucket_gate_judgments.jsonl`). 실측 정밀도: **A(유사≥0.5) 40% / B(주소O·유사<0.5) 36% / C(주소X·유사<0.5) 6%**.
   - **C(31건) 게이트 통과 → 일괄 기각**. O 2건도 전화일치로 찾은 동일 사업자의 *옛 주소* 레코드(2017·2020 폐업)라 현재 폐업 증거로 부적합 — 기각해도 손실 없음.
   - **A·B는 예상(~100%/~0%)과 달리 혼합 → 게이트 판정 불가.** 원인은 기계 유사도의 양방향 아티팩트: (↑가짜 고유사) 포함 보너스·지점/몰/지역 접미사 겹침("미트스팟 용산아이파크몰점"↔"제주스 용산아이파크몰점"), (↓가짜 저유사) 로마자·법인명·축약·어순 변형("피넛 수성점"↔"피넛(peanut)", "카페더꿈"↔"사단법인 꿈베이커리"). **판별자는 신호 버킷이 아니라 상호의 의미 비교** → 3번(LLM 분류)으로 이관.
   - 함정 재확인 2종: 직영 브랜드 대표번호(호두당↔식빵이맛있는집 네모, 전화일치인데 다른 매장)·백화점 한시적 팝업(기로띠 갤러리아, 본점 번호로 등록).

### P3. 4단계 운영 설계 반영 (설계서 §3.6·§7.6 갱신)

수집은 "최초 스냅샷(완료) + 증분 2종":

| 증분 | 필터 | 용도 | 규모 |
|---|---|---|---|
| 상태 델타 | `DAT_UPDT_PNT::GTE` (주기) | 매핑된 관리번호 조인 → 폐업 전환 감지. 업태 무관 | 일 수천 건 |
| 신규 델타 | `LCPMT_YMD::GTE` (월 1회) | 4업종 신규 인허가 **전량**(키워드·업태 제한 없음) → `new_store_candidate(WAITING_NAVER)` | 월 ~8.3천 건·~85콜 |

신규 판별 흐름: 프랜차이즈·명백 비대상 업태(편의점·키즈카페·극장·푸드트럭)만 사전 제외 → 키워드는 우선순위 신호로만 → **빵집 여부 최종 판별은 네이버 매칭 워커의 카테고리(베이커리·디저트·카페)** → 네이버 미등록(갓 오픈)은 `match_attempts` 재시도. 미매핑 잔여 가게 재매칭은 주소 타깃 스윕 재사용.
