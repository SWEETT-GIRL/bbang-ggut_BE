# 가게명 정합 · 검색 노출 — 확인 포인트 정리

작성: 2026-08-12 · 상태: **✅ 트랙 종결 (2026-08-14)** — 검수 1,695건 → 반영 1,661건 → alias 색인 → 재색인 → **검증 전 항목 통과** (§6). 잔여 소트랙: X 2건 재매칭, 폐업 후보 5건

## 1. 발단 사례

사용자가 **"맘모스베이커리"** 로 검색 → 운영 DB에는 **"맘모스"** 로 저장되어 있어 미노출(또는 미인식).
해당 건은 이미 검수 대기 proposal에 존재한다 — store `292121`: 운영명 "맘모스" vs 네이버명 "맘모스베이커리"
([storename-review.html](./inspection/storename-review.html)).

### 개선 방향(가설)

1. 네이버와 운영 DB의 가게명이 다르면 **네이버 공식 상호로 변경** (proposal 승인)
2. 구명(舊名)도 검색에 계속 걸리도록 **오픈서치에 둘 다 노출** (동의어 or alias)

이 문서는 위 방향을 실행하기 전에 확인해야 할 것들을 정리한다.

## 3. 확인 포인트

### A. 근본 원인 확인 — 검색 실패가 정말 "이름 차이" 때문인가 (본 앱 팀)

한국어 분석기(nori 등)를 쓴다면 질의 "맘모스베이커리"는 "맘모스"+"베이커리"로 분해되어
색인된 "맘모스"와 **매칭됐어야 한다**. 안 됐다면 이름 차이가 아니라 검색 구성이 원인일 수 있다.

확인할 것:

- [ ] store 인덱스의 **분석기** (nori 여부, 사용자 사전, 복합어 분해 모드)
- [ ] 검색 쿼리의 **매치 방식** — `operator`(AND/OR), `match_phrase`/prefix 여부, `minimum_should_match`
- [ ] 검색 **대상 필드** — 가게명 외에 무엇을 보는지 (메뉴명, 주소 등)
- [ ] 실측: 운영 오픈서치에 "맘모스베이커리" `_analyze` + 실제 검색 API 호출로 재현

> A의 결과에 따라 대응이 갈린다 — 분석기/operator 문제면 **이름을 바꿔도 다른 사례가 재발**하고,
> 검색 구성 수정이 본질 대응이다. 이름 차이가 맞으면 B~D로 진행.

### B. P-4 — 오픈서치 색인 경로 (본 앱 팀 · 기존 3단계 게이트의 우선순위 상향)

**DB에서 이름을 바꿔도 색인에 안 실리면 검색은 여전히 실패한다** — 이 사례가 P-4 확인을 앞당길 실증 근거.

1,695건 검수를 일관되게 처리하려면 기준이 먼저 필요하다.

- [ ] **원칙**: 이름 diff는 네이버 공식 상호 채택 (사용자 검색어와 일치하는 것은 네이버 쪽)
- [ ] **오매칭 예외**: 유사도 낮은 건(빨강 47)은 이름 변경이 아니라 **오매칭 신호** — 설계서 5장의

- [ ] **출처 예외**: provenance 가 ADMIN/USER 인 이름은 의도적 표기일 수 있음 — 개별 판단

- [x] **팝업 정책** (2026-08-13 확정): 디저트 팝업은 **현재 운영 중이면 서비스 포함**(제외 아님).
  운영 여부는 스냅샷 영업상태로 확인. 팝업은 한시 운영이므로 종료 감지 시 폐업 트랙으로 — 재크롤이 커버

### D. 구명 검색 보존 방식 — 동의어 사전 vs alias 필드 (본 앱 팀 협의 안건)

| 방식 | 평가 |
|---|---|
| 오픈서치 **동의어 사전** (가게별 쌍 등록) | 비권장 — 사전이 가게 수에 비례해 비대, **전역 적용**이라 무관한 가게에도 발동("맘모스" 포함 타 상호), 갱신마다 리로드/재색인 운영 부담 |
| store 문서에 **`alias` 필드** (구 상호 배열) + 검색 대상 필드에 포함 | **권장** — per-가게 별칭의 정석. 부작용 국소화, 갱신은 문서 재색인만. 단 본 앱 인덱스 매핑+검색 쿼리 수정 필요 |

- [ ] 본 앱 팀에 alias 필드 방식 제안 (동결 기간이므로 수정 가능 시점 협의)
- [ ] dataops 역할 경계: **오픈서치 직접 쓰기는 하지 않는다** (쓰기 표면 최소화 원칙 — 설계서 4.2,
  운영 DML은 `ServingWriter` 단일 통로·store/menu 한정). dataops 는 승인된 이름 변경 이력에서
  **구명 목록 추출·제공**까지 (`apply_log`/`change_proposal.old_value` 기반 — 데이터는 이미 있음)
