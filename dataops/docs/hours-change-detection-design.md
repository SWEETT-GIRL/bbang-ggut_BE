# 영업시간 변경 감지 설계안 (v3 P2 설계 과제)

작성 2026-09-27 · 상태: **구현·적용 (2026-09-27)** · 관련: [v3 계획 P2](./data-freshness-v3-plan.md) "영업시간 해시 잡음"

## 1. 문제

수집할 때마다 `ContentHashService` 가 의미 필드의 해시를 만들어 직전 해시와 비교한다. 다르면 "변경"으로 보고 스냅샷을 저장하고(건당 약 32KB), 재판정을 돌리고, `change_count` 를 올린다. 영업시간이 이 판정을 대부분 거짓으로 만든다.

**원인.** 네이버 영업시간은 오늘부터 7일을 보여 준다. 임시 일정이 있는 날(명절·임시휴무·단축영업)은 `토(9/26)` 처럼 날짜를 붙이고 **그날의 임시 값**을 담는다. 지금 해시는 날짜 라벨을 떼고 요일순으로 정렬한다(`ContentHashService.canonicalHours`). 그래서 임시 값이 그 요일의 정기 값 자리에 들어간다. 그날이 지나면 같은 요일이 정기 값으로 돌아오고, 해시가 또 바뀐다. 해시가 정기 일정이 아니라 **이번 주의 예외**를 보고 있는 것이다.

재판정은 이미 이 문제를 풀었다. `BusinessHoursParser` 는 날짜 붙은 요일을 건너뛰고, `ReconcileService.overlayHours` 는 읽힌 요일만 운영 값 위에 덮는다. 빠진 요일은 운영 값을 그대로 둔다(09-20 추석 주 표본에서 16/40곳이 요일을 잃는 제안이었던 것을 고친 결과). **해시만 이 원칙을 따르지 않는다.**

1차 표본에서 "해시에서 날짜 요일을 빼는" 단순 수정은 효과가 없었다(0/80). 한쪽 관측에만 임시 요일이 있으면 요일 수가 달라져 여전히 다르기 때문이다. 해시 하나로는 풀 수 없고, 직전에 알던 정기 일정과 **공통 요일끼리** 비교해야 한다.

## 2. 측정

| 자료 | 변경 사건 | 영업시간 **표시만** 달라짐 | 정기 요일이 실제로 바뀜 | 영업시간 밖 변경 |
|---|---|---|---|---|
| 관측 표본 2차 (같은 100곳, 약 20시간 뒤 재방문) | 61 | **58** | 3 | 4 (메뉴) |
| 09-20 이후 연속 스냅샷 (199곳) ※ | 142 | **115 (81%)** | 9 | 18 |

※ 같은 기간에 저장된 276건 중 134건은 영업시간과 무관한 파이프라인 사건이라 뺐다. P1-2 결함을 고친 뒤 같은 내용을 다시 저장한 재수집, 해시 세대 전환이 여기에 해당한다.

- 실제 영업시간 변경 예: 5242 목·금 마감 22:00 → 19:00, 472390 평일 마감 20:00 → 19:00.
- "표시만" 115건 중 9건은 기억에 없던 요일이 처음 보인 경우다(아래 3-3).
- 측정 스크립트: 스크래치 `hours_design_measure.py`. 영업시간 밖 필드(이름·전화·주소·좌표·메뉴)는 파이썬 근사다. 판정 대상인 영업시간 부분은 `BusinessHoursParser` 규칙을 그대로 옮겼다.

**비용.** 거짓 변경 1건마다 스냅샷 저장, 재판정 실행, `change_count` 증가가 따라온다. 매일 방문하면 가짜가 약 95%다. `change_count` 는 지금 보고용이지만, 변경률로 티어를 정하게 되면 이 오염이 수집 주기로 번진다. 재판정이 임시 요일을 무시하므로 잘못된 영업시간 **제안**은 생기지 않는다.

## 3. 설계

원칙은 v3 P2-1 과 같다. **변경 감지의 입력 = 재판정이 실제로 소비하는 필드와 의미.** 재판정은 영업시간을 "날짜 없는 요일의 시작·종료·휴무"로만, 그리고 부분 관측으로 소비한다. 변경 감지도 같은 단위와 같은 부분 비교를 쓴다.

### 3-1. 콘텐츠 해시 3세대 — 영업시간을 뺀다

`hashFor` 의 입력에서 `businessHours` 를 뺀다. 이름·전화·인스타·메뉴·배민 메뉴·주소·좌표는 그대로 둔다. `VERSION = 3`.

### 3-2. 정기 영업시간 기억 (`hours_known`)

가게마다 요일별로 마지막에 확인한 정기 값을 기억한다.

```
store_sync_state.hours_known JSONB
  {"MONDAY": {"open": "09:00", "close": "21:00", "closed": false, "observedAt": "2026-09-27T09:48:28"}, ...}
```

- **관측 값** = `BusinessHoursParser.parse` 결과(3-4의 `매일` 수정 포함). 날짜 붙은 요일은 없다.
- 받아들인 관측마다 갱신한다. 변경이든 무변경이든, 관측에서 읽힌 요일을 덮어쓴다.
- 운영 `store_business_hour` 가 아니라 **네이버에서 마지막으로 본 정기 값**이다. 운영 대조는 재판정의 일이다.

### 3-3. 영업시간 변경 판정

```
observed = parse(이번 관측)            # 날짜 없는 요일만
changed_hours =
    ∃ d ∈ observed ∩ known : observed[d] ≠ known[d]      # 공통 요일의 값이 다름
 or ∃ d ∈ observed − known                              # 처음 보이는 요일 (권장: 변경으로 본다)
changed = content_hash_v3 ≠ stored  or  changed_hours
```

- 날짜 붙은 요일은 비교하지 않는다. 그 요일의 실제 변경은 다음에 날짜 없이 보일 때 잡힌다(보통 1주 안). 재판정도 날짜 붙은 요일로는 어차피 제안하지 않으니 잃는 것은 없다.
- **처음 보이는 요일**: 기억에 없던 요일이 처음 정기 값으로 보이면 변경으로 본다. 재판정이 그 요일을 운영과 대조하려면 스냅샷이 저장돼야 하기 때문이다. 가게당 많아야 7번이고, 측정에서는 142건 중 9건이었다.
- 표기 전환(`매일` ↔ 요일별 7줄)은 값이 같으면 무변경이다. 설명 문구·브레이크타임·라스트오더는 재판정이 소비하지 않으므로 보지 않는다.
- `changed` 이후의 흐름(스냅샷 저장·재판정·`change_count`)은 지금과 같다.

### 3-4. 함께 고칠 결함 — `매일` 표기를 읽지 못함

네이버는 요일마다 같은 시간이면 `day: "매일"` 한 줄로 보낸다. `BusinessHoursParser.DAY_TO_ENUM` 은 `월`~`일`만 알아서 이 줄을 건너뛴다.

| 최신 스냅샷 50,747곳 중 `매일` 표기 | 8,421곳 (16.6%) — 지금 읽히는 요일 0개 |
|---|---|
| 운영 영업시간 없음 | **8,127곳** — 앱에 영업시간이 비어 있다 |
| 운영과 다름 | 176곳 |
| 운영과 같음 | 118곳 |

- 수정 규칙: `매일` 을 7요일로 편다. 같은 관측에 개별 요일 줄이 있으면 그 줄이 우선한다. 날짜 붙은 요일은 지금처럼 건너뛴다.
- 이 수정만으로 영업시간 제안이 약 8,300건 생긴다. 운영 쓰기이므로 따로 진행한다(dry-run → 표본 검수 → 제한 승인).
- 3-2의 기억도 이 수정이 먼저 들어가야 `매일` 가게에서 비지 않는다.

### 3-5. 세대 전환 — 가짜 변경 없이 넘어가기

해시 세대를 올린 직후 첫 방문이 전부 변경으로 잡히지 않게 한다(1세대 → 2세대 전환 때와 같은 원칙).

1. 마이그레이션: `hours_known JSONB` 컬럼을 추가한다.
2. 백필 배치: 가게마다 최신 저장 스냅샷에서 ① 3세대 해시와 ② `hours_known` 을 계산해 `content_hash_version = 3` 으로 기록한다. 스냅샷 원본이 남아 있으므로 재수집은 필요 없다. 최신 스냅샷 이후의 무변경 방문은 내용이 같았다는 뜻이라 기준으로 쓸 수 있다.
3. 백필 전에 들어오는 관측은 저장된 세대(2)로 비교한다. 지금의 `hashFor(version)` 경로를 그대로 쓴다.

## 4. 위험과 한계

| 위험 | 판단 |
|---|---|
| 날짜 붙은 요일의 실제 변경이 늦게 잡힘 | 다음에 날짜 없이 보일 때 잡힌다(보통 1주). 재판정도 그 요일로는 제안하지 않으므로 운영 반영 시점은 지금과 같다 |
| 매주 임시 표기인 가게(항상 날짜 붙음) | 그 요일은 기억에 들어오지 않는다. 지금도 재판정이 못 읽는 요일이라 새로 잃는 것은 없다 |
| 설명 문구 변화(`정기휴무 (매주 월요일)`)를 못 봄 | 재판정은 `휴무` 포함 여부만 소비하고, 그 변화는 휴무 플래그로 잡힌다 |
| 기억과 운영이 어긋남 | 기억은 변경 감지용일 뿐이다. 운영 대조·제안은 재판정이 운영 값을 직접 읽어 한다 |
| 해시에서 빠진 영업시간이 다른 소비자에 필요한가 | 스냅샷 원본에는 그대로 남는다. 해시는 저장 여부만 정한다 |

## 5. 단계와 검증

1. **`매일` 파서 수정 + 테스트.** 고정 입력: `매일` 단독, `매일` + 개별 요일 우선, `매일` + `토(9/26)`. 재판정 제안 수를 dry-run 으로 센다. 운영 반영은 별도 승인 절차로 한다.
   → 완료(09-27): `BusinessHoursParser` 가 `매일` 을 7요일로 펴고 개별 요일 줄을 우선한다. 최신 스냅샷 전체의 요일 표기는 `월`~`일`·날짜 병기·`매일` 셋뿐이고, `매일` 은 항상 단독·시간 있음이었다. 신호 파서 버전 2 → 3. 재파싱(09-27 14:54, `rebuild-all`): 50,716곳 v3, 31곳은 원본 미보존 관측이 스냅샷보다 새로워 건너뜀(다음 방문에 갱신). `매일` 가게 8,424곳 중 8,418곳의 신호에 7요일이 들어갔다 — 남은 6곳은 건너뛴 4곳과 8월 옛 원문 형식(`BusinessHour`) 스냅샷만 있는 2곳. 제안 생성·운영 반영은 아직.
   → 제안 생성(09-27, `POST /api/snapshots/reconcile-hours` — 영업시간 묶음만 재판정·정리): 최신 스냅샷에 `매일` 이 있는 8,424곳 중 8,397곳 판정, 8,276곳에 PENDING 제안(운영 영업시간 없음 → 채움 8,100 · 시간 갱신 141 · 요일 추가 35), 건너뜀 27(DELETED 등), 실패 0. 24시간(`00:00~23:59`) 제안 745건은 이름에 무인·24·셀프가 있는 곳이 3%뿐이고 주문 제작 케이크 가게가 많다 — "매일 00~24"가 영업시간이 아니라 연락 가능 시간인 경우라 별도 검수로 뺀다. 반영 전 막을 것: `ServingWriter.replaceBusinessHours` 에 조건부 쓰기(운영 현재 값 = 제안 old_value, DELETED 제외)가 없고, `approve_fill_pending.py` 가 15433(개발 DB 터널)에 하드코딩돼 있다.

2. **판정 구현 + 테스트.** 입력 예시:
   - 회전 주간: `토(9/26)` 휴무 → 다음 날 `토` 08:30~19:00 → 무변경
   - 실제 변경: 금 22:00 → 19:00 → 변경
   - 처음 보이는 요일 → 변경
   - `매일` ↔ 요일별 7줄(같은 값) → 무변경
   - 날짜 붙은 요일만 바뀜 → 무변경
