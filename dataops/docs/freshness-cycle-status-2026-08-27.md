## 4. 마지막 조각 — LOCALDATA 델타 (이 문서 작성 시점의 다음 작업)

현재 LOCALDATA 쪽은 **08-11 스냅샷 한 장**으로 일했다. 이후 보름의 인허가 변화(신규 월 ~8.3천 건
페이스·폐업 전환)가 미반영. 필요한 도구 2개:

1. **델타 수집** — `cond[LCPMT_YMD::GTE]`(신규 인허가)·`cond[DAT_UPDT_PNT::GTE]`(상태 변경)로
   변화분만 pull (콜 수백 개 수준)
2. **폐업 전환 감지** — 상태 델타 × 관리번호 매핑 조인 → "ACTIVE인데 인허가 폐업 전환" →
   네이버 부재 교차 → change_proposal 수납

완성 시 운영 리듬: **일 단위**(네이버 재동기화+승인) · **월 단위**(인허가 델타 → 폐업 감지 + 신규
유입 → 기존 검증·등록 파이프라인). 가게의 탄생부터 소멸까지 증분으로 도는 완전한 최신화 체계.

## 5. 추기 (2026-08-28) — 첫 델타 사이클 완주

§4의 계획은 실측에서 한 번 꺾였다: **서버측 GTE cond 는 값이 무시된다**(어떤 날짜를 넣어도
totalCount 동일 — 문서에만 존재하는 기능). 델타는 **재수집 + 클라이언트 diff** 로 재설계했다
(`localdata_fetch --delta` → `localdata_delta_diff`). 소요 콜 ~1.5만/월(2키 쿼터 내).

**첫 사이클 결과 (기준선 08-11 → 08-28):**

| 트랙 | 결과 |
|---|---|
| 수집 | 4업종 재수집 1,495,227행 (제과점은 업스트림 미갱신 — 최신 인허가일 08-04 동일) |
| diff | 신규 3,489 / 상태변경 1,242 (즉석판매는 부분 기준선 보정 — 인허가일 컷오프) |
| 폐업 | 매핑 교집합 95곳 전환 감지 → 네이버 교차: **부재 44 소프트삭제**, 생존 51 보류 |
| 신규 | 후보 2,861 → 네이버 검증 2,838 완주 → 확정 441(중복 placeId 238 제외) → **등록 166** + 기존 귀속 36, 실패 0 |
| 콘텐츠 | 스냅샷 202 → menu.add 1,349·인스타 94·개명 3·전화 3·가격 8 승인, 정크 27 거절 |

기준선은 pull 로 통째 치환 완료 — 다음 달부터 `--delta 202609` 한 줄로 반복.

**알려진 사각**: 일반음식점은 키워드 재수집이라 매핑 가게 중 11,248곳이 pull 밖 —
이들의 인허가 폐업 전환은 델타로 못 본다(일일 네이버 순회가 보완). 근본 해결은
월 1회 일반음식점 전량 pull(~2만 콜 = 2키 하루치 전용)로 가능 — 채택 여부는 후속 결정.
