## 1. 문제 정의

**dataops가 운영 DB에 반영하는 변경이 OpenSearch 색인에 자동으로 실리지 않는다.**

본 앱의 색인 갱신은 두 경로뿐이다:

| 기존 경로 | 동작 | dataops 변경에 대해 |
|---|---|---|
| 앱 레이어 이벤트 (`StoreIndexEventListener`) | 앱 서비스 코드로 저장할 때만 발화 (AFTER_COMMIT) | **미발화** — dataops는 직접 DML |
| 전체 재색인 (`POST /admin/search/reindex/stores`) | ACTIVE 가게 전량 재색인 (~10분) | 가능하지만 수동·전량 |

8/13~14 대량 백필(가게명 1,661 · 메뉴 93k · 주소 20 등)은 **전체 재색인 1회**로 해결했다.
그러나 이는 일회성 해법이다 — 앞으로 dataops는 **주기 크롤 → 판정 → 반영**을 상시 반복하며,
그때마다 전체 재색인을 돌릴 수는 없다.

### 제약 조건 (토론의 전제)

1. **크롤 주기와 색인을 동기화할 수 없다** — 네이버 크롤은 가게 수·차단 쿨다운에 따라 수 시간~수 일.
   완주 시점이 불규칙해 "크롤 끝나면 재색인" 모델이 성립하지 않는다.
2. **본 앱이 DB를 폴링(상시 감시)하는 방식은 배제** — 대부분의 폴링이 헛방(변경 없음)이고,
   변경의 진원지(dataops)가 이미 아는 정보를 추측으로 재발견하는 구조.
3. **dataops는 오픈서치에 직접 쓸 수 없다** — VPC 내부 엔드포인트(네트워크 경로 없음) +
   문서 조립 로직(메뉴 join·인기도·alias)이 본 앱에 있어 중복 구현이 됨. 이미 기각된 방향.
4. 변경 대상 필드: 가게명·메뉴(추가/소멸)·주소·좌표·가게 추가/삭제(폐업) — **가게 문서 전체 재조립**이
   필요한 변경들이라, 필드 단위 부분 갱신보다 "가게 단위 재색인"이 자연 단위.

### 이벤트 볼륨 실측 (규모 감각)

| 시나리오 | 변경 가게 수 | 빈도 |
|---|---|---|
| 초기 백필 (완료) | ~8,000곳 | 1회성 — 전체 재색인으로 이미 처리 |
| 정기 크롤 후 반영 (향후 상시) | 수십~수백 곳/회 추정 (이름·메뉴·가격 diff) | 주 단위 |
| 폐업/신규 반영 | 수 곳~수십 곳 | 월 단위 |

**결론: 초당 수만 이벤트급 인프라가 설계된 규모와 4자릿수 차이.** 하루 수천 건을 넘지 않는다.

## 2. 핵심 자산 — apply_log는 이미 아웃박스다

dataops의 불가침 규율: **모든 운영 쓰기는 `apply_log` 선기록 후 실행** (예외 없음, 8/13 백필 10만 건 실증).

메시지 큐가 본질적으로 제공하는 것 = ① 내구성 있는 이벤트 로그 + ② 소비 위치(오프셋).
우리는 이미 ①을 apply_log로 갖고 있고, ②는 워터마크(마지막 push 시각) 저장이면 된다.
**어떤 대안을 고르든 "변경된 가게 목록"의 원천은 apply_log다** — 대안들은 이 목록을
본 앱에 전달하는 "운송 수단"의 차이일 뿐이다.

## 3. 대안과 트레이드오프

### A. 현상 유지 — 반영 후 수동 전체 재색인

| | |
|---|---|
| 구조 | dataops 반영 완료 → 사람이 admin 전체 재색인 호출 |
| 장점 | 구현 0. 절대 누락 없음 |
| 단점 | 수동 운영 부담 · 수십 곳 바뀌어도 9천 곳 전량(10분+오픈서치 부하) · 사람이 잊으면 검색 낙후 |
| 평가 | 백필 같은 대량 1회성엔 적합. **상시 운영 모델로는 탈락** (이 문서의 출발점) |

### B. 주기 증분 재색인 — `updated_at` 워터마크 배치 (본 앱 단독)

| | |
|---|---|
| 구조 | 본 앱 @Scheduled(야간 1회 등): `updated_at > 지난 실행` 가게만 재색인. dataops 연동 코드 0줄 (모든 dataops 쓰기가 updated_at 갱신함) |
| 장점 | **가장 단순** · dataops와 완전 무결합 · 앱 내 변경(어드민 수정 등)도 함께 커버 |
| 단점 | 반영 지연 = 배치 주기 (일 1회면 최대 24h) · **폐업(soft delete) 가게 문서 잔류** — DELETED는 ACTIVE 조회에서 빠져 upsert 대상이 안 되므로 delete 별도 처리 필요 · "며칠 안 바뀐 가게"를 매일 확인하는 소량 헛방은 여전 |
| 평가 | 단독으로도 성립. 지연을 수용할 수 있으면 최소 비용 안 |

### C. 아웃박스 push — apply_log 워터마크 + HTTP 배치 호출 ★ dataops 제안

| | |
|---|---|
| 구조 | ① 본 앱: `POST /admin/search/reindex/stores/batch` (storeId 목록 → 기존 `bulkIndexStores` 재사용, DELETED면 문서 delete) ② dataops: 5분 스케줄 — apply_log에서 워터마크 이후 `DISTINCT store_id` 추출 → HTTP 호출 → 워터마크 갱신 |
| 장점 | 추가 인프라 0 · 반영 지연 ~5분 · 바뀐 가게만 정확히 · **폐업 문서 삭제 경로 확보** · at-least-once(워터마크 재시도) + 색인 upsert 멱등이라 중복 무해 · 본 앱 다운 시 push 실패해도 워터마크가 다음 주기 자동 재시도 · 오늘 검증된 통신 패턴(admin API — 이미지 백필 8만 장이 같은 방식) |
| 단점 | 본 앱 엔드포인트 1개 추가(~20줄) · dataops 스케줄러 1개 추가 · 동기 HTTP라 대량 호출 시 배치 분할 필요(구현 디테일) |
| 평가 | 현재 요구(폴링 없음·크롤 주기 무관·증분)를 최소 비용으로 정확히 충족 |

### D. SQS — 완전관리형 큐

| | |
|---|---|
| 구조 | dataops가 SQS에 storeId 발행(퍼블릭 엔드포인트+IAM — **로컬에서 가능, VPC 불요**) → 본 앱이 컨슈머 |
| 장점 | 본 앱 다운타임에 큐가 버퍼링 · 재시도/DLQ 내장 · 관리 부담 ~0, 비용 ~0 |
| 단점 | 본 앱에 SQS 컨슈머 스택 추가(의존성·리스너·에러 처리) · dataops에 AWS 자격 관리 · **C 대비 실익이 "다운타임 버퍼링"뿐**인데 그건 C의 워터마크 재시도가 이미 해결 |
| 평가 | C의 자연스러운 다음 단계. **컨슈머가 2개 이상 생기는 시점**(색인+캐시 무효화+알림 등 팬아웃)에 도입 가치 발생 |

### E. Kafka + dataops VPC 상주

| | |
|---|---|
| 구조 | dataops를 VPC 상시 서버로 이전, Kafka(MSK or 자가 운영)로 변경 이벤트 발행, 본 앱 컨슘 |
| 장점 | 대용량·다중 컨슈머·리플레이·순서 보장 — 이벤트 기반 아키텍처의 종착점 |
| 단점 | **브로커 운영 비용**(MSK 월 수십만 원대 or EC2 자가 운영 부담) · **dataops 상시 서버화라는 별개의 큰 결정을 강제** (현재 "로컬 + 필요 시 기동" 모델 폐기, 배포·모니터링 체계 신설) · 컨슈머 랙/오프셋 운영 지식 · 우리 볼륨(수천/일)과 설계 지점(수만/초)의 미스매치 |
| 평가 | **현 규모에 과잉.** §2 논리로 보면 apply_log가 이미 제공하는 보장을 브로커로 이중 구매하는 셈. 도입 신호(§5)가 오기 전엔 비권장 |

### F. CDC — Debezium/DMS로 DB 변경 스트림

| | |
|---|---|
| 구조 | 운영 PG의 WAL을 CDC로 캡처 → 스트림 → 색인 갱신 |
| 장점 | 쓰기 주체 무관하게 모든 변경 포착 (dataops·앱·수동 SQL 전부) |
| 단점 | RDS 논리 복제 설정 + 커넥터 인프라 + 스트림 소비자 — 도입 비용이 E급 · 스키마 변경 취약 |
| 평가 | "쓰기 주체가 통제 불가능하게 많을 때"의 해법. 우리는 쓰기 주체가 둘뿐(앱·dataops)이고 둘 다 통제됨 — 불필요 |

## 5. dataops 권고안

**C(아웃박스 push)를 주 경로로, B(야간 증분)를 안전망으로 병행.**

- C가 5분 내 증분 반영을, B가 push 누락·실패 보정과 앱 내 변경 커버를 맡는다.
  전체 재색인은 "매핑 변경 시"의 도구로 강등.
- **마이그레이션 경로가 열려 있다**: 본 앱 엔드포인트의 계약을 "storeId 목록 → 재색인"으로 잡아두면,
  훗날 D(SQS)로 갈 때 dataops의 호출부만 큐 발행으로 바꾸면 되고 본 앱 처리 로직은 그대로 재사용된다.
- **E(Kafka) 도입을 재검토할 신호**: ① 한 변경을 소비하는 시스템이 2개 이상(색인+캐시+알림 팬아웃)
  ② 변경 볼륨 상시 수만 건/일 초과 ③ 초 단위 실시간성이 제품 요구로 등장.
  이 신호들 전에는 어떤 MQ도 같은 보장의 이중 구매다.
- "dataops 서버화(VPC 상주)"는 색인 문제와 **독립적인 결정**이다 — 3단계 apply_log RDS 승격 시에도
  C 구조는 그대로 유지되고 지연만 준다. MQ 때문에 서버화를 앞당길 이유는 없다.

## 6. 토론 포인트 (팀 결정 필요)

1. **B의 지연(최대 24h)을 안전망이 아니라 주 경로로 수용할 수 있는가?** 그렇다면 C를 생략하고
   B 단독(+폐업 delete 처리)이 최소 구현이다. dataops는 "검색 반영 5분 vs 24h"의 제품 판단을 위임한다.
2. 부분 재색인 엔드포인트의 위치 — admin API(현행 permitAll)에 둘지, 인증을 붙일지.
   (admin 전체의 인증 도입은 별도 보안 논의로 분리 권장)
3. 야간 증분 잡의 주기(일 1회 vs 시간별)와 실행 시간대.
4. (참고) 향후 검색 외 소비자(캐시·알림)가 생기면 D(SQS) 전환 시점을 그때 논의.
