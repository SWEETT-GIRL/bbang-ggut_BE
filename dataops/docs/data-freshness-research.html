00한 장 요약

문제를 잘못 정의하고 있었다. “45,444개를 어떻게 다 최신으로 유지하나”는 달성 불가능한 목표다. 올바른 정의는 “고정된 크롤 예산 R 안에서 신선도를 최대화하는 자원 배분”이다.

이 보고서에서 가장 중요한 문장

일부 가게를 재크롤 대상에서 영구 제외하는 것은 타협이 아니라 이론적 최적해다.

최적 배분 공식 ρᵢ = √(μᵢΔᵢ/λ) − Δᵢ 에서 μᵢ/Δᵢ ≤ λ인 가게는 최적 크롤률이 정확히 0이다. (μ = 조회·수요율, Δ = 변경률, λ = 예산이 결정하는 전역 임계)

동시에, 지금은 이 공식을 쓸 수 없다. 입력이 모두 없기 때문이다 — 예산 R(네이버 지속 가능 요청률)도, μ(가게별 조회·구독 신호가 로깅되는지)도 확인되지 않았고, Δ(변경률)를 계산할 스키마 컬럼조차 없다.

답하지 못한 것

조사 축 하나가 여전히 비어 있다. 한국 공공데이터(LOCALDATA·국세청) 기반 폐업 감지는 검증 통과 근거가 단 한 건도 없어 이 보고서가 답하지 못한다.

인스타그램 — 리서치가 아니라 실측으로 답이 나왔다 (3.3절)

인스타는 비어 있는 걸 채우는 도구가 아니라, 있는 걸 갱신하는 도구다.

메뉴 0개 가게의 인스타 보유율 37.2%, 메뉴 있는 가게 67.2% — 30%p 차이. 가장 필요한 집단에서 가장 없다.

가장 급한 것은 최적화가 아니었다 (3.4절)

데이터가 2개월간 낡은 게 아니라, 처음부터 제대로 안 긁혔다.

네이버에 있는데 우리 DB에 없는 메뉴 2,978개 중, 판별 가능한 것의 68.8%가 “최초 수집 누락”이었다. 이건 스케줄링 문제가 아니라 일회성 백필 문제다.

결론 4줄

  1. 가장 급한 것 — 네이버 메뉴 재수집. 최초 누락 복구 + 메뉴 0개 가게의 47.7%를 무료로 채움(~3,170 가게 / ~32,000 메뉴). 유료 API도 인스타도 필요 없다. 단, 출처 컬럼 없이 덮어쓰면 사용자 기여가 유실된다.
  2. 당장 할 것 — store에 상태변수 4개(last_verified_at, crawl_attempts, change_detected_count, content_hash) 추가.
  3. 하지 말 것 — ① 변경률을 X/n으로 추정 — 비일관 추정량이다. ② “메뉴 0개를 인스타로 채운다” — 네이버 재수집이 더 많이, 더 싸게 한다.
  4. 다음 세션 1순위 — 한국 공공데이터 폐업 감지. 네이버 경로 폐업 감지가 실패했으므로 이게 유일한 대안일 수 있는데 근거가 0이다.

02검증 통과 발견

각 항목의 vote는 3인 독립 검증자의 반박 시도 결과다. 3-0은 3명 모두 반박에 실패했다는 뜻.

2.1  문제 재정의 — 예산 배분 문제다

vote 3-0 🟠 한국 데이터 없음

웹 문서의 변경은 포아송 과정으로 잘 설명된다. 270개 사이트 약 720,000 문서를 4개월간 매일 크롤한 실증 연구다. 개별 대상의 변경 시점은 예측 불가능해도, 대상별 평균 변경률 λ만 추정하면 최적 재방문 정책을 계산할 수 있다.

함께 읽어야 할 단서

검증 구간 한계 — 크롤 granularity가 1일이라 실제 검증된 것은 10~20일급 중간 주기 대상이다. 빵집 메뉴·영업시간은 주~월 단위라 검증 구간과 겹쳐 오히려 유리하다.

흔한 오독 주의 — 이 논문의 결론은 “재방문 빈도를 λ에 비례시키라”가 아니다. 균일 정책이 비례 정책보다 낫고, 최적 빈도는 λ에 대해 비단조적이다.

2.2  핵심 우선순위 공식 ⭐

vote 2-1 PNAS 115(32) · 2018 원 PDF만 사용 
목적함수   F₂(ρ) = Σᵢ μᵢρᵢ/(ρᵢ + Δᵢ)     제약  Σᵢ ρᵢ = R
최적해     ρᵢ = √(μᵢΔᵢ/λ) − Δᵢ
배제 규칙  μᵢ/Δᵢ ≤ λ  ⟹  ρᵢ = 0
  • μᵢ — 가게 i가 요청되는 포아송률 (조회수·인기·수요)
  • Δᵢ — 가게 i가 변경되는 포아송률
  • λ — 예산 R과 최종 활성 집합이 함께 결정하는 전역 임계

실무 함의 2가지: ① 크롤 빈도는 변경률에 선형이 아니라 제곱근 비례한다. ② μᵢ/Δᵢ ≤ λ인 가게는 크롤 빈도 0이 최적 — “전수 재크롤 포기”는 타협이 아니라 최적해다.

인용 오염 경고

PMC의 HTML 평문 변환이 근호(√)를 탈락시켜 호출마다 다른 잘못된 수식을 반환한다 (ρᵢ = μᵢΔᵢ(λ−Δᵢ) 등). 이번 검증에서만 서로 다른 오류 렌더링 2종이 관측됐다. PMC 렌더링본을 인용하지 말고 반드시 원 PDF를 쓸 것. 반대 1표도 이 오염이 원인으로 보이며, 검증자가 원 PDF로 축자 확인했다.

계산 비용 — μᵢ/Δᵢ 오름차순 정렬 → 임계 미달 항목 0으로 떨굼 → 재계산. Theorem 1이 O(n log n) 유일해를 보장하므로 n≈4.5만은 정렬 한 번 수준이다.

🟡 후속 — 우리에게 더 적합할 수 있음

Kolobov et al. SIGIR 2019가 동일 목적함수를 politeness(요청률 상한) 제약으로 확장했고 Microsoft가 구현을 오픈소스로 공개했다. 네이버 차단 회피가 실제 제약인 우리에게는 이쪽이 더 맞을 가능성이 높다 (미검증).

2.3  변경률 추정의 함정 — X/n을 쓰지 마라

vote 3-0

변경률을 “감지된 변경 횟수 / 방문 횟수(X/n)”로 추정하면 구조적으로 하향 편향되며, 표본 수 n을 아무리 늘려도 편향이 전혀 줄지 않는다(비일관 추정량).

조건결과
편향 10% 이내로 잡으려면방문 빈도 f가 실제 변경률 λ의 약 5배 (r < 0.21)
주 1회 변경 대상을 2주에 한 번 관측편향 57% (E[r̂]/r ≈ 0.43)

→ 네이버 차단 위험 때문에 f를 낮게 유지할 수밖에 없는 우리 조건에서 재크롤 우선순위를 X/n으로 매기면 변경률을 대폭 과소평가하게 된다.

🟡 보정 대안 — 확정 사실 아님

같은 논문 4.2절이 보정 추정량 r̂ = −log((X̄+0.5)/(n+0.5))을 제시한다. 다만 이 추정량의 실효성을 단독 주장으로 세운 클레임은 0-3으로 부결됐다. 논문 자체가 X̄=0일 때 특이점을 명시하므로, r이 큰 우리 상황에선 보정 추정량조차 포화될 수 있다.

2.4  상태 모델 — 이진 플래그로는 안 된다

vote 3-0 / 3-0

대형 POI 사업자들은 영업 여부를 이진 플래그로 관리하지 않는다.

사업자상태 모델
Google Maps 제보 택소노미 7종(Temporarily closed / Permanently closed / Doesn’t exist here / Duplicate / Moved / Not open to the public / Reopened) · 저장 enum 4값(OPERATIONAL / CLOSED_TEMPORARILY / CLOSED_PERMANENTLY / FUTURE_OPENING) — 영업시간과 별개 필드
OpenPOIs “POI가 실존하며 현재 일반에 영업 중일 확률”을 0~1 연속 점수로 모델링
인용문보다 강한 근거

“Do not mark a place open or closed based on its hours.”

hours 기반 판단을 closure로 쓰지 말라는 직접적 분리 지시. OPERATIONAL 설명 “operational, not necessarily open now”가 “영업중 상태 ≠ 지금 문 열려있음”을 못박는다.

→ 우리 함의: store.status(ACTIVE|DELETED) 단일 플래그로는 임시휴업·이전·중복·미존재를 표현할 수 없다. business_status enum + 영업시간 별도 컬럼 + existence_confidence 확률 컬럼 분리 설계가 1차 근거로 뒷받침된다.

OpenPOIs 4대 한계 — 반드시 병기
  1. 점수 산출기는 이식 불가 — confidence는 “OSM 태그 편집 이력에 적합시킨 베이지안 turnover 모델” 기반인데 우리는 OSM 편집 이력이 없다. 이전 가능한 것은 스키마 패턴이지 추정기가 아니다.
  2. 폐업 탐지기로는 무력 — 점수 분포가 <30%: 0.2% / 30~70%: 24.6% / 70~90%: 68.5% / >90%: 6.7%로 저신뢰 구간이 0.2%뿐이라 그대로 필터로 쓰면 거의 아무것도 못 거른다.
  3. 커버리지 미국 한정 — 한국·네이버·카카오 사례 아님.
  4. 캘리브레이션이 2026-07-30에 방금 변경됨(조사 시점 하루 전, 이전 릴리스와 비교 불가라고 프로젝트가 명시).

2.5  폐업 감지는 다중 약신호 결합 문제

vote 3-0 🟡 단일 벤더 블로그 · 4.75년 경과

Foursquare는 3,000개 이상의 후보 피처를 만들어 XGBoost 등 분류 모델을 학습시키는 ML 파이프라인으로 폐업을 판정한다. 신호는 서드파티 firmographic 데이터부터 자사 사용자 생성 시계열(방문·체크인·편집·팁·사진)까지 걸쳐 있다.

이식성 — 결정적 주의

이 클레임은 참이지만 빵긋으로의 운영 이전 가능성은 낮다. Foursquare의 최강 피처는 전 지구 규모 자사 체크인 스트림인데, 우리는 45,444개 가게에 회원 1,976명·2개월 제보 171건으로 그 밀도의 근처에도 없다.

이 근거는 원칙(“여러 약한 신호를 결합하라, 단일 소스에 의존하지 말라”)만 지지하며, 3,000피처 XGBoost 구축을 정당화하는 데 인용해서는 안 된다.

이 도출을 그대로 신뢰하지 말아야 할 4가지
  1. “가치비 균일 버킷 내 조회수 비례 스케줄” 유사 주장은 0-3으로 부결됐다. 위 1단계는 확정된 닫힌 형태로부터 유도했지만 독립 검증을 통과한 명제는 아니다.
  2. ⚪ 예산 R을 정할 근거가 없다 — R 없이는 λ도 정해지지 않아 배제 집합을 계산할 수 없다.
  3. ⚪ μ가 프로덕션에 로깅되는지 확인되지 않았다. 없으면 1단계조차 불가능하다.
  4. 균일 정책이 비례 정책보다 우수하다는 별도 결론을 감안하면, Δ 인프라 이전 단계의 정교한 스케줄링이 단순 라운드로빈 대비 실이득을 낼지 불확실하다.
제외 조건 반영

네이버가 유일 크롤 소스이므로 미매칭 14,500개(32%)는 어떤 스케줄링 개선으로도 갱신되지 않는다. 이 32%는 최적화가 아니라 매칭률 개선으로만 해결된다.

⚡ 부수 발견 — 크롤 예산 R의 하한 실측치

4장에서 “네이버 지속 가능 요청률을 몰라 λ를 계산할 수 없다”고 한 문제에 부분적 답이 나왔다: 0.67 req/s × 400회 연속, 차단 0건.

이는 R의 하한이며 상한은 아니다. 다만 이 한 번의 관측으로 다음을 말할 수 있다 — 45,444개를 이 속도로 한 바퀴 도는 데 약 19시간이다. 즉 전수 재크롤이 물리적으로 불가능한 게 아니라, 최적이 아닐 뿐이다(2.2의 배제 규칙).

부수 확인:

  • HTTP 404 = 0/400 — 네이버는 (이 표본 내에선) 폐업 가게 페이지를 삭제하지 않는다. 404를 폐업 신호로 쓸 수 없다.

  • has_hours 파싱 실패 399/400 — Apollo 정규화 캐시의 참조 처리를 못 한 스크립트 버그. 데이터는 응답에 실재한다(단건 프로브에서 09:30~20:00 확인). 수정하면 영업시간 0.5% 커버리지를 대폭 올릴 수 있다.

🟡 플랫폼 제약 — 일부만 공개 출처 확보
  1. 비로그인 해시태그 검색 차단 (🟡 공개 출처 미확보) — 다만 우리에겐 무관하다. 핸들을 네이버에서 이미 받으므로 계정 발굴 없이 프로필로 직행한다.
  2. 로그인 세션은 계정 정지 리스크 (🟡) — 3.5에서 부분 정정: Apify 문서는 “Login not required for public data”를 명시한다. 로그인 제약은 해시태그 검색과 일부 필드에 걸리는 것이지 공개 프로필 게시물에는 걸리지 않는다.
  3. 게시물 수집 단계는 유료다 — 핸들 확보(무료)와 별개. ✅ 3.5에서 공개 출처로 검증 완료.

벤더 비교와 실제 비용은 3.5절 참조.

핸들 확보 ≠ 메뉴 확보

이번 측정이 답한 것은 첫 관문(계정을 찾을 수 있는가)뿐이다. 그다음 단계 — 게시물 수집(유료) → 캡션에서 메뉴·가격 추출(LLM) → 기존 메뉴와 대조 — 는 전부 미검증이다.

⚠️ 3.4 측정 후 이 절의 결론이 약해졌다. “메뉴 0개를 채우는 수단”으로 인스타가 도달하는 ~2,470 가게보다 네이버 재수집이 ~3,170 가게를 무료로 채운다. 인스타 유료 파이프라인은 그 백필을 끝낸 뒤에 판단할 일이다.

문서에 “일부 엔드포인트는 #posts만큼 과금”이라 돼 있어, user/posts가 여기 해당하면 두 벤더가 사실상 같은 모델이 되고 대규모 우위가 사라진다. 첫 호출 한 번으로 판명된다.

세 가지 결론
  1. 스토리는 살 수 없다 — 독립된 두 벤더 모두 미지원. 표본 2개라 단정은 못 하지만 24시간 만료 + 접근 게이팅이라는 구조적 이유가 있어 “찾으면 있겠지”로 기대하지 않는 것이 안전하다.
  2. Apify는 한 실행에 콘텐츠 타입 혼합 불가 — 게시물과 릴스를 같이 못 받는다. 릴스 공지 비율에 따라 비용이 2배가 될 수 있어 파일럿에서 함께 측정할 것.
  3. 벤더를 고르지 말고 갈아끼울 수 있게 만들 것. 공통 인터페이스 뒤에 두고 응답 원형(payload jsonb)을 항상 보관해야 벤더를 바꿔도 과거 데이터를 다시 사지 않는다.

🔴 시장 조사는 미완이다. 위 두 곳은 지목받아 확인한 것이지 체계적 비교가 아니다. Bright Data·ScrapingBee·Zyte 계열 등의 인스타 지원 범위·가격·스토리 여부는 미확인(웹 검색 예산 소진). TODO 17번.
