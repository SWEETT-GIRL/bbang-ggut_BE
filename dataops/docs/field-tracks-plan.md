## ① 영업시간 (설계 확정 → 구현)

**소스**: 스냅샷 `businessHoursRaw` — 요일별 `{day, businessHours{start,end}, breakHours, description,
lastOrderTimes}`. 보유 74.3% (표본 1,000곳 실측). 재크롤 불요.

**타깃**: `store_business_hour(store_id, day_of_week[MONDAY..SUNDAY], open_time, close_time, is_closed)`
— 현재 214곳/1,498행뿐.

**표현 매핑 (운영 스키마가 단순해서 손실 매핑으로 확정)**:

| 네이버 | 운영 | 규칙 |
|---|---|---|
| `day: "월"` | `MONDAY` | 한→영 요일 매핑. `"토(8/1)"` 처럼 날짜 병기 = **임시휴무 주간 표기 → 해당 스냅샷의 그 요일은 스킵** (임시 상태를 정기 패턴으로 오염시키지 않음) |
| `businessHours: {start, end}` | `open_time, close_time` | `"24:00"` → `23:59` 보정. 자정 넘김(`02:00` 마감)은 그대로 저장 (운영도 time 타입이라 표현 동일) |
| `businessHours: null` + 휴무 | `is_closed = true` | description "정기휴무"류만. 애매하면 그 요일 스킵 |
| `breakHours`, `lastOrderTimes` | — | **버림** (운영 스키마에 자리 없음 — 확장은 본 앱 소관, 장기 제안으로만) |

**판정 정책** (병합 매트릭스 §6: business_hours = AUTO):
- 운영에 행이 **없는 가게(대다수)**: 채움 — 요일 7행 세트 INSERT. 2단계 규약상 proposal 경유하되
  phone 처럼 표본 점검 후 일괄 승인
- 운영에 행이 **있는 가게(214곳)**: 사람이 넣은 값일 수 있음 → **PROPOSAL 강등**, 개별 검수
- diff 단위는 **가게 단위 세트 비교** (요일별 부분 diff 는 과잉 — 정규화 후 7행 전체 해시 비교)

**쓰기 방식**: `ServingWriter.replaceBusinessHours(storeId, rows)` — DELETE 후 7행 INSERT (가게 단위
원자 교체, 단일 트랜잭션). `dataops_writer` 에 `store_business_hour` INSERT/DELETE 권한 추가 요청 필요
(현재 store·menu 한정 — **유일한 외부 의존**). 스키마 가드에 테이블 추가.

**구현 단계**:
1. 파서: `businessHoursRaw` → 요일 7행 구조화 (+ 위 매핑 규칙, 단위 테스트에 실페이로드 케이스)
2. reconcile diff 확장: `store.business_hours` target, 세트 해시 비교, 기존값 있으면 강등
3. ServingWriter + 가드 + 권한 협의 (본 앱 팀에 GRANT 한 줄)
4. 재판정 → 표본 30곳 눈검사 (플레이스 대조) → 일괄 승인
5. 완료 후: 본 앱 상세 페이지 영업시간 노출 확인. 색인 무관 (검색 필드 아님)

**규모 추정**: ~6,800곳(74.3% × 9,203) × 7행 ≈ **48k 행 INSERT**. 승인 파이프라인 실측 속도(120건/s)면 반영 1시간 내.

**리스크**: 임시휴무 오염(→스킵 규칙), 24시간/자정넘김 표기(→보정 규칙), 기존 214곳 충돌(→강등).

## ② 주소·좌표 (diff 확장 → 소량 검수)

**소스**: `PlaceDetailBase.address / roadAddress / coordinate{x,y}`. **타깃**: `store.address(varchar)`,
`store.location(PostGIS geography Point)` — 빵알람 지오펜싱의 입력이라 좌표 오류는 알림 오발/미발로 직결.

**판정 정책** (§6: PROPOSAL — 이전 vs 오매칭 구분 필요):
- 주소: 정규화(공백·층호 제거) 후 불일치 → proposal
- 좌표: **거리 임계값** — 기존 location 과 신규 좌표 거리 `> 150m` 일 때만 proposal
  (150m 미만은 지오코딩 오차로 보고 IGNORE — 알림 반경 20~200m 과 같은 자릿수라 이 이하 정정은 무의미)
- 주소와 좌표가 **함께** 크게 바뀌면 "이전(移轉)" 신호, 좌표만 바뀌면 오매칭 의심 신호 — 검수 화면에 구분 표시

**쓰기**: `updateStoreAddress(storeId, address, lon, lat)` — `ST_SetSRID(ST_MakePoint(?,?),4326)::geography`.
store UPDATE 권한 내라 **권한 협의 불요**.

**구현 단계**: 파서 좌표 추출 → diff(임계값) → ServingWriter → 재판정 → **전량 눈검사**(이동은 드물어
수십 건 예상 — 지도 링크 검수 페이지) → 승인. 좌표 반영분은 재색인 대상 목록에 포함(지도 검색 영향 가능).

**리스크**: 오매칭 잔존분(재매칭 트랙 2건 등)의 좌표를 덮으면 엉뚱한 위치로 이동 — 검수에서 오매칭 의심
플래그(가게명 유사도 재사용) 동반 표시로 방어.

## ④ 사진 (법률 게이트 — 마지막)

**현황**: 원재료 확보 — 스냅샷에 메뉴/가게 이미지 **원본 화질 URL**(ldb-phinf, 리사이즈 파라미터 없음)
보존. 운영 파이프라인은 S3 업로드 트리거로 검증·리사이징(`resizedKey320`).

**게이트 1 — 저작권 (선행, 최대 관문)**: 네이버 플레이스의 점주·이용자 사진을 자사 S3 로 복제·서빙하는
것은 링크와 달리 **복제·전송** — 인스타 수집을 "유료·법률 검토 후"로 보류한 것과 같은 결. 법률 검토
결과가 부정적이면 트랙 폐기하고 대안(점주 제보 유도, 사용자 업로드 리워드)으로 전환.

**게이트 2 — 기술 계약 (본 앱)**: S3 키 네이밍 규약, `menu_image_file`/`store_image_file` 행 삽입 주체
(트리거 람다 vs 업로더), 트리거가 기대하는 메타데이터, 버킷/경로 권한.

**법률 통과 시 파이프라인**: 스냅샷 URL → 다운로드(쿨다운 예산 — 네이버 CDN 부하 관리) → S3 업로드
(기존 트리거가 검증·리사이징) → 이미지 테이블 행 → 재색인 무관(썸네일은 DB 경유).
**파일럿 100곳 → 확대**. 우선순위는 메뉴 사진(백필 93k 전부 무사진) > 가게 사진.

**규모 추정**: ~93k 메뉴 × 1장 × ~400KB ≈ 37GB 원본 + 리사이즈. S3 비용 무시 가능, 다운로드가 병목
(0.67req/s 하한 기준 ~38시간 — 워커 쿨다운 규약 재사용).
