# Brainstorm (설계 방향 탐색)

spec 작성 전에 설계 방향을 **여러 안으로 펼쳐 비교**하고, 사용자와 방향을 합의한다.

## 적용 조건

다음 중 하나라도 해당하면 진행. 단순 작업(버그 수정, 단일 파일, 파라미터 추가)은 건너뛰고 바로 spec/구현.

- 새 Entity/테이블
- 새 도메인 패키지 또는 새 Service
- 외부 연동(S3 · FCM · Kakao · OpenSearch) 추가/변경
- 여러 파일(5개+)에 걸친 변경

## 실행 프로세스

1. **브랜치 확인**
   ```bash
   git branch --show-current
   ```
   - 비어 있으면(detached HEAD) `git rev-parse --short HEAD`로 식별자 대체, 또는 사용자에게 파일명 확인

2. **코드 탐색** — `Task(subagent_type=Explore)`로 관련 도메인의 Controller/Service/Repository/Entity 파악 (메인 컨텍스트 오염 없이 결과만)

3. **접근법 2~3개로 분기** — 문제를 해결하는 서로 다른 설계안 제시

4. **트레이드오프 비교** — 성능 · 복잡도 · 우리 제약(CQRS 분리 · PostGIS 공간쿼리 · 트랜잭션 경계 · 동시성) 적합성 기준

5. **방향 합의** — `AskUserQuestion`으로 확인 ← **게이트. 합의 전 spec/코드 작성 금지.**

6. **기록** — 합의된 방향을 `.claude/planning/{브랜치}.md`의 **"0. 설계 방향(Brainstorm)"** 섹션에 작성 (spec이 이를 전제로 시작)

## 접근법 비교 형식

```markdown
## 0. 설계 방향 (Brainstorm)

### 문제
- (무엇을 결정해야 하는가)

### 접근법 비교
| 접근 | 핵심 | 장점 | 단점/위험 | 우리 제약 적합성 |
|------|------|------|----------|------------------|
| A. … | … | … | … | … |
| B. … | … | … | … | … |

### 결정
- 채택: (안 + 이유)
- 제외: (안 + 제외 이유)
```
