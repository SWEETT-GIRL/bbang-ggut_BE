# 편지함(LETTER) — 개발자 ↔ 사용자 1:1 대화

작성: 2026-09-03

## 0. 무엇을 만드는가

앱 안에서 **개발자와 사용자가 편지를 주고받는다.** 한 사람당 대화방 하나(1:1 스레드).

```
어드민                                사용자 앱 (벨 → 편지 탭)
─────────────────                    ─────────────────────────
포실한 까눌레 님께                →    ┌──────────────────────┐
"인터뷰 가능하실까요?"                 │ 인터뷰 가능하실까요?   │
                                     └──────────────────────┘
                                     ┌──────────────────────┐
"네 좋아요!"                    ←    │ 네 좋아요!            │ (사용자 답장)
                                     └──────────────────────┘
```

### 알림(🔔)과의 경계

| | 알림 (기존) | 편지 (이번) |
|---|---|---|
| 방향 | 일방향 | **양방향** |
| 내용 | 누가 내 빵투어를 찜함 · 앱 공지 | 개발자 ↔ 사용자 대화 |
| 대상 | 전체 | 지정한 사람 |

앱은 벨 아이콘 하나 안에서 `알림` / `편지` 탭으로 나눈다. 진입점을 새로 파지 않는다.

**전체 공지("새 버전 나왔어요")는 이번 범위가 아니다.** 그건 알림 쪽에 타입을 늘리는
다음 작업이고, 편지함은 답장이 오가는 건만 다룬다.

## 1. 지금 있는 것

- `POST /inquiries` — 문의 등록 API가 있으나 **앱이 안 쓴다.** 조회 API도 어드민 화면도
  없어서 등록되면 아무도 못 본다. 앱 설정의 '문의하기'는 `mailto:` 링크다.
  → 편지함이 이 자리를 대체한다. `inquiry` 패키지는 이번에 건드리지 않고 남겨둔다(죽은 코드로 표시만).
- `MarketingNotification` 엔티티 — 만들어만 놓고 아무 데서도 안 쓴다. 제목·링크·스레드가
  없어 편지에 재사용할 수 없다. 그대로 둔다.
- `CourseSaveNotification` 스택 — 목록/미읽음/읽음처리의 완성된 사례. 이번 작업은 이 모양을
  따라간다(Slice 페이징, `readAt` 널 여부로 미읽음, 벌크 UPDATE 전체읽음).

## 2. 스키마

```
letter_thread     한 회원당 대화방 하나 (member_id UNIQUE)
letter_message    스레드에 달린 편지 한 통 (sender = ADMIN | MEMBER)
```

`letter_thread.last_message_at` 만 비정규화한다 — 어드민 목록이 "최근 대화순"으로
정렬되는데, 매번 메시지 테이블을 group by 하면 스레드가 늘수록 느려진다.
미읽음 개수는 비정규화하지 않는다(두 벌 관리 = 어긋날 자리).

## 3. 엔드포인트

### 사용자 (`/letters`, 인증 필요)

| | |
|---|---|
| `GET /letters` | 내 편지 목록. page/size, 최신순. `{ messages[], hasNext }` |
| `POST /letters` | 편지 보내기 `{ body }`. 스레드 없으면 만든다 |
| `GET /letters/unread-count` | 벨 배지용. 안 읽은 **ADMIN** 편지 수 |
| `PATCH /letters/read` | 편지함 열 때 전체 읽음 |

### 어드민 (`/api/admin/letters`)

| | |
|---|---|
| `GET /threads` | 스레드 목록. 닉네임·마지막 편지·미읽음 수 |
| `GET /threads/{id}` | 대화 내용 |
| `POST /threads/{id}/messages` | 답장 `{ body }` |
| `POST /send` | 새 편지 `{ memberIds[], body }` — 각자 스레드에 꽂는다 |
| `PATCH /threads/{id}/read` | 어드민 읽음 처리 |

수신자를 고르려면 회원 검색이 필요한데 어드민에 없다 → `GET /api/admin/members?q=`를 새로 붙인다.

## 4. 보안 — 반드시 짚고 갈 것

`SecurityConfig`에서 `/admin/**`, `/api/admin/**`이 **`permitAll()`** 이다. 어드민 웹의
로그인도 프론트 JS에 박힌 목 계정이라 서버 쪽 인증이 사실상 없다.

코스 등록이면 데이터가 지저분해지는 정도지만, **편지 발송이 열려 있으면 아무나 개발자를
사칭해 사용자에게 메시지를 보낼 수 있다.** 성격이 다르다.

→ 편지 어드민 경로에만 거는 `AdminApiKeyFilter`를 같이 넣는다.
- `admin.api-key` 프로퍼티(환경변수 `ADMIN_API_KEY`)가 **설정돼 있으면** `X-Admin-Key` 헤더를 검사
- 설정이 비어 있으면 통과 + 기동 시 경고 로그 (로컬 개발이 막히지 않게)
- **prod에는 반드시 넣어야 한다.** 안 넣으면 지금과 같은 무방비 상태다.

## 5. 안 하는 것

- 푸시(FCM) — 벨 배지만. 푸시 작업이 끝나면 그때 붙인다
- 전체 공지 알림 — 다음 작업
- 첨부 이미지, 편지 삭제/회수
- 스팸 차단 — 대신 사용자 발신에 **분당 1통 · 1000자** 제한만 둔다

## 6. 순서

1. 마이그레이션 + 엔티티 + 리포지토리
2. `LetterService`(사용자) → 테스트
3. `AdminLetterService` → 테스트
4. 컨트롤러 2개 + `AdminApiKeyFilter` → 테스트
5. 실제 서버에 찔러 확인 (`/auth/guest`로 토큰 받아서)
