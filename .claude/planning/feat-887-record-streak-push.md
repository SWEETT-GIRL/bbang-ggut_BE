# 기록 스트릭과 내 빵순위 푸시 Spec 및 Plan

작성일: 2026-10-08 KST · 상태: #887 기반 구현 중 (실제 발송 미연결)

첫 주 푸시는 새로운 빵집 탐색보다 **기록하기 → 연속 기록 확인 → 내 빵순위 정리 → 남긴 기록 다시 보기**를 연결한다. 홈에 이미 있는 스트릭을 재사용하고, 실제 숫자를 넣어 오늘 기록하면 무엇이 달라지는지 알려준다. 신규 미션이나 별도 스트릭 보상은 만들지 않는다.

이 문서는 BE와 앱의 계약·구현 순서·검증 기준을 함께 다룬다. 구현 착수 요청 후 BE #887 (`dev` 기준), FE #148 (튜토리얼이 반영된 `main` 기준)의 별도 기능 브랜치를 생성했다. DB 변경·운영 발송·배포는 아직 하지 않는다. 아래 Spec의 미확정 운영 계약은 구현된 것으로 간주하지 않는다.

## 1 근거와 제품 결정

### 1.1 관측된 근거

8/31~9/30 신규 800명을 첫날 행동으로 구분하고 10/7까지 관측한 결과다. KST 달력 기준 정확한 D1·D7이며 내부 계정을 제외했다.

| 첫날 행동 | 대상 | D1 | D7 |
| --- | --- | --- | --- |
| 기록 완료 | 53명 | 14/53명, 26.4% | 5/53명, 9.4% |
| 탐색했지만 기록 미완료 | 488명 | 47/488명, 9.6% | 12/488명, 2.5% |

기록 완료자 53명 중 51명은 탐색도 했다. 기록의 인과 효과를 확정한 결과가 아니라, 기록까지 연결된 집단의 복귀가 더 높았다는 관측이다. 9/28~10/6 신규만 보면 D1은 기록 8/43명(18.6%), 탐색만 18/157명(11.5%)으로 격차가 작다. 새 더미 튜토리얼 한 건의 효과를 이 수치로 추정하지 않는다.

분모·날짜별 조회 링크: [행동별 리텐션 분석과 기록 중심 푸시 실험안](https://chatgpt.com/space/page_f3ad1558e1a48191b9366a824f2ddb4a).

### 1.2 확정된 방향

- 홈 스트릭을 없애거나 새로운 미션으로 바꾸지 않는다.
- **스트릭에는 튜토리얼 기록도 포함한다.** 2026-10-08 사용자 확인. 튜토리얼 다음 날 일반 기록을 남기면 2일 연속이다.
- 첫 일반 기록 전환·실제 기록량·순위 후보는 `RecordType.NORMAL`로 따로 판단한다.
- 오늘 기록 완료 여부와 실제 스트릭 숫자를 문구에 반영한다. 오늘 이미 기록한 사람에게 기록 독촉을 보내지 않는다.
- 현재 사진 필수, 기존 작성 흐름, 빵탑 보상, 튜토리얼 뒤 OS 권한 직접 요청은 유지한다.
- 탐색·지역 추천, 성장 미션, 스트릭 복구권·추가 보상, 별도 사전 알림 허용 시트는 범위 밖이다.

### 1.3 초기 운영 제안

- 첫 주 D1·D3·D5를 발송 기회로 둔다. D2·D4·D6·D7에는 정기 발송하지 않는다.
- 최대 3회, 하루 최대 1회, 캠페인 간격 최소 24시간. 스트릭이 이어져도 매일 발송하는 캠페인으로 자동 확대하지 않는다.
- 첫 후보 시각은 19:30 KST. 19:30~20:00 안에서만 처리하고 놓친 기회는 생략한다. 최적 시각이 검증된 것은 아니다.
- 최초 관측 후 최소 대기 12시간을 제안한다. D1 창까지 12시간이 안 지났으면 D1을 생략하며 D2에 보충하지 않는다.
- 정책·동의·대상 기준이 확정되기 전 기본값은 비활성화 및 dry-run이다.

## 3 Spec 스트릭의 단일 정의

### 3.1 기준

- 시간대: `Asia/Seoul`. 서버 `Clock` 주입으로 날짜 경계를 테스트한다.
- 기준 필드: **기록의 생성일 `createdAt`**, 먹은 날 `eatenAt`이나 수정일이 아니다.
- 대상: 해당 사용자 소유이며 삭제되지 않은 NORMAL과 TUTORIAL 기록. 공개·비공개 모두 포함한다.
- 같은 KST 날짜에 여러 건을 써도 하루다. 게스트에서 회원으로 승격·병합한 뒤에도 같은 원칙이다.
- 임시 저장·오프라인 대기·API 실패·튜토리얼 미리보기는 세지 않는다.
- 이전에 먹은 빵을 오늘 새로 작성하면 오늘 기록한 것이다. 기존 기록의 먹은 날짜만 수정하면 새 기록일이 생기지 않는다.
- 삭제된 기록만 남은 날짜는 스트릭에서 빠진다. 삭제 취소 기능이나 스트릭 복구는 추가하지 않는다.

### 3.2 계산 계약

`today`는 서버 기준 KST 날짜다. `recordDates`는 유효한 기록 생성일의 중복 없는 집합이다.

1. `recordedToday = recordDates.contains(today)`.
2. 오늘 기록이 있으면 오늘, 없으면 어제를 시작점으로 잡는다.
3. 시작점부터 하루씩 뒤로 이동하며 연속해서 존재하는 날짜 수가 `currentStreakDays`다.
4. 오늘 미작성일 때 `nextStreakDays = currentStreakDays + 1`. 오늘 작성했다면 추가로 한 건 써도 증가하지 않으므로 현재 값과 같다.
5. 오늘도 어제도 없으면 현재 스트릭은 0이며 다음 기록은 1일이다.

| 상태 예시 | 오늘 완료 | 현재 | 오늘 새로 작성한 뒤 | 사용할 안내 |
| --- | --- | --- | --- | --- |
| 기록 없음 | 아니오 | 0 | 1 | 첫 기록 1일 차 |
| 어제 튜토리얼 1건 | 아니오 | 1 | 2 | 오늘 남기면 2일 연속 |
| 어제까지 3일 연속 | 아니오 | 3 | 4 | 오늘 남기면 4일 연속 |
| 오늘 포함 4일 연속 | 예 | 4 | 4 | 유도 푸시 생략, 홈에서 4일 달성 |
| 그제 마지막 기록 | 아니오 | 0 | 1 | 오늘부터 다시 1일 |
| 어제 3건, 오늘 2건 | 예 | 2 | 2 | 건수가 아닌 기록한 날짜 수 |

오늘이 바뀌거나 데이터가 오래됐으면 숫자 문구를 만들기 전에 다시 조회한다. 숫자를 모르는 상태를 0일로 처리하지 않는다.

### 3.3 홈과 서버 계약 제안

기존 `/bread-records/summary`는 먹은 기간의 통계이므로 여기에 스트릭 의미를 혼합하지 않는다. 인증된 본인(게스트 포함)용 `GET /bread-records/activity`를 추가하는 안이다.

응답 필드:

| 필드 | 의미 |
| --- | --- |
| `asOfDate`, `timeZone`, `computedAt` | KST 기준 날짜, 시간대, offset 있는 계산 시각 |
| `recordedToday`, `currentStreakDays`, `nextStreakDays` | 홈과 발송에 쓰는 동일 정의 |
| `activeRecordCount`, `normalRecordCount` | 삭제 제외 전체 및 NORMAL 기록 수 |
| `lastRecordedDate` | 마지막 유효 생성 날짜, 없으면 null |
| `latestNormalRecordId`, `latestNormalEatenDate` | 달력 연결용. 없으면 null |
| `policyVersion` | 예: `CREATED_KST_INCLUDE_TUTORIAL_V1` |

홈은 지원 서버에서 이 값을 사용한다. 생성·수정·삭제·병합 완료·앱 foreground·KST 자정에 다시 조회한다. 새 정책 미지원 버전에는 숫자 캠페인을 보내지 않는다. 네트워크 오류 시 오래된 숫자를 확정값으로 보여주거나 ‘0일’로 바꾸지 않고, 기존 표시를 유지하되 유도는 보류한다. 새로 생성한 기록 후에는 결과 재조회가 끝나기 전 임의로 N+1을 더하지 않는다.

## 4 Spec 대상과 최소 상태 분기

### 4.1 신규와 D0

- 제품 정의는 최초 앱 관측일 KST가 D0다. 게스트 포함, OAuth 로그인 전환으로 초기화하지 않는다.
- `firstAppSeenAt`의 서버 수집·식별 연결을 구현 전 확정한다. Amplitude `_new` 분석 기준과도 대조한다.
- 제안: 앱이 최초 관측 시각을 보존하고, 최초 인증 시 서버 캠페인 등록에 전달한다. 기존 설치를 새 유입으로 취급하지 않도록 신규 설치 판별·기존 사용자 제외·시각 유효성 검사를 함께 둔다.
- 클라이언트 시간은 무조건 신뢰하지 않는다. 미래 시각·재설치·계정 전환·기존 계정 로그인·오래된 오프라인 최초 실행 처리와 허용 오차를 계약화한다. 신뢰할 최초일을 확정할 수 없으면 캠페인에는 미등록한다.
- 기존 회원을 기능 출시일 기준 D0로 일괄 등록하지 않는다. 회원 생성일이나 튜토리얼 완료일로 바꾸려면 지표 이름과 대상 정의까지 명시적으로 승인받는다.
- D1·D3·D5는 최초 관측일로부터 달력 날짜 차이다. D7 이후 캠페인은 종료한다.

### 4.2 발송 우선순위

관심 점수나 매일의 행동 분류 테이블을 만들지 않고, 유효 기록·스트릭·순위 상태와 캠페인 이력만 사용한다.

| 기회 | 1순위 | 2순위 또는 생략 |
| --- | --- | --- |
| D1 | 오늘 미작성이고 어제부터 이어진 스트릭이면 연속 기록 응원 | 스트릭 0이고 NORMAL 기록이 없으면 첫 실제 기록 안내. 오늘 기록했다면 이 기회는 생략 |
| D3 | 회원이며 NORMAL 기록으로 순위 시작이 가능하고 같은 안내를 안 받았다면 내 빵순위 | 순위 대상이 아니며 D1 기록 안내 후 새 기록을 실제로 남겼고 오늘 미작성·스트릭 유지 중이면 연속 응원. 아니면 생략 |
| D5 | NORMAL 기록이 있고 달력 안내 미발송이면 기록 다시 보기 | 없으면 생략 |

이번 안에서는 D1을 기록 실험, D3을 취향 정리 기회로 명확히 구분한다. 앞선 초안의 ‘D1에 기록자에게 곧바로 순위 안내’는 첫 구현에서 제외한다. 오늘 작성자는 **기록 유도에서만 제외**되며 D3의 순위·D5의 달력은 각 조건을 충족하면 받을 수 있다. 어느 경우든 한 번에 한 메시지다.

NORMAL 기록이 없어도 어제 튜토리얼을 썼다면 D1 첫 기록 1일 문구가 아니라 **2일 연속 문구**를 쓴다. 일반 기록이 없다는 것과 스트릭이 0이라는 것을 혼동하지 않는다.

‘첫 기록’ 문구는 현재 유효 기록이 전혀 없는 사용자에게만 쓴다. 튜토리얼만 있거나 이전 작성·삭제 이력이 있으면 ‘네가 먹은 빵을 남겨볼까?’를 사용한다. ‘다시 1일’은 과거 기록 이력이 확인될 때만 가능하며 첫 버전에서 재시작 푸시를 별도 추가하지 않는다.

### 4.3 내 빵순위 적격성

- 기존 API처럼 로그인 회원만 대상이다. 게스트에게 순위 작성을 약속하고 로그인 벽으로 보내지 않는다.
- 삭제되지 않은 NORMAL 기록에 연결된 ACTIVE 가게가 있어야 한다. 가게 직접 입력만 있고 storeId가 없는 경우, 튜토리얼 전용 가게는 제외한다.
- 실제 카테고리·가게를 기존 API에서 추가하고 순위를 부여할 수 있어야 한다. 기록 2건 이상 같은 임의 조건을 추가하지 않는다.
- 초기 메시지는 ‘내 빵순위 첫 작성’이다. 이미 순위가 있으면 미완료자로 취급하지 않는다. 새 빵 이후 순위 업데이트 개인화는 후속 범위다.
- 빵 종류가 확실하지 않으면 소금빵 취향으로 추정하지 않는다. 여러 후보의 관련성 선택이 불확실하면 일반 내 빵순위 화면으로 연결하거나 해당 기회를 생략한다.

## 5 Spec 메시지 계약

서버가 제목·본문과 버전·숫자 snapshot을 관리한다. 첫 버전은 코드 템플릿으로 시작하고 어드민 편집 UI를 추가하지 않는다. `{next}`에는 계산한 정수만 들어가며 치환 실패 시 보내지 않는다.

| 키 | 제목 | 본문 | 조건 |
| --- | --- | --- | --- |
| `FIRST_RECORD` | 오늘 먹은 빵 있어? 🥐 | 첫 빵로그를 남기고, 오늘부터 기록 1일 차! | 기록 없음·현재 스트릭 0·오늘 미작성 |
| `FIRST_NORMAL_RECORD` | 이번엔 네가 먹은 빵을 남겨볼까? 🍞 | 빵로그를 남기면 네 빵탑에 빵이 하나 더 쌓여! | 튜토리얼/이전 경험은 있으나 NORMAL 없음·스트릭 0 |
| `STREAK_CONTINUE` | 오늘 남기면 {next}일 연속이야! 🔥 | 오늘 먹은 빵 있어? 빵로그로 남기고 기록을 이어가 보자! | 어제까지 현재 N≥1·오늘 미작성, next=N+1 |
| `MY_BREAD_RANKING` | 먹어본 빵, 맛있었던 순서로 정리해봐 🏆 | 내 빵순위에서 빵 종류별로 가게 순위를 매길 수 있어! | 실제 순위 등록 가능·첫 순위 안내 |
| `RECORD_CALENDAR` | 어떤 빵을 먹었는지 달력에서 확인해봐 📅 | 날짜를 누르면 그날 남긴 빵로그를 다시 볼 수 있어! | 유효 NORMAL 기록이 있는 날짜로 연결 |

`STREAK_RESTART` 후보: “오늘부터 다시 1일! 🍞 / 먹은 빵이 있다면 다시 기록을 이어가 보자!”는 첫 주 기본 규칙에 넣지 않고 재활성화 실험으로 보류한다.

‘오늘 먹었다’고 단정하지 않는다. ‘끊기면 손해’, ‘빵댕이가 굶고 있어’처럼 죄책감·손실을 자극하지 않는다. 사진만 고르면 작성이 모두 끝난다고 약속하지 않는다. 광고성으로 분류되면 승인된 표시·수신 거부 안내를 최종 문구에 반영해야 하며 위 문구를 그대로 발송 승인본으로 보지 않는다.

기존 홈 칩은 2일 이상 표시를 유지한다. 오늘 작성 후 `N일 연속`과 축하 멘트가 갱신되면 된다. 1일 칩·별도 모달·새 보상 애니메이션은 이번 필수 범위가 아니다.

## 6 Spec 발송 자격과 취소

발송 예약 때와 외부 전송 직전에 모두 확인한다.

1. 캠페인 활성화, 지원 앱 버전·환경·정책 버전 일치.
2. 활성 계정이며 삭제·쓰기 제재·게스트 쓰기 차단 등 목적 행동을 막는 조건이 없음.
3. 메시지 목적에 맞는 동의, 알림 수신 설정, 유효한 기기 토큰.
4. 사용자 요일·시간대와 캠페인 발송 창을 모두 충족. 시간대가 없으면 캠페인 기본 창을 사용하고, 명시 설정과 충돌하면 생략.
5. D일차·최소 대기·24시간 간격·하루 1회·주간 3회·주제별 중복 조건 충족.
6. 최신 기록·스트릭·순위·달력 대상이 문구와 일치.
7. 목적 화면 접근 가능, 관련 대상 미삭제, 데이터 조회 성공.

알림 허용 OS 상태는 서버가 실시간으로 완전히 알 수 없으므로 ‘토큰 있음=현재 허용’으로 보고하지 않는다. 앱이 관측한 거부는 토큰/설정에 반영하며 서버는 확인 가능한 상태로만 판단한다.

리텐션 캠페인의 광고성 분류·필요 동의는 운영 승인 게이트다. 기존 `NOTICE`로 우회하지 않는다. 분류가 미정이면 실발송 금지. 새 `RETENTION_TIP` 타입을 추가하더라도 필요한 마케팅 동의 검사 여부를 명시적으로 정하고 누락 방지 테스트를 둔다. 법적 결론을 이 설계에서 대신 내리지 않는다.

당일 기록 유도는 조회 직후 기록 생성과 경합할 수 있다. 최종 재조회·기록 생성 시 미전송 후보 취소로 창을 줄이되, 이미 FCM에 인계된 메시지는 회수하거나 표시를 보장할 수 없다. 이 한계를 숨기지 않는다.

원래의 ‘두 번 전송 후 무복귀면 중단’은 서버에 복귀 관측이 있어야 적용한다. 첫 주 실험에 필요한 최소 활동 신호가 준비되면 각 발송 후 24시간 구간의 복귀로 판단한다. 아직 그 신호가 없거나 적재 지연이면 ‘무복귀’로 판정하지 않는다. 이 경우 dry-run 또는 D1 단일 발송부터 시작하고, 검증 없이 D5까지 자동 확장하지 않는다.

## 7 Spec 저장과 전송 안정성

### 7.1 기존 구조 재사용

`Notification`, `NotificationRecipient`, `NotificationDelivery`, `PushDispatcher`, `FcmService`는 재사용한다. 날짜별 숫자가 사용자마다 다르므로 개인별 notification을 생성한다. 전체 공지 fanout에 개인 숫자를 넣지 않는다. 선택적 캠페인의 예약·취소는 기존 운영 알림과 격리한다.

월간 보고서의 예약 선점·전송·결과 저장 구조를 참고하되 테이블은 도메인별로 유지한다. 모든 알림을 처리하는 범용 캠페인 엔진으로 확장하지 않는다.

### 7.2 최소 논리 저장안

| 저장 단위 | 필수 정보 |
| --- | --- |
| `retention_campaign_enrollment` | member, 안정적인 campaignSubjectId, campaignVersion, firstAppSeenAt와 근거, D0, experimentArm, ACTIVE/STOPPED/FINISHED, 마지막 확인된 활동 시각 |
| `retention_campaign_dispatch` | enrollment, opportunityDay, messageKey·copyVersion, 예정일·만료, 상태·사유, notificationId, 현재/목표 streak snapshot, 기준일·정책, claimToken, claim 시각·전송 시도·결과 |

SQL 이름과 필드는 구현 시 최종 확정한다. 새로운 일별 관심 행동 테이블은 만들지 않는다. `notification_delivery`는 기존 최종 전송 결과를 유지하고, 캠페인 의사결정·생략 사유는 dispatch에서 관리한다.

유니크 키는 사용자 캠페인 버전별 enrollment, `(enrollment_id, opportunity_day)`별 기회다. 문구 버전이나 선택 주제를 바꿔 같은 날 새 푸시가 만들어지지 않게 한다. 하루/24시간/주제 중복 검사와 후보 생성은 같은 enrollment 잠금 아래 판정한다. 게스트 병합은 source·target 순서 고정 잠금, 가장 이른 유효 시작일, 기존 배정·발송 이력 유지, 미전송 중복 취소를 한 흐름으로 처리한다.

새 계정으로의 게스트 승격은 같은 캠페인을 유지한다. 기존 회원에 병합되면 기존 회원을 신규로 재등록하지 않는다. 이미 참여한 양쪽의 실험군이 충돌하면 임의 재추첨하지 않고 mixed-exposure로 표시해 분석·발송 정책을 별도 적용한다.

### 7.3 상태와 경계

상태 제안: `PLANNED → CLAIMED → SENDING → SENT | FAILED | UNKNOWN`, 또는 전송 전 `SKIPPED | CANCELLED | EXPIRED`.

- 트랜잭션 A: 선점·최신 상태 검증·문구 확정·notification 연결 후 커밋.
- 외부 호출: DB 트랜잭션·행 잠금을 잡지 않고, 캠페인 worker만 한 번 인계한다. 같은 건에 기존 비동기 이벤트까지 발행해 이중 발송하지 않는다.
- 트랜잭션 B: claim 소유권 확인 후 결과 저장.
- SENDING 상태에서 네트워크 타임아웃 또는 프로세스 종료가 나면 FCM 접수 여부를 모를 수 있다. **UNKNOWN은 자동 재전송하지 않는다.** 외부 표시까지 exactly-once라고 주장하지 않는다.
- 첫 버전은 꿀팁의 중복을 피하기 위해 외부 전송 시작 뒤 자동 재시도를 하지 않는 보수적 정책을 제안한다. 전송을 시작하지 않은 선점만 안전하게 회수한다.
- 여러 기기에 보낼 때 회원 단위 한 번의 캠페인이다. 지원 버전 토큰만 선택해야 하므로 Dispatcher의 전체 토큰 발송을 그대로 호출해 구버전까지 보내지 않는다. 기기별 실패 때문에 이미 받은 기기로 재발송하지 않는다.
- 기존 FCM TTL은 1시간이다. 이 캠페인은 발송 창·KST 당일 경계를 넘지 않는 만료를 적용한다. 다른 알림의 TTL을 전역 변경하지 않는다.
- 이미 알림함에 적재한 뒤 자격이 사라진 경우의 처리도 정한다. 전송 전 취소된 캠페인 recipient는 숨기거나 비노출 상태로 처리해 오래된 ‘오늘 N일’이 미읽음으로 남지 않게 한다. 발송 완료 이력은 과거 발송 날짜와 함께 보존한다.

## 8 Spec 앱 도착 경험과 계측

### 8.1 도착 경험

- 기록: 현재 `openRecord(...)` 진입 함수를 재사용한다. 임의의 존재하지 않는 `/record/create` 경로를 넣지 않는다. 제안하는 앱 진입 경로는 `/retention-entry`이며 목적 enum을 검증하고 준비 후 기존 플로우를 호출한다.
- `RECORD_CREATE`, `MY_BREAD_RANKING`, `RECORD_CALENDAR` 세 목적만 허용한다. 링크에 들어온 memberId로 계정을 바꾸거나 상대 기록을 조회하지 않는다.
- cold start, background, 앱 실행 중 진입, 인증 복원·약관·게스트 제한 후 원래 목적 유지, 초기 튜토리얼과 중첩되지 않는 동작을 검증한다.
- 순위는 기존 `/bread-ranking`으로 연결한다. 필요한 후보가 없어졌으면 안내 후 일반 화면으로 복귀하고 가짜 순위나 후보를 만들지 않는다.
- 달력은 기존 `/bbanglog/log`에 `latestNormalEatenDate`를 전달해 해당 날짜를 선택하는 계약을 추가한다. 스트릭 날짜(createdAt)와 달력 날짜(eatenAt)를 혼동하지 않는다.
- 만료되었거나 이미 오늘 기록한 기록 유도 푸시를 눌렀으면 홈의 최신 스트릭을 보여준다. 과거 목표 숫자를 현재 목표처럼 고정하지 않는다.
- 푸시 진입 그 자체로 기록 생성, 보상 지급, 스트릭 증가가 일어나지 않는다.

### 8.2 Payload와 계측

FCM data와 알림함 모두 같은 `campaignId`, `campaignVersion`, `dispatchId`, `notificationId`, `messageKey`, `copyVersion`, `opportunityDay`, `asOfDate`, `policyVersion`, `expiresAt`, `destination`을 전달한다. 숫자 문구에는 `currentStreakDays`, `nextStreakDays`도 포함한다. 기기에 토큰 원문·사진·메모·다른 사용자의 정보는 넣지 않는다.

앱 `push_open`에 발송 식별자를 추가하고 `retention_destination_view`로 실제 도착을 별도 확인한다. `record_create_success`에는 `record_type`과 출처, `my_bread_rank_set`에는 같은 출처, 달력의 실제 기록 열람에는 `recordId`와 출처를 붙인다. 클릭과 도착에서 같은 알림을 중복 기록하지 않도록 message/dispatch ID로 중복 처리를 방지한다.

직접 기여 출처는 같은 앱 세션에서 최장 30분을 초기안으로 두고, 목적 행동 완료·로그아웃·다른 캠페인 진입 시 해제한다. ‘발송 후 24시간 안에 발생한 행동’은 별도 관측 창이며 직접 기여와 섞지 않는다. 출처 없이 자발적으로 발생한 기록도 실험군 전체 효과에는 포함한다.

발송 결과는 FCM 수락·실패·불명, 앱 클릭·화면 도착은 실제 클라이언트 관측으로 구분한다. 서버 전송 결과를 OS 표시·열람으로 표현하지 않는다.

## 9 Spec 실험과 성공 기준

- 1차: D1 첫 기록/스트릭 응원 대 미발송 대조군. 안정적인 사용자 단위 무작위 배정, 같은 기존 운영 알림 정책.
- 2차: D3 내 빵순위·D5 기록 확인을 추가한 첫 주 시리즈. D1 단일 실험과 캠페인 버전을 구분한다.
- 주요 효과: 기존 정의의 D1·D7 복귀, 첫 NORMAL 기록 전환, 추가 NORMAL 기록, 내 빵순위 첫 저장.
- 보조 효과: 홈 스트릭 증가, 목적 화면 도착, 달력 기록 열람. 튜토리얼 포함 스트릭과 NORMAL 전환을 따로 보고한다.
- 안전 지표: 수신 거부·관측 가능한 권한 해제, 중복 전송, 발송 실패·UNKNOWN, 숫자 불일치, 도착 실패.
- 발송 가능 신규 인원 확인 후 배정 비율·기간·필요 표본·효과 기준을 결정한다. 표본 부족 시 결론을 유보한다.
- 클릭자만의 리텐션을 효과로 제시하지 않는다. D3·D5가 D1을 높였다고 해석하지 않는다. D7 성숙 코호트만 비교한다.
- 숫자 불일치·중복·동의 위반이 발생하면 해당 캠페인을 즉시 중지하고 원인을 확인한다. 정량적 품질/효과 중단선과 책임자는 실발송 전에 확정한다.

### 구현 범위

- `/retention-entry`와 `RETENTION_TIP` payload 검증, 기존 openRecord 로그인 게이트, 순위 화면, 달력의 먹은 날짜 연결. 만료·오류·오늘 작성·게스트 순위 접근은 안전한 화면으로 돌아간다.
- `push_open`에 dispatch/campaign/message 식별자를 추가. NORMAL 기록 완료와 해당 진입 후 첫 순위 저장의 같은 계정·세션 30분 이내 기여를 분리한다. 튜토리얼은 기존 TUTORIAL 이벤트를 유지한다. 계정 생애 최초 순위 저장 여부는 별도 서버 지표이며 이 이벤트만으로 확정하지 않는다.
